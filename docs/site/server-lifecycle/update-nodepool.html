update-nodepool — what actually happens

One request sets how many workers of one hardware kind a hosted cluster runs. You give the total; the run spreads it over the cluster’s NodePools of that kind so that no two are more than one replica apart, writes the new replicas into the cluster’s day1 file, has Argo CD apply that commit, and checks that the NodePools on the MCE show it.

Or one NodePool, by name. Send nodepool instead of infra_env_kind and replicas is that NodePool’s own number, set exactly: no spread and no balance rule, the other NodePools left as they are.

The day1 file owns replicas. Nothing on the MCE is written directly: the change is one commit to day1 main, synced by Argo CD. The run scales up or down through a child workflow — scale-up-nodepool or scale-down-nodepool — and on a scale-down a NodePool that names a scale-down policy has the servers that leave chosen and marked first. Without one, CAPI picks at random, as it always has.

Done means the NodePools show the new replicas, not that new nodes are Ready (decided with the operator, 2026-11-03). After a scale-up HyperShift creates the Machines, and each one takes a free Agent of its InfraEnv when there is one. The servers a scale-down removes stay in the MCE’s inventory, free Agents again.

Which NodePools

The InfraEnv kind, and only this cluster’s NodePools

A NodePool takes Agents from the InfraEnv its selector names: spec.platform.agent.agentLabelSelector.matchLabels["infraenvs.agent-install.openshift.io"]. It is of kind K when that InfraEnv is exactly K, or K followed by - and anything. Nothing after the dash is read, and no zone label is needed.

infra_env_kind cisco-m6-bat-yam-64c-512gbits kind?
cisco-m6-bat-yam-64c-512gbyes
cisco-m6-bat-yam-64c-512gb-zone-ayes
cisco-m6-bat-yam-64c-512gb-b2yes
cisco-m6-bat-yam-64c-512gbxno — no dash after the kind

A shorter kind also takes the longer kinds that start with it: cisco-m6 would select every cisco-m6-* NodePool. The result lists every NodePool selected with its InfraEnv, so a kind that is too wide shows there.

A kind exists only on the Agent platform. A KubeVirt NodePool (platform: kubevirt, the sandbox’s ocp4-upgrade-demo) takes VMs, not Agents: it has no InfraEnv, so no kind selects it (NodePoolKindNotFoundError). Set such a NodePool by name.

Only the NodePools of the cluster you name count: those in its HostedCluster’s namespace whose spec.clusterName is that HostedCluster. Another cluster’s NodePools of the same kind, on the same MCE, are never counted and never changed.

update-nodepool, then its child

What the run does

Each card carries a phase, read live through the progress query of the run it belongs to. The parent also reports direction and, while its child runs, child_workflow_id.

1

read_day1_cluster

phase reading-day1

The cluster’s file in day1 main, read by the hub’s upgrade-gitops worker: its path, its git blob, the HostedCluster it renders (openshift-<clusterName> in hcp-<clusterName>), and each nodepool[] entry’s name, replicas (the chart’s default 1 when absent) and InfraEnv (infraEnvName, else agentLabelSelector.nodeLabelValue).

The file must sit under sites/<site>/mces/<mce_cluster>/, or the run stops with ClusterNotOnMceError before reading anything on the MCE. A file the chart would refuse (a key written twice, a NodePool named twice) stops it with Day1ClusterProblemsError.

2

read_hosted_cluster

phase reading-nodepools

The HostedCluster’s NodePools on the MCE, read by the MCE’s cluster-upgrade worker: spec.replicas, the InfraEnv of the selector, and the redbull.io/scale-down-policy label or annotation. The kind’s NodePools are selected here.

With nodepool, only that NodePool is selected, whatever its kind; one the cluster has on neither side is NodePoolNotFoundError.

Live and day1 must agree, both ways: every NodePool of the kind on the MCE is in day1 under its name with the same replicas and InfraEnv, and every one of the kind in day1 is on the MCE. Anything else stops the run with NodePoolReplicasDriftError, naming each NodePool, before anything is written — a NodePool made by hand, one Argo CD has not created yet, replicas someone changed on the cluster.

3

The plan

phase planning

By kind: NodePools already more than one replica apart are refused (NodePoolsUnbalancedError): balancing them is a person’s edit, never a side effect. Otherwise the new total is spread one replica at a time. By name: the NodePool takes exactly the number asked — no balance check, even if its kind then ends more than one apart (a later run by kind is refused until they are evened out).

Already what was asked: the run completes here, direction: "none", nothing written.

4

The child

phase scaling-up · scaling-down

scale-up-nodepool or scale-down-nodepool, awaited, on its own id and queue. Its result is the parent’s scale. It is abandoned, never cancelled, if the parent is closed: it marks Machines and writes git in an order that must not be cut.

5

read_scale_down_candidates · mark_machines_for_deletion

phases selecting-servers · marking-machines — scale-down, with a policy

Only when a NodePool that loses replicas names a policy. The MCE’s server-lifecycle worker reads that NodePool’s Machines (by HyperShift’s hypershift.openshift.io/nodePool annotation), and through the hosted cluster’s admin kubeconfig their Nodes, Pods and — for least-utilized — NodeMetrics. The run ranks them, then puts cluster.x-k8s.io/delete-machine: scale-down-nodepool-<cluster> on each chosen Machine and reads it back. CAPI deletes a marked Machine before any other, so the commit that follows removes exactly those.

Refused with nothing written: an unknown policy value, a Machine already deleting, a delete mark this run did not write, a Machine count that is not the replicas, Machines in two MachineSets (a rollout). A mark an earlier attempt of this run left on a Machine not chosen now comes off first.

6

commit_day1_change

phase committing-day1

The new replicas of every NodePool that moves, in one commit to day1 main, nodepool(<cluster>): replicas a 3→4, … [<run id>]. Only those replicas: lines change; comments and quoting stay. Compare-and-set on the blob read in step 1: a file someone else changed since is never committed over (Day1FileChangedError). day1’s validator runs first when one is configured.

On a scale-down, a refused commit takes the run’s marks off again (unmarking-machines) before it fails.

7

sync_argo_application · read_hosted_cluster

phases syncing-argo · verifying-nodepools

The cluster’s Argo CD Application synced to exactly that commit. Only the moved NodePools may be out of sync; anything else pending is someone else’s change and the sync is refused (ArgoSyncRefusedError). Then the NodePools are read back: each must show its planned spec.replicas, or NodePoolsNotReconciledError.

8

watch_marked_machines

phase verifying-machines — scale-down, with marks

One heartbeating watch, every 15 s for up to 10 minutes, until every marked Machine is deleting or gone. An unmarked Machine of those NodePools deleting instead is ScaleDownWrongMachineError — named, and it cannot be undone. The run does not wait for the drain or for the Agent to come free.

The rule a scale keeps

How the total is spread

One replica at a time. Up: to the NodePool with the fewest. Down: from the one with the most. Ties go by InfraEnv name, then NodePool name — ascending going up, descending going down — so the first NodePool in that order keeps the extra one. From a balanced start every step stays balanced, and no NodePool ever moves the other way.

scale-down-nodepool

Which servers leave: the NodePool’s own policy

Set on the NodePool, never in the request: a label or an annotation redbull.io/scale-down-policy. The run reads it off the NodePool on the MCE, which is what Argo CD rendered from day1 (or what a person set there). The spread rule decides how many each NodePool loses; the policy decides which of its Machines.

valuewhich servers leave first
absentNothing is marked. CAPI’s MachineSet picks — at random, HyperShift’s default.
fewest-podsThe fewest workload pods: the least for the drain to move. Workload means not a DaemonSet’s, not a mirror pod, not finished — the drain’s own rules.
least-requestedThe lowest share of the Node’s allocatable its pods request, the larger of CPU and memory. From the pods’ requests, as the scheduler counts them; no metrics needed.
least-utilizedThe lowest live use of allocatable, the larger of CPU and memory, from metrics.k8s.io on the hosted cluster. A cluster with no metrics API fails the run (NodeMetricsUnavailableError); a Node that just joined is waited for until its metrics appear.
anything elseRefused before anything is marked or written: ScaleDownPolicyInvalidError.

Under every policy the order is:

  1. Machines CAPI counts unhealthy — no nodeRef, a failure, or NodeHealthy / HealthCheckSucceeded False, read off the Machine exactly as CAPI’s isMachineHealthy does — by name;
  2. a Machine already carrying this run’s mark, so a re-run keeps its choice;
  3. a Node the hosted cluster does not have, or has NotReady or cordoned, while CAPI still counts the Machine healthy;
  4. the policy’s reading. Ties go by Machine name.

Different NodePools of one kind may name different policies, or none.

Why the mark decides which servers go

HyperShift backs an InPlace NodePool with one CAPI MachineSet and a Replace one with a MachineDeployment, sets their replicas from the NodePool, and sets no delete policy — so CAPI’s default, Random, applies. On a scale-down the MachineSet ranks its Machines and removes the top ones, ties by name. Under Random a Machine annotated cluster.x-k8s.io/delete-machine outranks every healthy one in every CAPI version, and an unhealthy one from CAPI 1.9 on (OpenShift 4.19 and later). In 4.18’s CAPI a marked and an unhealthy Machine rank the same, which is why CAPI-unhealthy Machines come first, in CAPI’s own order: the Machines CAPI removes are then exactly the marked ones in every version.

The mark only orders Machines inside one MachineSet. A Replace NodePool in the middle of a rollout has two, and its MachineDeployment may scale down the other one: a NodePool whose Machines span two MachineSets is refused (ScaleDownRolloutInProgressError). HyperShift leaves annotations on Machines alone; its own docs annotate them with another CAPI annotation (machine.cluster.x-k8s.io/exclude-node-draining). The watch after the sync still checks that the marked Machines are the ones deleting.

Setting it in day1. Under the NodePool’s nodepool[] entry, as a label or an annotation. The hostedclusters-setup chart passes every label of an entry and its annotations onto the NodePool (since 2026-11-08, GitHub copy):

nodepool:
  - infraEnvName: dell-r660-128c-1024gb
    replicas: 3
    labels:
      allowDeletion: false
      redbull.io/scale-down-policy: fewest-pods

The air-gapped GitLab copy of the chart renders only allowDeletion, maxReplicas and minReplicas until it gets the same change. There, set the key on the NodePool directly (oc label nodepool <name> -n hcp-<cluster> redbull.io/scale-down-policy=fewest-pods); Argo CD leaves a label it never set alone.

The maxReplicas / minReplicas labels are not the run’s (the operator, 2026-11-08). The commit changes replicas only. Left unwritten, the chart derives them from replicas (replicas and replicas − 1), so they follow; written in the entry, they keep the value written.

When it stops

Refused before anything is written, or stopped after

Every one is a FAILED run on the status endpoint. A child’s failure fails the parent with ScaleNodePoolFailedError, whose message carries the child’s own type and message.

After the commit — the commit stays in day1

errorwhen
ArgoSyncRefusedErrorSomething else in the Application is out of sync. The marks stay: when the commit is applied, CAPI removes the marked Machines first.

Out-waited, never failed

Every call retries without limit, backing off to once a minute: day1 unreachable or a push that lost a race with another commit, an MCE or hosted API server that is down, an Argo CD sync that failed or found another operation in progress. The run sits RUNNING with the failure on the activity. A call no worker picks up within 5 minutes — that worker not deployed, or not on this MCE — fails the run instead.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async: the POST hands back the workflow id at once and you poll it. The children have no route of their own. The API has no auth of its own: anyone who can reach it can change a cluster’s workers.

POST /workflows/server-lifecycle/update-nodepool 202 · 409 while a run or an upgrade of the cluster runs · 422 on a bad body

  "cluster":        "ocp4-prod-alpha",             // the day1 file's name, without .yaml

update-nodepoolpending → reading-day1 → reading-nodepools → planning → scaling-up | scaling-down → completed
scale-up-nodepoolpending → committing-day1 → syncing-argo → verifying-nodepools → completed
scale-down-nodepoolpending → [selecting-servers → marking-machines] → committing-day1 [→ unmarking-machines] → syncing-argo → verifying-nodepools [→ verifying-machines] → completed
whatwhere
the three workflowsthe workflows-orchestrator brain, each on its own queue
day1 read and commitupgrade-gitops-activity, the hub’s upgrade-gitops-worker (it holds the day1 push token)
NodePools, Argo CD synccluster-upgrade-activity-<mce>, the cluster-upgrade-worker inside that MCE (get/list on NodePools)
Machines, hosted Nodes and Pods, the marksserver-lifecycle-activity-<mce>, the server-lifecycle-worker inside that MCE (list/patch on Machines, its existing rbac.hostedClusters grant)

What it never does

  • No write to a NodePool, HostedCluster or Node on the MCE — the change is day1’s, applied by Argo CD.
  • No commit over someone else’s edit, and no sync of someone else’s pending change.
  • No balancing of NodePools that are already more than one replica apart.
  • No removal of a server from the MCE: the servers a scale-down frees stay in the inventory.
  • No wait for new nodes to be Ready, or for a drain to finish.
