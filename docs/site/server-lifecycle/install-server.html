Temporal workflow · domain: server-lifecycle

install-server — what actually happens

One request makes a physical server installable in an MCE InfraEnv: the workflow asks server-scan for a healthy, unclaimed machine matching that InfraEnv, picks two NICs for a bond, and creates the three Kubernetes resources the Assisted Installer needs — a BareMetalHost, its BMC Secret and an NMStateConfig.

It replaces bmh-generator-operator (BareMetalHostUCS), a Kopf operator that queried HP OneView, UCS Central, Dell OME and Intersight live on every reconcile. server-scan already collects all of that on a 6-hour cron, so one HTTP call replaced four vendor SDKs.

The first thing to know

Two ways to trigger it: name a server, or don’t

server_name is optional, and leaving it out is the normal mode. The InfraEnv’s own name is then the hardware query, so you ask for “a server for this InfraEnv” and the workflow decides which one.

Naming a server narrows the pool — it does not lower the bar

Every other rule applies identically in both modes: HEALTHY only, at least two NIC MACs, two link-up NICs on two distinct physical ports, a bmc_vendor this orchestrator has an Ironic driver for, and well-formed MACs. So a named server that cannot carry a bond fails exactly as it would have inside a pool draw.

The only behaviour a name changes is the already-installed skip. Naming a machine is a request to converge that machine, so an existing BareMetalHost is the expected state rather than a reason to move on.

Why the pattern is just a prefix

An InfraEnv’s name states which hardware it is for — cisco-m6-bat-yam-64c-512gb is vendor, model, site, cores, memory — and server-scan names carry the same tokens behind an ocp- prefix. So the query is ^ocp-<infraEnv>: neither name is parsed apart, and there is no mapping table to keep in step with either.

The InfraEnv name is caller data going into a regex, so it is escaped. Today’s names are [a-z0-9-] and it changes nothing — a . would silently widen the pool without it.

Five phases, in order

What the run does

Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run an install currently is.

1

get_inventory_segment

phase resolving-vlan

The MCE’s INVENTORY segment, found by cluster name — one inventory network per cluster, so the VLAN is a property of the MCE this run targets and of nothing else. It is read before a candidate is drawn, because no machine the draw might return could make a missing allocation usable.

GET/api/segments?type=INVENTORY · once per run, on the SEGMENT-LIFECYCLE queue

On the other domain’s queue on purpose: the Segments Manager token already lives on segment-lifecycle-worker, and routing one activity there beats a second copy of that credential on this limb. The endpoint has no cluster_name filter, so the cluster match is made client-side — and re-checked in the workflow, because this is the one value that decides which VLAN a host is tagged onto.

No segment for this MCE → InventorySegmentNotFoundError; two → AmbiguousInventorySegmentError; one belonging to another cluster → InventorySegmentMismatchError. All three non-retryable — an operator fixes the allocation, retrying does not. There is deliberately no vlan_id input: a caller-supplied VLAN could contradict the segment the cluster owns.

2

acquire_servers

phase acquiring-server

One read against server-scan, which returns machines that are unclaimed, reachable, not in maintenance and at the requested health — live-rechecking each one it hands back, so freshness is its problem rather than ours. Several candidates are drawn (candidate_count) so that one unusable server is a retry rather than a failed run.

GET/servers/available?pattern=…&health=HEALTHY&min_nic_macs=2&count=N

HEALTHY is asked for server-side: without it the endpoint fills HEALTHY, then WARNING, then MAJOR, and a WARNING server would be returned — and live-rechecked at a vendor manager’s expense — only to be discarded here. Nothing assignable → ServerNotAvailableError; a name spanning several documents → AmbiguousServerNameError.

3

Candidate selection

phase selecting-server

The first candidate that survives every one of these is the one installed. Most of it is pure workflow logic — no activity, no round trip, and it replays identically:

  1. its server-scan name can be a Kubernetes resource name once lowercased;
  2. its bmc_vendor is one this orchestrator has an Ironic driver for — a STANDALONE machine reports null, and guessing IPMI would be silently wrong for a Redfish-only BMC;
  3. server-scan actually collected a BMC host for it;
  4. it offers two link-up NICs on two distinct physical ports (below);
  5. those MACs are well-formed;
  6. it does not already have a BareMetalHost — one read per surviving candidate, skipped when a server_name was given;
  7. no other run holds server-scan’s install lock on it (phase reserving-server) — the lock is taken here, before anything is written.
GETbaremetalhosts/<server> · per surviving candidate, on the MCE’s queue
POSTserver-scan /servers/{id}/reservation · the chosen candidate

The lock is the guard across MCEs. server-scan lists a machine AVAILABLE until a cluster reports it, and the probe above only sees this MCE — so without it a server installed into MCE-A is drawn again by a run for MCE-B, and both clusters drive one BMC (server-scan’s ADR-0035). It is keyed on this run’s workflow id, so a retry or a renewal extends it; it is renewed as the Agent wait begins, extended to a day on success (phase holding-server), and released only after a rollback’s teardown. A failure anywhere else leaves it to expire, because half-created resources may still name the machine. A lock held elsewhere is a skip; a whole pool held elsewhere fails as ServerReservedError, naming the holder and its MCE.

Every one of those is a SKIP, not a failed run. The multi-candidate draw exists so that one unusable server is a retry, and a reason handled outside this loop would quietly break that promise for part of the fleet — a pool of three would die on a STANDALONE machine at the front while two installable servers sat behind it.

When nothing survives, each reason is reported as its own group — they are different people’s problem, and merging them sends whoever reads it to the wrong place. The failure takes the specific error type when every candidate was rejected for the same reason, which is always the case for an explicitly named server, whose pool holds one.

4

create_bmc_secret → create_baremetal_host → create_nmstate_config

phases creating-secret / -baremetalhost / -nmstateconfig

In dependency order: the BareMetalHost references the Secret by name, so the Secret goes first. All three are idempotent — an existing resource is success, never an overwrite, so a BMC credential or a bond an operator corrected by hand survives a re-run.

POSTsecrets/<vendor>-cred-<server> · credentials from THIS worker’s Secret
POSTbaremetalhosts/<server> · customDeploy: start_assisted_install
POSTnmstateconfigs/nmstate-config-<server> · 802.3ad bond + tagged VLAN

Resource names are byte-identical to the operator’s, so a cluster already holding resources bmhgen created is converged rather than duplicated. The one difference: names are lowercased, because server-scan names carry an uppercase vendor serial (…-HP0001592) and Kubernetes rejects any uppercase letter in a resource name outright. bmhgen never met this — its names came from a CR a human had written.

5

find_agent_for_host, on a bounded timer

phase awaiting-agent

An Agent is the only observation that proves the install worked. It exists because the machine POSTed, booted the discovery ISO and reached assisted-service — so in one reading it proves the BMC accepted virtual media, the bond formed, the VLAN was the right one and DHCP answered. A 30-second durable timer, a 1-hour deadline: bare metal POSTs for longer than a VM takes to boot.

The Agent is matched by bond MAC, never by name. BMAC names an Agent after the host's own inventory UUID, and the live CRD's agent.spec carries approved, clusterDeploymentName, role and installation disk — no reference back to the BareMetalHost at all. Both bond members are searched, since the host registers with whichever NIC brought the ISO up.

This replaced a 10-minute Ironic-registration deadline, which was the wrong signal in both directions. It passed hosts that would never boot — one whose bond or VLAN is wrong registers perfectly and is then never heard from again — and it could not recognise a dead one: on an unreachable BMC Metal3 reports provisioning state registering with operationalStatus: OK and no errorType, observed unchanged for 14 hours on a live cluster. Nothing but the deadline itself ever distinguished a slow host from a dead one; an Agent distinguishes them by existing.

6

teardown_bmh_resources, then the next candidate

phase rolling-back

No Agent by the deadline is that candidate’s failure, not the run’s. Its NMStateConfig and BareMetalHost are removed and its install lock released (phase releasing-server) — which returns the machine to the inventory — and the loop goes back to step 2 with the next candidate. Only an exhausted pool fails the run, as AgentNeverAppearedError.

So steps 2–5 are a loop, not a pipeline. A server cannot be shown to be installable without creating its resources and watching what happens, so the draw is a list of things to try rather than to validate, and an hour-deep failure is a skip like any other. Leaving a rolled-back host in place would strand that machine invisibly: server-scan reports a server unclaimed until a cluster reports the node, so no other MCE would know it was taken.

The order is load-bearing, and every step of it came from a live cluster rather than from the docs:

  1. Detach first. baremetalhost.metal3.io/detached applied after deletionTimestamp is set does nothing — measured inert for four minutes. It only works before the delete.
  2. The NMStateConfig explicitly — it has no finalizer and no ownerReference, so nothing removes it implicitly.
  3. Delete the host, then wait, bounded.
  4. Drop metal3’s finalizer if it will not release. baremetalhost.metal3.io blocks while trying to deprovision through the BMC — and a rollback happens precisely because that BMC never answered, so this is the expected path here, not an exceptional one (stuck past four minutes, state deleting, no error ever reported). Only that one: BMAC’s bmac.agent-install.openshift.io/deprovision released inside one second, so taking it would rob a controller already doing its job.
  5. Confirm the Secret is gone. It carries an ownerReference to the BareMetalHost, so the garbage collector takes it — but only once the host genuinely goes, which is after the finalizer clears. Its name is read from the host’s own credentialsName, never rebuilt from the vendor.

Teardown refuses to report success while the host still stands (BmhTeardownError, retryable). The server must never be reported back to the inventory while a BareMetalHost still points at it — that is the one outcome worse than a slow rollback.

✓

Result

phase completed

The server that is now installable, its VLAN, the BMC address that was written, the bond MACs and the boot MAC — plus agent_name, the Agent that proved it, and attempts, how many candidates were installed and watched before one produced one. resources_changed is false for a re-run that found all three resources already present — the run still succeeds, and the flag says nothing was written this time. bmh_registered is implied rather than separately observed: an Agent cannot exist unless Ironic registered the host and drove it through a boot.

Everything between step 3 and the Agent is BMAC’s, not this workflow’s: it sees the infraenvs.agent-install.openshift.io label, finds the InfraEnv in the same namespace, and attaches its discovery ISO over virtual media. This workflow does not orchestrate any of that — it only waits for the one artefact that proves all of it happened.

The subtle part

Two link-up NICs on two distinct physical ports

Both halves of that sentence exist because of a specific way of getting it wrong.

Members come from interfaces[], never nic_macs

server-scan reduces Dell NPAR partitions to one entry per physical port in network.interfaces, but leaves identity.nic_macs whole on purpose. A 4-port partitioned card therefore reports 4 interfaces and 16 MACs.

bmhgen indexed that MAC list positionally, which can bond two partitions of one physical port: one wire, no redundancy — and it looks correct right up until that wire fails. Distinctness here is by port, not by interface, so a Dell controller/port/partition location collapses to controller/port and two partitions of one port share a key.

UP is required strictly, and that excludes whole vendors

Not “not DOWN” — UNKNOWN does not qualify. HPE OneView’s portMap carries no link state at all, so server-scan stores UNKNOWN unconditionally, and Intersight vNICs mostly report none either. Servers from those collectors therefore fail bond selection rather than being quietly passed over.

That is a decided, accepted trade. The failure names the provider and every observed link state, because the usual cause is that the collector cannot report link state rather than that the hardware is down — and from the workflow’s side those two look identical.

Why a health filter is not enough on its own

server-scan’s rollup is max(category severities), and UNKNOWN ranks below HEALTHY — so a category that was never read cannot lower it. A server whose NIC read failed has no network facts to fail a policy on, and comes out HEALTHY overall. Hence min_nic_macs=2 on the query and the structural rule above: the health tier says nothing bad was observed, and these say the machine is actually installable.

Where the VLAN comes from, and why it is step one

An MCE has one inventory network, found by cluster name

The VLAN a host is tagged onto belongs to the MCE this run targets — not to the machine chosen, and not to the caller, who could otherwise supply a VLAN contradicting the segment the cluster actually owns. So the lookup takes one input, the cluster name, and runs before a single candidate is considered.

Why it is resolved before the draw

Every other reason a candidate cannot be installed is a skip — the draw exists so that one unusable server is a retry. A missing inventory allocation is not one of them: it is the same for every machine in the pool, so no candidate could make it usable. Failing at the lookup names the real problem immediately instead of reporting it once the pool is exhausted.

Run as InventorySegmentNotFoundError — non-retryable, because an operator allocates the segment and retrying does not. Two INVENTORY segments for one MCE is AmbiguousInventorySegmentError: broken data a human resolves, since picking one would tag hosts onto a VLAN chosen by document order.

bmc_vendor picks the driver, not the network

Ironic still reaches an HP, a Dell or an Intersight-managed server over Redfish and a UCS blade over IPMI — that is the bmc.address scheme, built from what server-scan parsed. It no longer selects a segment.

It was briefly two networks

For a day the type was split by how a BMC is driven — INVENTORY_REDFISH for HP, Dell (iDRAC is Redfish underneath) and Intersight, INVENTORY_IPMI for a UCS blade — on the reasoning that Ironic reaches the two over different networks. That made the segment a property of the chosen machine, so the lookup moved inside candidate selection, was memoized per class, and a candidate whose class the MCE had not allocated was passed over like any other unusable one.

Reverted on both sides on 2026-09-27, by the team lead’s decision: two inventory scopes per MCE is a second thing to allocate, track and keep in step, and an MCE holding only one of them made “this cluster takes no servers driven that way” a state every consumer had to model. The Segments Manager’s Literal accepts plain INVENTORY again and rejects the two split values, so an allocation still carrying one must be re-typed.

How a hub workflow writes to a dozen clusters

One worker per MCE, routed by task queue — not by credentials

The brain runs on the hub. The resources belong on the MCE that owns the InfraEnv, which is a different API server at its own api.<mce>.<domain>.

mce_cluster is the whole mechanism

It names two things at once: the INVENTORY segment the VLAN is read from, and the activity queue every cluster write is dispatched to (server-lifecycle-activity-<mce_cluster>). A server-lifecycle-worker runs inside each MCE, polls only its own queue, and talks to its own API server as its own ServiceAccount.

So the VLAN’s cluster and the cluster written to are the same string and cannot disagree. The worker’s MCE_CLUSTER setting builds the same queue name, which is why it must match what callers send.

Routing beats holding kubeconfigs

No cross-cluster kubeconfig exists anywhere, and because workers dial out to Temporal to long-poll, the hub never needs inbound access to an MCE’s API server. The alternative — one hub worker holding a kubeconfig per MCE — concentrates admin-equivalent credentials for the whole fleet onto one pod.

A run whose MCE has no worker waits rather than acting. The cluster writes carry a 5-minute schedule-to-start timeout, so history shows repeated timeouts instead of a task sitting invisibly in a queue, and the status endpoint reports activity_queue — which says which MCE to go and look at.

Running it twice

A re-run converges — or refuses, but never lies

Temporal retries activities and operators re-POST things, so both have to be safe. “Safe” here means more than “does not crash”.

An existing resource is success once it MATCHES

An ALREADY EXISTS is not an error, and not an upsert either: the object is left exactly as it is. But reporting success for one that names a different BMC address, credential Secret, boot MAC, InfraEnv or VLAN would describe an installation that is not the one on the cluster — so those fields are read back and compared, and any disagreement is a non-retryable BmhConflictError naming the field. A human decides which is right.

Only identity fields are compared. Status, an operator’s added annotation, a hardware profile corrected by hand: all left alone deliberately. The MAC set is compared unordered — the bond is the same wiring whichever member became nic1.

The id serializes per POOL; the probe and the lock cover the rest

install-server-<infraEnv> keys on the candidate pool (^ocp-<infraEnv>), not on the machine — which is not known when the run starts — and not on the target. Two MCEs filling an InfraEnv of the same name draw from the same pool, so a second trigger while one is in flight gets 409 even when it names a different MCE.

That covers concurrent runs. The sequential case an id cannot cover — a second run minutes later, before any cluster has reported the node, so server-scan still calls the machine unclaimed — is what step 3’s already-installed probe is for. Without it, every create would answer “already exists” and the run would report success having added nothing. A run for a different MCE cannot see that BareMetalHost at all — that case is the install lock’s.

Installing several servers from one pool concurrently is now only a looser id

The run locks the machine it chose, so two concurrent runs can no longer end up on the same one. Keying the id on (InfraEnv, MCE) would let two MCEs fill one InfraEnv at once; that is a separate decision and has not been made — the id is still per pool.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async throughout: the POST hands back the workflow id at once and you poll it.

POST /workflows/server-lifecycle/install-server 202 · 409 if already running

The minimum body is three fields — the InfraEnv to fill, its MCE, and the namespace the InfraEnv lives in.

// request — fill the InfraEnv from the pool
{
  "infra_env":   "cisco-m6-bat-yam-64c-512gb",
  "mce_cluster": "ocp4-mce-bat-yam-01",
  "namespace":   "multicluster-engine"
}

// request — install one specific machine instead
{
  "infra_env":   "cisco-m6-bat-yam-64c-512gb",
  "mce_cluster": "ocp4-mce-bat-yam-01",
  "namespace":   "multicluster-engine",
  "server_name": "ocp-cisco-m6-bat-yam-64c-512gb-WZP12345"
}

// 202 response
{ "workflow_id": "install-server-cisco-m6-bat-yam-64c-512gb", "run_id": "…" }

The body forbids unknown fields. Chiefly that means a vlan_id is a 422 rather than a silently ignored value: the VLAN comes from the MCE’s segment, and a caller who sends one expects it to be used.

namespace must be the InfraEnv’s own namespace. BMAC looks for the InfraEnv beside the BareMetalHost, so a host created elsewhere is never given a discovery ISO.

GET /workflows/runs/{workflow_id} 200

Domain-agnostic: workflow ids are globally unique, so one route serves every domain. It addresses the progress query by name, so the response carries the live phase, the server chosen once there is one, and the activity queue this run dispatches to.

// 200 while running
{
  "status":   "RUNNING",
  "progress": {
    "phase":          "awaiting-agent",
    "server_name":    "ocp-cisco-m6-bat-yam-64c-512gb-WZP12345",
    "activity_queue": "server-lifecycle-activity-ocp4-mce-bat-yam-01"
  }
}

A phase that does not advance is diagnosable from this alone: it means nothing is polling activity_queue, so that MCE has no server-lifecycle-worker deployed or it cannot reach Temporal.

No healthy server matching the InfraEnv, no candidate with two link-up NICs on distinct ports, and a BareMetalHost that never registers are all FAILED runs on the status endpoint — not 4xx on the trigger. Everything the outcome depends on happens inside the run, as a retried activity.
