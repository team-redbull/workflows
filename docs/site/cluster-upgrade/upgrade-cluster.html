upgrade-cluster — what actually happens

One request takes one HyperShift HostedCluster from the release it runs to a target release. Every change is a commit to the cluster’s day1 file followed by a sync of that cluster’s one Argo CD Application on its hosting MCE. The run never patches the HostedCluster or a NodePool itself: Argo CD stays their only writer, so git and the cluster always agree.

The control plane moves one minor at a time, along a ladder of releases the team verified. The NodePools follow one at a time, at a person’s pace: between two of them the run may wait days or weeks, and that wait costs nothing. One approval comes before anything is committed. An upgrade that passes every gate makes no LLM call; the upgrade agent is asked only when a gate fails or a watch stalls, and even then a person decides what happens next.

Five rules the whole run follows

Git is intent, the cluster is truth

Every change goes through day1 git and Argo CD

A step edits one or two lines of the cluster’s day1 file — mastertag for the control plane, nodepool[<name>].workertag for a NodePool — runs the day1 validator on the result, pushes to main, then syncs Application/<cluster> in openshift-gitops on the MCE to exactly that commit.

A file someone else edited since planning is never committed over: the run stops and asks. A sync with anything out of sync besides what this step changes is refused: someone else’s change is pending.

Temporal owns the upgrade; the agent only advises

The workflow is the state machine: order, gates, timeouts, approvals and the audit log. The upgrade agent is one activity, called on a failed gate. It diagnoses, may fix a known-safe thing within a budget, and proposes the rest. Control always comes back to the same gate.

“Continue” and “skip” are never agent verdicts. Only a person moves a run past a gate that still fails.

Control plane through every minor

Never skips a minor; a must rung is never skipped. Workers may skip minors but never fall more than 2 behind.

Digests, pinned once

Tags stay in git. At planning every tag is resolved to a digest; right before each commit it is resolved again, and a tag that moved stops the run.

The happy path is boring

Every check is deterministic code. No LLM is called on an upgrade that passes every gate.

The lifecycle at a glance

Plan, check, one approval, then step by step

The run reads and checks everything before it asks for approval, and commits nothing before it. After approval it walks the plan’s steps in order. Each step is either a control-plane step or a worker step, and the run continues as new after each one.

reads and checks — nothing written writes — a day1 commit and an Argo CD sync, or the admin ack a person decides — no deadline
The path

A ladder in git, one minor per control-plane step

A disconnected fleet has no upgrade graph to ask, so the path comes from a rules file in day1: upgrade/ladder.yaml, read at the start of every run. Each rung is a release the team checked upgrades cleanly into the next minor; every consecutive pair is an edge in Red Hat’s public stable graphs.

The ladder today

4.15.41 → 4.16.55 → 4.17.58 → 4.18.56 → 4.19.53 → 4.20.44 → 4.21.40, every rung must: true. Last checked against the graph on 2026-10-31; the approver is shown that date.

There is no 4.22 rung: Red Hat publishes 4.21 → 4.22 edges only in candidate-4.22. A cluster already on 4.22 can take a 4.22 z-stream; nothing moves into 4.22 until a rung is added. The rungs are proposed; the team confirms them before production.

The rest of the rules file

  • maxWorkerSkew: 2 — the team’s rule. HyperShift allows 3, so 2 is the stricter.
  • release — the one full mirror and its layout: {imagePath}/openshift/release-images:{version}-x86_64, and the control-plane-operator image next to it.
  • adminAcks, apiUsageIgnoredUsers — admin acks.
  • Per MCE, upgrade/mces/<mce>.yaml: supportedHostedVersions (must match the MCE, check 1) and maxConcurrentControlPlanes.

A validator in day1, scripts/validate_upgrade_rules.py, keeps the file sane: rungs ascending, no minor missing, skew 1–3.

Control plane: the next step

  1. Already in the target’s minor: the target, after any must rung between the two.
  2. Else, if its own minor has a rung newer than it: that rung. A release is only known to upgrade into the next minor from the rung the ladder verified.
  3. Else: the next minor’s rung, or the target if that minor is the target’s. A minor with no rung is refused.

Workers: never more than 2 minors behind

  • Before a control-plane step that would leave a NodePool more than maxWorkerSkew minors behind, every lagging NodePool moves to the control plane’s current release.
  • A worker step always goes to the control plane’s release, never past it.
  • A rung marked dataPlane: required rolls the workers right after the control plane reaches it.
  • workers_to_target (default true) adds a final worker step.

Worked example: 4.16.27 → 4.21.40, skew 2

2control plane → 4.17.58ladder
3control plane → 4.18.56ladder; workers now 2 behind, still allowed

Steps 4, 7 and 9 move each NodePool two minors in one InPlace roll. That was tried on a sandbox HostedCluster (4.17.58 → 4.19.53): each node was drained and rebooted once, one node at a time. Should it ever misbehave, maxWorkerSkew: 1 rolls the workers every minor instead.

Choosing the target

target_version names a release, which must be in the mirror; it need not be a rung, but it can only be the last step. target_minor ("4.21") lets the run pick: the newest release of that minor that is both in the mirror and a rung.

Refused up front, nothing changed

A downgrade; a NodePool newer than its control plane (patch included); a NodePool already beyond the skew; a version spelled other than X.Y.Z or X.Y.Z-x86_64; a repeated rung. Each fails the run at planning.

Digests: pinned at planning, re-checked before every commit

Planning resolves every release in the plan to two digests — the release payload and the HyperShift control-plane-operator image — and checks the payload images exist. Those go into the plan the approver sees. Right before each commit the step’s tags are resolved again; anything else than the approved digests stops the step before it commits: “the mirror changed under the run”, and a person decides. Tags stay in the chart; the chart needs no change.

Step by step

What the run does

Each card carries its phase, read live off the running workflow through its progress query. Whenever a person is needed, progress.waiting_for says what to do, in words.

1

planning

phase planning

Reads only. First the cluster’s day1 file (hub): the folder it sits in, sites/<site>/mces/<mce>/, is the MCE the run works on from then on. Then the rules file (hub), the MCE’s hypershift/supported-versions and the HostedCluster with its NodePools (MCE). It derives the profile — zoned when NodePools carry topology.kubernetes.io/zone, else generic, unless the file’s upgrade.profile says otherwise — and the NodePool order. Then it resolves the path, pins every release to its digests and checks day2 has a layer for every version.

HUBread_day1_cluster · read_upgrade_rules · pin_release_digests · check_day2_layers · list_release_tags for a target_minor
MCEread_mce_state · read_hosted_cluster

Any failed check (1–4, git matching the cluster, auto-approve allowed) fails the run, listing every failure at once. A cluster already at the target completes here, with nothing done.

2

pre-flight

phase preflight

Checks 5–11 of the pre-flight table, in parallel reads on the MCE. A control plane still settling is re-checked every minute for up to 30 minutes first.

Before approval only the IDMS check (11) fails the run. Every other failure, here and after approval, waits for a person (needs-human): a PDB’s owner can fix theirs and retry.

3

the one approval

phase awaiting-approval

waiting_for shows the plan, step by step, the date the ladder was last checked against the graph, and the admin acks the plan will meet. approve starts the steps. abort here ends the run CANCELLED: nothing was committed.

This is also the dry run: start, read the plan, abort. With auto_approve, only allowed when the cluster file says upgrade.wave 0 or 1 (lab, canary), the run approves itself.

4

a control-plane step

phases preflight → admin-acks → waiting-for-slot → control-plane-step → awaiting-day2-confirm

Pre-flight 5–10 again. Before a minor step, the admin acks. Then a free slot on the MCE: the child workflow’s id is upgrade-control-plane-<mce>_<n>, n up to maxConcurrentControlPlanes, so a taken id means a busy slot. All busy: look again every 2 minutes. The child then:

  1. checking-mirror — re-resolves the tags; a changed digest ends the step before any commit.
  2. committing — mastertag: <v>-x86_64, with every NodePool’s workertag pinned explicitly so no worker moves with it; compare-and-set on the file’s blob id.
  3. syncing — Application/<cluster> to that commit, refused if anything but the HostedCluster is out of sync (5 min).
  4. watching — one heartbeating activity, polling every 30 s, until status.version.history[0] is the version and Completed, ClusterVersionSucceeding and ValidReleaseInfo True, not Progressing, and every ClusterOperator at the version. 20 min with no change is a stall; 3 h is the deadline. (The design proposes a 45-minute stall window plus the CVO’s own “wait has exceeded” signals, because the CVO itself gives slow operators 30 to 40 minutes; still open.)
  5. diagnosing — a stall or the deadline goes to the agent. After a stall it may clear the gate and the watch runs once more.
  6. needs-human — the child tells the parent and waits, still holding its slot: the HostedCluster is mid-upgrade. A person’s retry watches again.
HUBpin_release_digests · commit_day1_change · control-plane
MCEsync_argo_application · watch_control_plane

Then day2: the cluster’s day2 Applications (day2.gitops/cluster=<cluster>) now render for the new version and are OutOfSync. The day2 team syncs them; the run waits for confirm-day2, after every control-plane step, intermediate ones too. It never syncs day2 itself.

The child is started with ParentClosePolicy.ABANDON: a parent terminated mid-step leaves the slot taken until the step ends. The parent drives it by signals (stop, hold, retry), never by cancellation. An early end before the sync — the mirror changed, someone edited the file, the validator or Argo CD refused — is a result, frees the slot, and becomes needs-human in the parent.

5

a worker step, one NodePool at a time

phases awaiting-continue → preflight → nodepool-roll → nodepool-gate

The order is nodepool_order from the request, else the file’s upgrade.nodePoolOrder, else by zone (a, b, c) when every NodePool has one, else file order. For each NodePool:

  1. Wait (manual mode, the default) for continue, which may name the next NodePool. This can take a week. Auto mode goes on after the previous gate’s soak.
  2. Pre-flight 5–10, scoped to this NodePool, and the digest re-checked.
  3. Commit nodepool[<name>].workertag and sync, refused if anything but NodePool/<name> is out of sync. A sync refused after the commit landed is retried alone.
  4. Watch until NodePool.status.version is the version, UpdatingVersion False and AllNodesHealthy True (and SupportedVersionSkew True where the operator sets it). No node finishing for 30 min is a stall; a drain the eviction API refuses for 10 min is handed over early (below). Deadline: ceil(replicas / maxUnavailable) × 60 min, maxUnavailable 0 counting as 1.
  5. Gate: all the NodePool’s nodes Ready and schedulable; for a zoned cluster, or one that declares readiness checks, also PDBs back to disruptionsAllowed ≥ 1, StatefulSets ready, and the cluster’s own checks (PromQL or HTTP). All of it must hold for the soak — 30 min zoned, 0 generic, or upgrade.soakMinutes. Deadline: the soak plus 60 min. For now a declared check fails as “not run”, so a cluster that declares one waits for a person at every gate: how the limb reaches the hosted Prometheus (it needs a token there) and a customer’s route from the MCE is still open (design O22).
HUBpin_release_digests · commit_day1_change · nodepool
MCEsync_argo_application · watch_nodepool · watch_nodepool_gate

A failed watch or gate goes to the agent, then the same watch or gate once more, else needs-human. “Skip to the next NodePool” is never the agent’s call. Per-node preparation stays in the existing node finalizer framework (CAPI pre-drain hooks).

6

post-flight

phase postflight → done

Drops the top-level workertag the run may have added (per-NodePool lines stay, now equal to mastertag), syncs with nothing allowed out of sync, and reads the HostedCluster: the control plane and every NodePool at the target — or, with workers_to_target: false, where the plan left them. Anything else is needs-human.

Waiting is free

Every human wait is a wait_condition on a flag an Update sets: no timer, no polling, so a week between two NodePools adds nothing to history. The run continues as new after every control-plane step and every NodePool, carrying the plan, pinned digests, profile, order and limits it was approved with — whatever the rules file says by then.

Abort and pause, checked before every act

Right before each commit, sync, admin ack, child start and agent call, as well as in every wait and watch. Pause holds the run before its next commit; what is already rolling finishes. Abort before approval cancels. After it, the run stops a running child, commits pausedUntil for the HostedCluster and every NodePool, syncs, and ends ABORTED.

If the validator or Argo CD refuses the abort, a person is asked and the run retries; it never ends half-aborted. There is no downgrade, and no commit is ever reverted.

Deterministic, no LLM

The checks, and what each failure does

Checks 1–4 run at planning. Checks 5–11 run before approval; 5–10 run again before every control-plane step and every NodePool roll. Before approval a Failed check fails the run; after approval no check fails it — it waits for a person.

Before a control-plane minor step

Admin acks: given by the run, unless a client still uses the API

Some releases make an administrator acknowledge an API removal before the control plane may leave their minor. From 4.19.15, a 4.19 cluster asks for ack-4.19-admissionregistration-v1beta1-api-removals-in-4.20: four admissionregistration.k8s.io/v1beta1 resources — Mutating and Validating webhook configurations, ValidatingAdmissionPolicies and their bindings — are gone in 4.20. Until the ack is given, the hosted CVO says Upgradeable=False, AdminAckRequired, and HyperShift refuses a minor change of the HostedCluster.

What the run reads

Through the hosted cluster’s admin kubeconfig, right before the step’s commit (and only when the step changes the minor — a z-stream needs no ack):

  • openshift-config-managed/admin-gates and openshift-config/admin-acks;
  • the CVO’s AdminAckRequired message;
  • for each API the rules list for the gate, its APIRequestCount over the last 24 hours: who called it, with which user agent, which verbs, how often.

A gate is pending, by the CVO’s own rule, while its ack-4.<minor>- matches the control plane’s minor and admin-acks does not hold exactly "true" for it.

What it decides, per pending gate

the gatethe run
listed in the rules, no calleracks it itself, logged as given by workflow
listed, with callersawaiting-admin-ack, listing each caller — then approve-admin-ack (a reason is required) or retry
not listedneeds-human: a person checks the removal, acks by hand or adds the gate to the rules, and retries

Callers in apiUsageIgnoredUsers do not count: the garbage collector, the namespace controller, kube-controller-manager and cluster-policy-controller walk every API.

The write, and the wait after it

One merge patch of data.<gate>: "true" into the hosted openshift-config/admin-acks, read back. It is the run’s only write inside a hosted cluster, and it is never taken back: it allows a minor step, it does not start one. Then the run waits for the CVO to stop saying AdminAckRequired — polled every minute, for up to 10 minutes, then needs-human. A commit before that would sit refused.

Strict on purpose

One counted request is enough to ask a person, because the ack is what lets the removal go ahead. The count covers 24 hours, so a client that just moved to the v1 API keeps showing for up to a day: the person may approve sooner, knowing that, or retry later.

APIRequestCount cannot see idle workloads or tools outside the cluster, so listing a gate in the rules is a reviewed team decision. The approver sees, at approval, every listed ack the plan will meet.

Only when a gate fails

The upgrade agent: diagnoses, proposes, never decides

One activity, invoke_upgrade_agent, on upgrade-agent-activity-<mce>, called only on a failed gate or a stalled watch. It runs on kagent inside the MCE (GLM 5.3 in production) and holds no credentials: its tools run in a separate upgrade-tools server under the agent’s own identity.

Typed in, typed out

In (AgentRequest): the run, the cluster and MCE, the profile, the step and NodePool, which gate failed and its failing checks, an evidence bundle collected on the MCE (HostedCluster and NodePool conditions, ClusterOperators, events, the Argo app, data-plane health; capped at 512 KB, no Secrets), and a budget: 15 minutes, 40 tool calls, 2 tier-1 actions.

Out (AgentVerdict): a diagnosis with its confidence, every tool call it made, the actions it proposes, and one verdict: retry_gate, needs_human or abort_recommended.

A malformed reply is needs_human. An agent that cannot be reached in two attempts is answered as needs_human too; the run never fails for it. Every answered call is written to Brain as an incident.

What happens with the verdict

  • retry_gate with nothing proposed: the same stalled watch, or the same gate, runs once more. A second failure is needs-human.
  • Anything proposed: needs-human, the proposals listed in progress.pending_actions. A person approves or rejects each; an approved one runs with the workflow’s identity; then retry.
  • abort_recommended: needs-human, with the recommendation shown. Only a person aborts.
  • A watch that hit its deadline always ends at needs-human.

What the agent knows (Brain, runbooks, incidents) and what it may do (the tool server and the admission policy) are separate: a Brain page can never widen the allowlist. Graduating a fix to tier 1 in more waves is a reviewed change to the code and the policy.

The one known remediation so far: a drain stuck on an OpenShift PDB

Seen live on the sandbox: a NodePool roll waited 35 minutes on openshift-console/downloads. Both of that PDB’s pods were crash-looping on the starved node being drained, so the PDB could never allow a disruption, and the eviction API refused every try: “Cannot evict pod as it would violate the pod’s disruption budget”. nodeDrainTimeout is 0 by default, so it waits for ever. Deleting the two pods unblocked it.

  • Handed over early. The NodePool watch reports a stall once a node has waited 10 minutes on a refused eviction, instead of the 30-minute stall window. Its evidence names the node, the PDB and the PDB’s pods with their state.
  • The fix: delete the not-Ready pods behind that PDB — deleting a pod bypasses the eviction API, its controller recreates it elsewhere and the drain goes on — then retry_gate. Never the PDB itself, never a Ready pod, never outside openshift-*.
  • Who does it: the agent itself in waves 0–1; elsewhere it proposes the deletes and a person approves them, until the evals graduate it.
  • A customer’s PDB in the same spot is never touched: needs_human, naming the PDB, for its owner.

How you start it, steer it and watch it

Served by workflows-orchestrator-api once the router is mounted. Every route lives under /workflows/cluster-upgrade/upgrade-cluster. Decisions are Temporal Updates, answered at once: the run itself says whether it was waiting for that decision.

POST /workflows/cluster-upgrade/upgrade-cluster 202 · 409 if this cluster already has a run · 422 on a bad body

Which cluster, to what. Exactly one of target_version (X.Y.Z or X.Y.Z-x86_64) and target_minor. What it never does

  • No patch of a HostedCluster, NodePool or IDMS — Argo CD applies what day1 says.
  • No commit over a person’s edit, and no sync over someone else’s pending change.
  • No skipped minor on the control plane, no skipped must rung, no worker more than two minors behind.
  • No tag after planning — every commit is checked against the approved digests.
  • No force-upgrade-to, no downgrade, no reverted commit.
  • No day2 sync — the day2 team does that and confirms.
  • No ack for a gate the rules file does not list.
  • No LLM call on an upgrade that passes every gate.
