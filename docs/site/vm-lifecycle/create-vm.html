create-vm — what actually happens

One request creates one VirtualMachine for a KubeVirt InfraEnv, on the KubeVirt cluster of the InfraEnv’s zone where it packs best under the headroom buffer. The VM is created Halted, with a fixed MAC and the label kubevirt-redfish exposes it by, so server-scan lists it as a server named ocp-<infraenv>-<suffix> and add-server-to-mce installs it through Ironic like any physical machine.

A bare-metal InfraEnv has servers to draw. A KubeVirt one — named <conf>[-<letter>]-zone-<zone>-<cpu>, say x201-zone-a-8 — has nothing until a VM of <cpu> vCPUs and <cpu> × 8 GiB exists. This run is that step. It never starts the VM (Ironic does, later), never creates a namespace, and writes nothing on the MCE.

TriggerPOST /workflows/vm-lifecycle/create-vm
Workflow idcreate-vm-<mce_cluster>_<infra_env>_<slot>
Workflow queuecreate-vm-workflow
Activity queuevm-lifecycle-activity (one hub limb, every zone)

The limb holds no Kubernetes credential. It reaches each KubeVirt cluster through two small agents the platform deploys there behind Routes — kv-capacity (read-only facts) and kv-vm-api (the idempotent VM create, read and delete) — and reads the zone’s cluster list from the day1 repo. Until the agents are up on a zone’s clusters, a run there waits (RUNNING, every cluster no-agent).

Read this first

Names carry everything: site, zone, size

Nothing is looked up to decide what to create; the two names say it, and the API derives it once (the run carries the derived values and never re-derives them).

What the names say

  • MCE ocp4-<env>-mce-<site>-<letter> → the site (ocp4-prod-mce-bat-yam-a → bat-yam).
  • InfraEnv <conf>[-<letter>]-zone-<zone>-<cpu> → the zone and the VM’s size (x201-zone-a-8 → zone a, 8 vCPU, 64 GiB). A -metal InfraEnv is refused: it takes servers, not VMs.
  • (site, zone) → the seed cluster ocp4-seed-<site>-<zone>, whose day1 folder lists the zone’s KubeVirt clusters, ocp4-kubevirt-<site>-<zone>….
  • VM ocp-<infraenv>-<6 hex>, MAC <VM_MAC_PREFIX>:xx:xx:xx from the same six hex digits — name and MAC agree by construction.

What it never does

  • It never starts the VM: it is created runStrategy: Halted, and kubevirt-redfish powers it on when Ironic asks.
  • It never moves a create to another cluster: the PUT on the chosen cluster is out-waited. Halted, the scheduler is not consulted, and a move after an ambiguous failure could leave two VMs.
  • It never leaves a VM whose root disk did not bind: that VM is deleted again before the run fails. A re-run draws a new suffix and could never resume the old one.
  • It never creates a namespace and never touches the MCE.

The agents’ URLs and tokens are limb settings; neither enters history.

Four phases, a fifth only on failure

What the run does

Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run it currently is. A run that has not started its first step reports pending.

1

list_kv_clusters

phase listing-kv-clusters

A fresh clone of the day1 repo at main, and every file of the seed folder sites/<site>/mces/ocp4-seed-<site>-<zone>/hostedClusters/ is one candidate: its day1 name, its chart clusterName (the file’s own, else the name minus ocp4-) and its HostedCluster. A missing folder is an empty list.

gitclone main · DAY1_REPO_URL, read only, one clone per attempt

No candidate at all fails the run with NoKvClusterError naming the folder and the prefix looked for. A file in the folder not named ocp4-kubevirt-<site>-<zone>… is ignored. Nothing filters on day1’s platform: kubevirt — that key means a cluster whose nodes are VMs.

2

rank_kv_clusters

phase ranking-kv-clusters

Every candidate’s kv-capacity agent is read at once (10 s each, 45 s for the zone): its schedulable nodes with their allocatable and the requests of their Pending|Running pods (the kube-scheduler’s own view), our Halted, not-yet-started VMs as reservations, and every VM’s MAC. Then the rule of docs/design/kubevirt-vm-placement.md:

  1. Fit is per node: one schedulable node must have the headroom for the launcher pod — CPU cpu × 15 / 16 cores, at least one (what the agents’ vm.yaml.j2 requests), memory the guest’s plus 1 GiB.
  2. The buffer is per cluster: the fill after placing — active requests + Halted reservations + this VM, over the schedulable allocatable — stays at or under 1 − HEADROOM_BUFFER_PERCENT on CPU and on memory.
  3. Best-fit among the survivors: the cluster fullest after on its dominant resource, ties by name. Never first-fit.
GET/v1/capacity · on every candidate’s kv-capacity Route, bearer KV_CAPACITY_TOKEN

A cluster that cannot be read is a row with a reason, never an exception: unreachable, no-agent (nothing behind the Route yet), refused-token, malformed. Only when no cluster could be read is the step retried (KvCapacityUnavailableError), and only when every reachable one refused the token does the run fail (KvAgentAuthError). Nothing fitting fails with NoKvClusterFitsError, the table summarised per reason. The whole ranked table is in progress and in the result, so you can see why B was chosen over A.

3

create_vm_on_cluster

phase creating-vm

The run draws six hex digits from its own random (replay-safe). A draw whose MAC tail is already any VM’s in the zone is dropped without a call. Then ONE PUT on the chosen cluster’s kv-vm-api: name ocp-<infraenv>-<suffix>, the namespace, the size, the MAC. The agent renders the platform’s vm.yaml (storage class, network and node selector are its own per-cluster values) and creates the VM Halted, labelled redfish-enabled: "true".

PUT/v1/vms/<name> · {"namespace", "cpu", "memory_gib", "mac", "labels"} · 201 created, 200 same identity already there

Idempotent by name and identity: a retry after a lost answer gets 200 for its own VM (created: false in the result — a retry artifact, never something a re-run relies on). A 409 means the name holds another identity, born between the capacity read and the PUT: the run redraws. At most 3 draws (a taken MAC and a 409 each spend one), then VmNameExhaustedError. The create is out-waited on this cluster — an agent outage is retried without bound, never answered by moving to another cluster.

4

await_vm_ready

phase awaiting-root-disk

ONE heartbeating activity polls the VM every 8 s until its root disk’s DataVolume is Succeeded with its PVC bound and KubeVirt has admitted the VM. Its clock lives in the heartbeat, so a retry on another worker pod resumes it rather than starting over.

GET/v1/vms/<name>?namespace= · every 8 s, heartbeat each poll

Bounded at 10 minutes on the activity’s own clock. The VM vanishing meanwhile fails the run with VmDisappearedError (someone else deleted it; creating it again would be a second VM under a name the run no longer owns).

5

delete_vm_on_cluster

phase removing-vm · only on the deadline

No bound root disk after 10 minutes: the run deletes its own VM and its DataVolume — by name and by the MAC it gave it, so the agent deletes nothing else — then fails with VmRootDiskNotBoundError quoting the last phase seen.

DELETE/v1/vms/<name>?namespace=&mac= · 204 deleted, 404 already gone (both success), 409 not this MAC

Why delete rather than leave it: a re-run of the slot is a new execution with a new suffix. It cannot converge on the orphan; it would add one VM per attempt. The usual cause is a WaitForFirstConsumer storage class, which never binds a Halted VM’s disk: the VM’s storage class must bind Immediately. A 409 on the delete means someone replaced the VM under that name; the run leaves it and fails with VmIdentityConflictError.

✓

Result

phase completed

The VM’s vm_name and mac, its namespace and size, the kv_cluster it is on (day1 name, chart clusterName, HostedCluster, the agent host used), the full placement table, redraws, root_disk_phase, and the request echoed back (infra_env, mce_cluster, site, zone). The VM is Halted, waiting for server-scan to list it and add-server-to-mce to install it.

When it stops

Classified errors fail the run; everything else is out-waited

Every error below is a FAILED run on the status endpoint, never a 4xx on the trigger, and fails after one attempt — a retry would get the same answer. Only one of them leaves the run having written anything, and that one undoes it first.

Raised by the workflow itself

errorwhen
NoKvClusterErrorlisting-kv-clusters: the seed folder lists no ocp4-kubevirt-<site>-<zone>… cluster. The message names the folder and the prefix. Nothing was read from or written to any cluster.
NoKvClusterFitsErrorranking-kv-clusters: no cluster takes the VM under the buffer. The message groups the clusters by reason (no node with the headroom, past the buffer, unreachable, no agent, token refused, malformed). Nothing was written.
VmNameExhaustedErrorcreating-vm: three draws, each a MAC already in the zone or a 409. Nothing of this run survives on the cluster; run it again for a fresh draw.
VmRootDiskNotBoundErrorremoving-vm: the root disk did not bind within 10 min; the VM was deleted again. Check the storage class binds Immediately, then the DataVolume and the CDI log on that cluster.

Raised by an activity, non-retryable

errorwhen
KvAgentAuthErrorEvery reachable cluster’s kv-capacity refused KV_CAPACITY_TOKEN, or the chosen cluster’s kv-vm-api refused KV_VM_API_TOKEN (401/403). Rotate the Secret with the agents.
VmNamespaceNotFoundErrorThe VM’s namespace does not exist on the chosen cluster (404 on the PUT). The platform creates chassis namespaces; this run never does.
VmRequestRejectedErrorkv-vm-api refused the request (422): a shape its template cannot render, or one the cluster’s API server / an admission webhook refused. The agent’s (or the cluster’s) own wording is carried.
VmDisappearedErrorawaiting-root-disk: the VM is gone before its disk bound (404). Something else deleted it.
VmIdentityConflictErrorOn the delete only: the VM under that name no longer carries this run’s MAC (409) — replaced by someone else, so the run leaves it. On the create a 409 is a redraw, not a failure.

Everything else is retried without bound, backing off from 1 s to at most 1 min between attempts: the day1 repo unreachable or without main (ValuesRepoGitError, ValuesBranchNotFoundError), no cluster of the zone readable (KvCapacityUnavailableError — typically the agents not deployed yet), the chosen cluster’s kv-vm-api unreachable or answering 5xx (KvVmApiUnavailableError). The run stays RUNNING in its phase and the failure shows on the activity in the Temporal UI.

The two reads (steps 1–2) carry a 5-minute schedule-to-start timeout: with no vm-lifecycle-worker polling, they fail the run saying so, before anything exists. The create, the wait and the delete carry none on purpose — Temporal never retries that timeout, and a limb pod away for five minutes after the PUT must not fail the run, or its rollback, and leave the VM behind. Those wait for a worker, visible as a pending activity.

Running it twice

A re-run is a new VM; a retry is the same one

Temporal retries activities and operators re-POST things. The two are different here, on purpose.

Inside one run: idempotent by identity

The PUT carries the VM’s whole identity (namespace, size, MAC, labels). Retried after a lost answer, it finds its own VM and gets 200: created: false in the result, nothing duplicated. The delete carries the MAC, so a retried delete after a 204 gets 404 — success. The ready wait resumes its clock from its last heartbeat.

Across runs: a slot, and a fresh draw

The id is create-vm-<mce>_<infra_env>_<slot>. Asking again while a run is in flight fills the next free slot — it is asking for one more VM, so it is never a 409 (only when all 100 slots are busy). A finished slot is free again. Every run draws its own suffix, so a re-run never resumes an earlier VM — which is why a failed run leaves nothing behind: there would be no way back to it.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async: the POST hands back the workflow id at once and you poll it. The API has no auth of its own — anyone who can reach it can start a run.

POST /workflows/vm-lifecycle/create-vm 202 · 409 only when all 100 slots are busy · 502 when Temporal refuses

Two fields are required: the MCE and the InfraEnv. namespace defaults to inventory; count asks for several VMs. mce_cluster is accepted with or without its ocp4- prefix and must be named ocp4-<env>-mce-<site>-<letter>; infra_env must be a KubeVirt InfraEnv of the convention.

// request — three VMs, in another chassis namespace

  "mce_cluster": "ocp4-prod-mce-bat-yam-a",
  "infra_env":   "x201-zone-a-8",
  "namespace":   "redfish-vms",

}

{

GET /workflows/runs/{workflow_id} 200

The agents on each KubeVirt cluster

Two services per cluster, their own repo (kv-agents), deployed by the platform behind Routes, one fleet bearer token each; the contract is docs/design/kv-agents-api.md and the models’ vendored copy is pinned by tests/test_kv_agents_contract.py.

agentcallanswersRBAC it holds
kv-capacityGET /v1/capacitynodes (schedulable, allocatable, Pending|Running requests), Halted launcher-less VMs of ours with their would-be requests, every VM’s MACget/list nodes, pods, virtualmachines, virtualmachineinstances
kv-vm-apiPUT /v1/vms/{name}201 created · 200 same identity · 409 another identity · 404 no namespace · 422 · 401create/get/delete virtualmachines, get/delete datavolumes, get namespaces
GET /v1/vms/{name}?namespace=the VM’s MAC, size, runStrategy, admitted, root disk phase/bound · 404
DELETE /v1/vms/{name}?namespace=&mac=204 deleted (VM + DataVolume) · 404 already gone · 409 not that MAC

Where it runs

queuepolled byused for
create-vm-workflowthe brain, workflows-orchestratorthe workflow itself
vm-lifecycle-activityvm-lifecycle-worker, one release on the huball five activities, for every zone

Timeouts: the list 180 s (a git clone), the rank 60 s, the create and the delete 90 s, the ready wait 12 min with a 2 min heartbeat timeout; retries unbounded with the classes above as the only stops.

Proven end to end on 2026-11-05 against a real OpenShift Virtualization cluster (nine simulated KubeVirt clusters, the brain and the limb from source): the create, best-fit on real numbers, a Halted reservation tipping the next create, every skip reason, the three placement failures, the wrong-token failure and the 10 min rollback — docs/lab/create-vm/ in the repo rebuilds it. Two things it found: the root disk is ReadWriteMany + Filesystem, which ceph-rbd refuses (the cluster’s storage class must allow that pair, or every run rolls back); and count runs rank before any of them creates, so they all land on the same cluster — reservations protect sequential creates only. The same scenarios run on every pytest against a simulated fleet (tests/test_create_vm_e2e.py).
