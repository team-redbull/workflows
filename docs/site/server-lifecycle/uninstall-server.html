uninstall-server — what actually happens

One request takes one server all the way out of an MCE, whatever state its Agent is in. A hosted cluster’s node first leaves the hosted cluster: its CAPI Machine is deleted, CAPI drains the Node, the Agent provider releases the Agent and the host reboots back into discovery. Then — for every server, a node or not — it leaves the MCE’s inventory through remove-server, run as an awaited child.

The inventory half is never reimplemented here: remove-server’s power-off, BareMetalHost, NMStateConfig, Agent and PXE cleanup run exactly as they do on its own route, which keeps working alone.

Read this before you run it

On its own it replaces a node — it does not shrink the cluster

NodePool replicas are not this workflow’s business. It deletes the Machine behind the server and nothing else on the NodePool, so what happens next depends on who lowered the replicas — or didn’t.

Standalone = REPLACE

Run on its own, the NodePool still wants the same number of nodes. Its MachineSet creates a new Machine the moment the old one goes, and the Agent provider binds another Agent from the InfraEnv to it. The hosted cluster ends the same size, on a different server; this one leaves the MCE.

Use it to swap a broken or reassigned machine out of a hosted cluster. If the InfraEnv has no other free Agent, the new Machine waits for one — that is the NodePool’s problem, not this run’s.

Driven by a scale-down = SHRINK

A caller that lowers the replicas first shrinks the cluster. That is the job of the future scale-down-nodepool workflow: it owns the NodePool’s annotation and replicas, then triggers uninstall-server once per server.

Such a run finds the Machine already deleting, so its one write — the Machine delete — is a no-op recorded in skipped, and it only waits for CAPI and removes the host from the inventory.

How the path is chosen

By the binding it observes — never by a state string

The run inspects the host once and picks one of two shapes. A third case — nothing of the server on the MCE — is not a path of its own: the child finds nothing and completes with found: false.

a hosted cluster’s nodean inventory host
what inspection seesan Agent bound (spec.clusterDeploymentName) and an AgentMachine behind it — or an AgentMachine whose status.agentRef still names the Agent (a Machine deletion already under way: the run resumes it)no Agent bound, no AgentMachine naming one — or no Agent at all
hosted-cluster halfruns: delete the Machine, wait for CAPI and the provider, verify the AgentMachine, the Node and the Agentskipped, and named in skipped
inventory halfremove-server, awaitedremove-server, awaited
resulthosted: true, the hosted cluster, Machine, AgentMachine and Nodehosted: false

An Agent bound to a ClusterDeployment with no AgentMachine behind it — an early-bound ACM/ZTP cluster, or a binding left behind by a cluster that is gone — has no Machine to delete, and is refused (NotHostedClusterNodeError). That case is left for a later version.

Six steps, in order

What the run does

Each card carries a phase, read live off the running workflow through its progress query — with a sub_phase while it waits for the Machine, and the Agent’s last agent_state.

1

lookup_server_membership

phase checking-inventory

server-scan is the authority on where a server is. The run reads its record by exact name: a search narrows, the server’s own document confirms the name (case-insensitively) and carries openshift.{lifecycle_state, cluster_name, mce_name, contested_with}, maintenance and the srv_… id the lock is keyed on. Never /servers/available, which hides exactly the claimed and reserved machines an uninstall is about.

GET/servers?search=<name>
GET/servers/{id} · per exact-name hit

Refused only on a contradiction, with nothing written: an unknown name (no lock could be taken on it), a record contested_with another claim, or one placing the server on another MCE (compared with or without ocp4-). AVAILABLE is accepted — it is what an unbound host often reads as between membership runs. Maintenance is logged, not refused.

2

inspect_bound_host

phase inspecting

Reads only. The BareMetalHost <server>; the host’s Agents, matched by BMAC’s bmh label or by any MAC (the BMH’s, the NMStateConfig’s, server-scan’s); for each, its binding, status.debugInfo.state and the AgentMachine behind it. For the one hosted Agent: the owning Machine (its deletionTimestamp, nodeRef, pending delete hooks and deletion conditions) and the HostedCluster. The Node name is captured now: the Machine is about to go.

LISTagentmachines.capi-provider.agent-install.openshift.io · all namespaces
GETmachines.cluster.x-k8s.io · the AgentMachine’s owner
LISThostedclusters.hypershift.openshift.io · all namespaces

Refused here, still with nothing written: two bound Agents (MultipleBoundAgentsError); a binding with no AgentMachine, or an AgentMachine in no HostedCluster’s control-plane namespace (NotHostedClusterNodeError); server-scan naming another cluster than the Agent’s, or reading INSTALLED_TO_INVENTORY while the Agent is bound (ClusterMembershipMismatchError). An INSTALLED record that has not caught up with an unbinding is not a contradiction — an unbound Agent names no cluster, and that is a re-run’s normal view.

3

reserve_server

phase reserving-server

server-scan’s install lock, holder uninstall-server and this run’s workflow id, taken always and before the first write. Its TTL covers the whole hosted-cluster half — the 20-minute drain, the 1-hour reboot, both 5-minute verifications and a margin: 1 h 40 min. Why an uninstall needs a lock at all is below.

POST/servers/{id}/reservation

A lock another run holds fails the run here (ServerReservedError), nothing changed. The common case is install-server’s day-long hold after it installed the machine: release that hold in server-scan, then re-run.

4

the hosted-cluster half

hosted nodes only

deleting-machine — ensure_machine_deleting, the run’s one write on the MCE: a Machine already carrying a deletionTimestamp (a scale-down, an operator, an earlier run) or already gone is left alone and named in skipped; otherwise one DELETE.

awaiting-machine-deletion — every 30 s, until the Machine is gone and the Agent is known-unbound, in two sub-phases with their own clocks, each started when this run first sees it:

  • draining while the Agent is still bound — pre-drain hooks, the Node drain, volume detach. 20 minutes, else MachineDrainTimeoutError.
  • unbinding once the provider has released the Agent — the host reboots into the discovery image, on bare metal the same POST-and-boot install-server allows an hour for. 1 hour, else AgentUnbindTimeoutError (or MachineDeletionTimeoutError if the Agent is free but the Machine never went).

verifying-agentmachine — the AgentMachine is gone (5 min, polled every 10 s). verifying-node — the hosted cluster has no Node of the captured name, read through its admin kubeconfig; skipped when the Machine never had a nodeRef (CAPI skips its drain for the same reason). verifying-agent — unbound, no agentMachineRef label, known-unbound, approved, its BareMetalHost present and not in error (5 min): what remove-server needs to power it off and take it.

DELETEmachines.cluster.x-k8s.io/<machine> · unless already deleting
GET/api/v1/nodes/<node> · on the hosted cluster

Every failure after the delete leaves things as they are — a Machine delete cannot be undone — and a re-run of the same id resumes: it finds the Machine deleting and skips the write.

5

reserve_server, again

phase holding-server

The lock extended to 24 hours — the ceiling server-scan accepts, and install-server’s precedent — before the child starts, so the hold covers the inventory half too and outlasts the membership jobs that will report the machine free.

Refused now (the lock lapsed and another run took the machine), the run logs it, reports reservation_expires_at: null and still removes the host: it must not stay in this InfraEnv either way.

6

remove-server, as a child

phase removing-from-inventory

execute_child_workflow on remove-server-<server> and its own queue, awaited; its RemoveServerResult is embedded in this run’s result. The child powers the host off, removes the BareMetalHost and NMStateConfig, deletes the Agent last and clears the host’s MACs from its own site’s PXE VM — all its own rules, unchanged. Nothing on the MCE is its found: false, and this run completes.

Parent-close policy ABANDON: closing this run never cuts the child off between its power-off and its deletes. A remove-server already running on that id fails this run (RemoveServerAlreadyRunningError, naming it); a child that fails fails it too (RemoveServerFailedError, carrying the child’s own error).

When it stops

Refused before anything is written, or stopped after the Machine

Every one is a FAILED run on the status endpoint, never a 4xx on the trigger, and its message says what to do. Nothing is ever undone.

Refused — nothing changed

errorwhen
ServerNotInServerScanErrorserver-scan has no server of that exact name, so no lock can be taken on it. A host that is only on the MCE is remove-server’s.
ClusterMembershipMismatchErrorserver-scan contradicts the request or the MCE: the server is on another MCE; INSTALLED in another cluster than the one the Agent belongs to; INSTALLED_TO_INVENTORY while the Agent is bound (its agents job re-reads the MCE every 15 min — re-run once it agrees); or contested between two claims.
MultipleBoundAgentsErrorMore than one of the host’s Agents is bound, or has an AgentMachine. One machine is one node.
NotHostedClusterNodeErrorAn Agent bound with no AgentMachine behind it; an AgentMachine in no HostedCluster’s control-plane namespace; or an Agent bound to a ClusterDeployment other than its AgentMachine’s hosted cluster.
ServerReservedErrorAnother run holds server-scan’s lock — typically install-server’s day-long hold. Release it in server-scan, then re-run.
AmbiguousServerNameErrorTwo server-scan documents carry the name.

Stopped after the Machine delete — a re-run resumes

errorwhen
MachineDrainTimeoutErrorStill draining 20 min after the Machine was first seen deleting. Names the Machine’s deletion conditions and every pending pre-drain.delete.hook.* / pre-terminate.delete.hook.* annotation — usually a PodDisruptionBudget or a hook nobody releases.
AgentUnbindTimeoutErrorThe released Agent did not reach known-unbound within an hour; names its last state (or that it is gone, or still bound with its Machine gone — a paused AgentMachine skips the unbind).
MachineDeletionTimeoutErrorThe Agent is free, but the Machine is still there an hour on — another pre-terminate hook, or a Node deletion CAPI cannot finish.
ServerStillPresentErrorThe AgentMachine is still on the MCE 5 min after its Machine went.
HostedNodeStillPresentErrorThe hosted cluster still has the Node. It is an orphan and this run never deletes a Node: the message carries the oc delete node <name> to run against the hosted cluster. remove-server is not started.
AgentStillBoundErrorAfter the Machine went, the Agent is not a clean inventory host within 5 min; names every unmet condition. remove-server is not started.
RemoveServerAlreadyRunningErrorremove-server-<server> is already running (started on its own route). Let it finish, then re-run.
RemoveServerFailedErrorThe child failed; carries its error type, message and id. Re-running skips the hosted-cluster half (the Agent is no longer bound) and runs the removal again.

Transient trouble is retried without bound, as everywhere in this repo: server-scan unreachable, the MCE’s API, and a hosted API server that cannot be reached (HostedClusterUnreachableError). A hosted cluster whose admin kubeconfig cannot be used is permanent (HostedClusterAccessError).

The window it closes

Why an uninstall takes server-scan’s install lock

Two jobs see the machine, neither sees the whole move

The hosted cluster’s nodes job frees the server the moment its Node disappears. The MCE’s agents job re-claims it as INSTALLED_TO_INVENTORY on its own 15-minute cadence. Between the two the document can read AVAILABLE while the host is still in this MCE’s InfraEnv — and another MCE’s install-server would draw it, putting two clusters on one BMC.

Taken first, held a day, never released by a failure

Taken before the first write, with a TTL covering the hosted-cluster half; extended to 24 h before the inventory half; on a failure left to its TTL, because the host may still be half-way out.

The flip side of the day-long hold: a machine uninstalled now is not drawable by install-server for a day, unless someone releases it in server-scan.

Reading a Node

How the run reaches the hosted cluster — and what it never keeps

The admin kubeconfig, pointed at the in-cluster Service

The worker reads the Secret the HostedCluster names in status.kubeconfig (in the HostedCluster’s namespace, key kubeconfig) and replaces its server with the control plane’s Service on the MCE, https://kube-apiserver.<hc-ns>-<hc>.svc:6443. The kubeconfig names the external endpoint, which the pod network may not reach; the Service always is reachable from the MCE, and the API server’s certificate covers it, so TLS is still verified — against the kubeconfig’s own CA.

The limb parses the kubeconfig itself and writes the CA, certificate and key into a per-call temporary directory that is deleted when the call returns — the Kubernetes client’s own loader caches those files for the life of the process. Nothing from the kubeconfig enters an error, a log line or workflow history; errors name the hosted cluster and what was wrong.

Read off the upstream code

Two facts the design had to be corrected for

Neither shape is documented as an API; both were taken from the code that writes it, and both changed what the run does.

The binding names the control-plane namespace

HyperShift creates the AgentCluster — and through it the ClusterDeployment an Agent binds to — in the hosted control-plane namespace, named after the HostedCluster (hypershift-operator/…/platform/agent/agent.go; cluster-api-provider-agent’s AgentCluster controller). So an Agent’s clusterDeploymentName.namespace is <hc-ns>-<hc>, never the HostedCluster’s own namespace.

The HostedCluster is found by HyperShift’s own rule — <namespace>-<name with dots as dashes> (pkg/manifests.HostedControlPlaneNamespace) — matched against a list of HostedClusters, because clusters-a-b could be clusters/a-b or clusters-a/b. Hence list on hostedclusters, not just get.

The provider releases the Agent before the Machine is gone

On a Machine deletion, cluster-api-provider-agent clears the Agent’s clusterDeploymentName, its agentMachineRef label and namespace annotation first, then holds the Machine on pre-terminate.delete.hook.machine.cluster.x-k8s.io/agentmachine until the Agent reaches an unbound state (controllers/agentmachine_controller.go).

For that whole stretch only the AgentMachine’s status.agentRef still links the two. So “a hosted node” includes an AgentMachine whose agentRef names the Agent — otherwise a re-run mid-unbinding would read an inventory host and skip straight to remove-server.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async throughout: the POST hands back the workflow id at once and you poll it.

POST /workflows/server-lifecycle/uninstall-server 202 · 409 if that server is already uninstalling · 502 if Temporal refuses

Which machines, and on which MCE — nothing else. server_names is one name or a list of 1–20, each once (case-insensitively); mce_cluster is accepted with or without ocp4- and is needed because it names the activity queue of the worker inside that MCE; namespace (the InfraEnv’s, where the BMH and Agent live) defaults to inventory. The reply follows what was sent: one name is {workflow_id, run_id}, a list is a per-run report — even a list of one.

The body forbids unknown fields: there is no count, node_pool or hosted_cluster — server-scan and each Agent’s own binding say where a server is, and a caller-supplied cluster could only contradict them. Each is a 422, and so is server_name (singular), pointing at server_names.

The id is the machine, lowercased, so one server is one uninstall however its serial was typed. The uninstall- prefix keeps it apart from install-server-name-<server> and from remove-server-<server>, which this run starts as its child.

One ClusterRole, cluster-wide because Machines live in each control-plane namespace and kubeconfigs in each HostedCluster’s — neither an InfraEnv namespace, neither named in the request. Rendered by rbac.hostedClusters (default true); off, any host with an Agent fails its inspection with a 403 before anything is written, so use remove-server on such an MCE. The worker’s pods also need network access to each kube-apiserver.<hc-ns>-<hc>.svc:6443 — check NetworkPolicies on the control-plane namespaces if verifying-node keeps retrying HostedClusterUnreachableError.

Roll the limb out first. CI ships the brain before the limb, and a brain that reaches activities an old limb does not register retries them until it does — the run sits in checking-inventory. Upgrade each MCE’s server-lifecycle-worker and apply its ClusterRole before using this route. Production’s chart is vendored in redbull-platform (gitops/charts/server-lifecycle-worker/) and needs the same ClusterRole there.

What it never does

  • No NodePool or replicas change — that is scale-down-nodepool’s (above).
  • No Node delete, ever — an orphan is reported with the command to run.
  • No Node-side drain — CAPI drains as the Machine goes.
  • No PXE map write — the PXE cleanup stays in remove-server.
  • No undo — a Machine delete cannot be undone, so a failure leaves everything as it is and a re-run resumes.
