Temporal workflow · domain: segment-lifecycle

initialize-segment — what actually happens

A single request creates a network segment in the Segments Manager. That is the whole workflow: one activity, retried until it succeeds, and the segment is Available the moment the run completes.

One segment = one durable Temporal run — which is the point, not the ceremony.

TriggerPOST /workflows/segment-lifecycle/initialize-segment
Workflow idinitialize-segment-<network>
Workflow queueinitialize-segment-workflow
Activity queuesegment-lifecycle-activity
One activity. Why a workflow at all?

Because the retry, the dedup id and the status are the product

A bare HTTP call to the Segments Manager would do the same thing on a good day. This exists for the bad ones.

Durable, unbounded retries

A Segments Manager outage is out-waited, not failed — and the operator's request survives an orchestrator restart, because the run lives on the Temporal server, not in a process.

One place owns the dedup id

The id is built from the network alone, so a duplicate trigger while a run is in flight is a 409 rather than a second creation attempt.

A status anyone can poll

One run per segment, each with its own id and its own outcome — which is exactly what lets the /bulk route start N of them and report per segment instead of returning a single pass/fail for the batch.

Creation is inside Temporal

It used to be the other way round: the Segments Manager created the segment, then fired a best-effort HTTP trigger at us. Creation sat outside any run — invisible in the UI, and silently skipped whenever that call failed.

If you remember this workflow being bigger

The firewall flow is gone

What was removed, and why

This workflow used to do far more: discover every same-site peer segment its type needed rules against, submit open-rules requests to the black-box next connectivity service (plus mandatory MCE↔BMC rules), mirror the pending request ids into the Segments Manager UI, poll indefinitely for a human to approve them — rolling its history over with continue_as_new so a slow approval could never fail it — and finally flip the segment from Locked to Available.

Every firewall between segments is open now. So the peers, the requests, the approval wait, the request-id display, the failure note and the Locked status itself were all removed, along with their configuration (NEXT_*, PORTS_*, SITE_NETWORKS, SITES_WITH_OPEN_CONNECTIVITY) and the test-only mock service. A segment is born Available.

Running it twice

A re-submitted definition is not an error

Temporal retries activities, and operators re-POST things. Both have to be safe, so create_segment resolves a rejected create instead of trusting the status code.

How a conflict is resolved

The Segments Manager answers 400 both for “this CIDR is already taken” and for “this definition is invalid”, so only its stored record can tell them apart. The activity looks the CIDR up and decides:

  • Absent → the definition itself was rejected — SegmentValidationError
  • Present and matching → a previous attempt already applied it — success
  • Present and different → two definitions for one CIDR — SegmentConflictError

What “matching” compares

The segment's immutable identity: site, vlan_id, epg_name. Deliberately not dhcp — the Segments Manager models that as the one field editable after creation, so a flipped flag is a legitimate later edit, not evidence of a conflicting definition. A difference there is logged and the stored value kept. Nor type, status or cluster: those are allocation state, so a segment allocated since it was created still matches the definition that created it.

Who decides a definition is valid

The Segments Manager is the validator of record

Site known, CIDR inside the site pool, no overlap with an existing segment, VLAN free — all its rules. The orchestrator re-derives none of them, because two copies of one rule set only drift apart.

So a bad definition is a FAILED run, not a 4xx

Creation happens inside the workflow, so the trigger has already returned 202 by the time the Segments Manager sees the definition. An invalid one surfaces on GET /workflows/runs/{workflow_id} as a failed run carrying the manager's own error text. The route itself only rejects a body that does not fit InitializeSegmentInput at all — including one carrying a type.

A segment is born without a type

The type (HC, MCE, INVENTORY, PXE) is allocation state, like the cluster: allocate-segment takes it as a parameter and the Segments Manager stamps it onto whichever Available segment it reserves; a release clears it again. So every created segment joins one shared pool per site, and a type in this body is refused (422) rather than silently dropped.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async — the id comes back immediately, and the id is what you poll.

POST /workflows/segment-lifecycle/initialize-segment 202 · 409 if already running

The body is the full segment definition — the workflow creates it, so it needs everything the Segments Manager needs.

// request
{
  "segment":  "130.154.20.0/24",
  "site":     "site1",
  "vlan_id":  100,
  "epg_name": "EPG_PROD_01",
  "dhcp":     true               // optional — defaults to true
}

// 202 response
{ "workflow_id": "initialize-segment-130.154.20.0", "run_id": "…" }

The CIDR mask is dropped from the id, so two requests for the same network address dedup regardless of how the mask was written. Re-triggering while a run is in flight answers 409; re-triggering after it finished simply completes again.

POST /workflows/segment-lifecycle/initialize-segment/bulk 202 · always, with a per-item report

Takes {"segments": [ … ]} and starts one workflow per segment — never one batch workflow. Each segment gets its own dedup id, its own run status and its own failure, so a bad row in the middle can neither delay nor fail the rest.

// 202 response
{ "started": 2, "already_running": 1, "failed": 0,
  "results": [
    { "segment": "130.154.20.0/24", "workflow_id": "initialize-segment-130.154.20.0", "status": "started",         "run_id": "…" },
    { "segment": "130.154.21.0/24", "workflow_id": "initialize-segment-130.154.21.0", "status": "already_running" }
  ] }

It answers 202 even when items failed: a single status code for the batch would hide which segments actually got a workflow.

GET /workflows/runs/{workflow_id} 200 · 404 if unknown id

The same domain-agnostic status endpoint every workflow uses. While RUNNING it returns the live phase; when COMPLETED, the result.

// RUNNING
{ "workflow_id": "initialize-segment-130.154.20.0",
  "workflow_type": "InitializeSegmentWorkflow", "status": "RUNNING",
  "progress": { "phase": "creating-segment" } }

// COMPLETED
{ …, "status": "COMPLETED",
  "result": { "segment": "130.154.20.0/24" } }
When things go wrong

Outages are out-waited. Real errors stop the run.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so a Segments Manager outage never fails a run. Retrying stops only for errors explicitly classified as permanent.

Classified as permanent — these fail the run

  • SegmentValidationError — the Segments Manager rejected the definition
  • SegmentConflictError — that CIDR is stored with different attributes
  • SegmentsManagerAuthError — bad SEGMENTS_MANAGER_API_TOKEN (401/403)

Exactly the three errors create_segment raises deterministically — no more, because a type listed here that the activity cannot raise is dead configuration, and no fewer, because an unclassified permanent error is the worst failure mode available.

Everything else is transient

Any other Segments Manager response becomes a retryable SegmentsManagerError — including a lookup that fails during conflict resolution, which is deliberately treated as “ask again” rather than guessed at.

The failure mode to watch for

An unclassified permanent error retries every minute forever: the run sits RUNNING in the Temporal UI, not FAILED, with the real error on the activity. The fix is to classify it, never to add a deadline.

Nothing to clean up

On failure or cancellation there is no compensating cleanup, because there is nothing half-applied: either the segment was created or it was not.

The field names and constraints mirror the Segments Manager's own POST /api/segments schema exactly, so the activity can post the body straight through. Semantic validation stays there.
