provision-dell-server — what actually happens

A technician racks a Dell and gives its iDRAC an IP. That is the last manual step. This workflow takes it from there to a fully configured machine — root on the enforced password, the template applied, the boot RAID built and the profile named — after which install-server can draw it.

It replaces what the DC team used to do by hand in OpenManage Enterprise: discover the machine, build a server profile, attach a template, rename the profile — plus the RAID 1 someone built in the BIOS. Dell only, for now.

Why this is a workflow and not a script

Because it reboots someone else’s hardware

A script that does this has to survive a template deployment that reboots the machine and a Lifecycle Controller applying RAID on the way up — neither of which fits in a request, and both of which leave a machine half-configured if the script dies.

Every wait is durable and bounded

Discovery, template deployment, the reboot that applies storage, the rename — each is a workflow.sleep on the Temporal server, not a process holding a socket. Each is machine convergence, so each gets a real deadline and fails loudly by name when it passes.

The id is the machine

Built from the iDRAC address alone — the only identity the run has before it has read anything. A technician double-submitting a row of a bulk list lands on the running run rather than starting a second one that races it through the same reboots.

Nothing half-applies

Storage is staged and applied by one reboot, so the machine is never left between two layouts by a crash in the middle. Every activity is idempotent: a re-run of a finished server finds the profile already deployed and the RAID already built, and changes nothing.

Done means configured

The run ends on its own work, not on another system noticing it. server-scan picks the machine up on its next six-hourly collection; waiting for that would add hours to every run to observe something the run cannot influence — and would turn a paused collector into a fleet of failed provisions.

The run, step by step

Eight steps, and what each one is waiting for

Every phase below is a value you will see on GET /workflows/runs/{workflow_id}, alongside a waiting_on naming the job or the machine the run is blocked on.

1

probe_idrac_credentials

phase probing-idrac

Which root password does this iDRAC accept? The target one first — a re-run, or a machine that shipped with it — then each configured factory password, one request each, in order.

GET/redfish/v1/Systems/System.Embedded.1 · once per candidate, HTTP Basic

iDRAC9 blocks a source address after 3 failed logins in its fail window. One round is at most three candidates, so a round can only trip the block when all of them are wrong — and the next round then waits the penalty out (11 min) instead of feeding it. Three rounds, then IdracCredentialsRejectedError.

An iDRAC that answers nothing is a different wait: still being cabled, or a mistyped IP. Retried every 2 min for up to 30 min, then IdracUnreachableError.

2

read_idrac_identity · find_in_server_scan

phase reading-identity → checking-server-scan

Service tag, model and iDRAC firmware, off the machine itself. A non-Dell or non-PowerEdge answer stops here (NotADellServerError).

Then the guard that matters: is a cluster already using this machine? Everything after this point reboots it or rewrites its BIOS, and an IP typed one digit wrong must not take a production node down. A server-scan document whose lifecycle state is anything but AVAILABLE fails the run with ServerAlreadyInstalledError.

GET/servers?search=<service tag> · then /servers/{id} to confirm the serial exactly

Never /servers/available — that endpoint live-rechecks against the vendor manager on every call, which is far more than a yes/no guard needs. These are Mongo-backed reads, and this is the only time the run reads server-scan.

3

find_ome_device · start_ome_discovery

phase discovering-in-ome

Skipped entirely when OME already holds the service tag. Otherwise the run creates a discovery for this one address and waits for its job — polled every 30 s, deadline 30 min.

POST/api/DiscoveryConfigService/DiscoveryConfigGroups · RunNow, one target
GET/api/JobService/Jobs(<id>) · until LastRunStatus is terminal

The discovery group is named deterministically from the service tag, the purpose and the run id, so a retried activity finds the discovery it already created instead of making a second one.

4

deploy_ome_template

phase deploying-template

The template for this machine’s (Redfish model, iDRAC firmware) pair, from DELL_TEMPLATES. There is no fallback: an unlisted pair fails with TemplateNotConfiguredError rather than getting a near-miss template.

POST/api/TemplateService/Actions/TemplateService.Deploy · may reboot the machine

A device already carrying a profile from this template returns that profile’s own DeploymentTaskId, so a retry waits on the job that really deployed it. A profile from any other template is ProfileConflictError — never redeployed over. Deadline 2 h, polled every minute.

5

check_idrac_login

phase verifying-root-password

Root’s password was set over Redfish back in step 2, before OME ever saw the machine, so this is a guard rather than the mechanism: nothing in the deployment may have moved it. Polled every minute for 20 min, because the iDRAC may restart after the template changes its own settings. Still refusing the target password → TemplatePasswordNotAppliedError, which means the template carries a Users.* component that changed it — something the step-2 audit should already have refused.

There is no re-discovery. There used to be: OME was discovered on whatever password the server arrived with, the template then enforced the target one, and OME had to be re-pointed at it or it would lose the machine. Setting the password first makes a stale credential impossible, so OME is discovered exactly once.

6

read_storage_layout → stage → apply → verify

phase configuring-storage → applying-storage → verifying-storage

RAID 1 across the BOSS pair, every PERC drive Non-RAID. Both are staged OnReset and applied by one reboot, then the layout is read back and re-planned — a converged plan is the only success.

POST.../Storage/<boss>/Volumes · RAIDType RAID1, @Redfish.OperationApplyTime OnReset
POST.../DellRaidService.ConvertToNonRAID · PDArray
POST.../ComputerSystem.Reset · ForceRestart — the one reboot

A PERC runs its Non-RAID conversion immediately (a real-time job), so the reset that applies the BOSS volume must not cut it off mid-apply. The run waits for the real-time jobs to settle before resetting, and the limb refuses the reset while any job is still active.

Storage comes after the template on purpose: the template can reboot the machine and apply BIOS attributes, so doing storage afterwards means the layout verified here is the one the server ends up with — and every storage call runs on the target password, never a factory one.

7

request_server_name · get_ome_profile

phase naming-server → verifying-name

The naming service is the author of the name: it reads the device’s cores, memory and disks from OME, rounds them its own way and renames the server profile. This workflow asks, then verifies — it never re-derives the numbers, because two roundings eventually disagree.

ocp-dell-r660-<region>-128c-1024gb-10tb-<service tag>

Checked against the convention, the run’s region and the iDRAC’s own service tag — getting either wrong would file the machine under the wrong server-scan site, or name it after a different server. Read back from the OME profile, because that is the name server-scan reads. Polled every 30 s for 30 min, then ServerNameNotAppliedError.

And that is the run. The machine is configured, and server-scan’s own OME collector lists it on its next pass — which the run deliberately does not wait for. Until then the machine simply is not in the inventory yet, which is a fact about server-scan’s schedule rather than anything wrong with the server.

The part that would be easy to get dangerously wrong

No password is ever in Temporal history

Activity inputs, results and error messages are all recorded verbatim in history and readable by anyone with Temporal UI access. So a run never carries a password — it carries a position.

Credentials by index

A run refers to a root credential as IdracRef.credential, an integer: 0 is the target password, 1 and up are the factory ones in configured order. The limb resolves the index against its own Secret at the moment of the call. History records credential=1; the logs say credential=1; the result says factory-1.

The list changing under a running run is caught rather than guessed at: an index with no password behind it is IdracCredentialsMissingError.

Only root. Never the OME account.

This workflow touches iDRAC user 2 (root) and nothing else. The OME service account on the iDRAC is never read and never changed — changing it would cut OME off from the machine, and OME is how the rest of this run (and server-scan after it) sees the server at all.

The real passwords live only in the worker’s Secret. They are not in this repo, not in the chart’s values.yaml, and not in the tests.

Storage policy

Nothing is ever deleted to make room

A new server arrives with an empty controller. One that does not is either not new, or was configured by hand — and either way that is a person’s call, not this workflow’s.

What gets built

  • The BOSS card (the M.2 boot pair) carries one RAID 1 over both drives — the OS disk.
  • Every drive behind a PERC becomes Non-RAID, so the OS sees each one directly (ODF and local storage want whole disks).
  • Anything else — CPU-attached NVMe, an embedded SATA controller — has no RAID state to set and is left alone.

Bond members and drive states are read from the machine, never assumed. NVMe drives report their RAID status under DellPCIeSSD rather than DellPhysicalDisk, which is the kind of detail that silently drops a drive if you read only one of them.

What fails the run instead

  • A drive that is already a volume member
  • A BOSS volume that is not exactly that RAID 1
  • A PERC that already holds volumes
  • A drive in a state that is neither Ready nor NonRAID

Each is a StorageLayoutUnsupportedError naming what it found, raised before anything is staged. Delete it by hand if it really is unused.

The template must not carry storage components

A Dell server profile template that includes storage deploys with RAIDresetConfig=True, which wipes the controller — every volume on the machine, at step 4, before this workflow has read the layout it promised never to destroy. Capture templates from BIOS and iDRAC components only; the RAID is this workflow’s job, at step 6.

Where the machine is

Region is resolved at the edge, once

From the iDRAC’s address prefix

Technicians submit IPs, not regions, and the address plan already says where a machine is: each region’s iDRACs live under their own prefix. The router resolves it and the run carries it as input.

So editing the prefix table never changes what an in-flight run does — a lookup inside the workflow would be a non-deterministic change on replay — and an address matching no prefix is a 422 to the technician now, not a failed run an hour later.

It has to be a server-scan site code

The region is the <region> token of the server name, and server-scan parses a server’s site out of that name. A region that is not a site code server-scan knows produces a machine filed in the wrong place — which is why the name is verified against the run’s region at step 7.

An explicit region in the request body overrides the lookup, for a machine on a network the table does not cover yet.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Technicians rack servers in batches, so /bulk is the route that gets used most.

POST /workflows/server-provisioning/provision-dell-server 202 · 409 if already running · 422 if no region

One machine, identified only by its iDRAC address.

// request
{
  "idrac_ip": "134.1.20.31",
  "region":   "israel"          // optional — resolved from the prefix when omitted
}

// 202 response
{ "workflow_id": "provision-dell-server-134.1.20.31", "run_id": "…" }

The address is normalised before it becomes the id, and a non-address is refused rather than reinterpreted (010.001.002.003 is an error, not 10.1.2.3), so the dedup key is the same however it was typed. Unknown fields are refused too.

POST /workflows/server-provisioning/provision-dell-server/bulk 202 · always, with a per-item report

Takes {"servers": [ … ]} and starts one workflow per iDRAC. Each machine gets its own dedup id, its own status and its own failure, so one bad row can neither delay nor fail the rest of the rack.

// 202 response
{ "started": 2, "already_running": 1, "rejected": 1, "failed": 0,
  "results": [
    { "idrac_ip": "134.1.20.31", "workflow_id": "provision-dell-server-134.1.20.31", "status": "started",         "region": "israel", "run_id": "…" },
    { "idrac_ip": "134.1.20.32", "workflow_id": "provision-dell-server-134.1.20.32", "status": "already_running", "region": "israel" },

The same domain-agnostic status endpoint every workflow uses. A provisioning run is long, so phase and waiting_on are the fields to watch.

  "progress": { "phase": "applying-storage",

// COMPLETED
{ …, "status": "COMPLETED",
  "result": { "service_tag": "7XK2QF3", "initial_credential": "factory-1",
              "profile_name": "ocp-dell-r660-israel-128c-1024gb-10tb-7XK2QF3",
              "boss_raid1_created": true, "non_raid_drives_converted": 4,
              "os_hostname_cleared": true, "bios_attributes_checked": 37,
              "bios_attributes_remediated": 1, "bios_attributes_unverified": 0 } }

bios_attributes_unverified counts attributes the template names that this machine’s BIOS registry does not have — the honest coverage gap, and what says whether one template can serve several firmware levels. initial_credential names the credential by position (target, factory-1), never by value — it tells you whether the machine arrived factory-fresh without telling you the password.

When things go wrong

Outages are out-waited. Real errors stop the run.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so an OME restart or a flapping iDRAC never fails a run. Retrying stops only for errors explicitly classified as permanent. Each activity gets 5 min per attempt.

Activity errors classified as permanent

  • IdracAuthError — the iDRAC rejected the credential mid-run
  • IdracCredentialsMissingError — the configured list changed under the run
  • IdracRequestRejectedError — the iDRAC refused the request itself
  • OmeAuthError — bad OME_USERNAME/OME_PASSWORD
  • OmeRequestRejectedError — OME refused the request itself
  • TemplateNotConfiguredError — no DELL_TEMPLATES entry for this (model, firmware)
  • TemplateNotFoundError — OME holds no template by that name, or several
  • ProfileConflictError — the device carries a profile from another template
  • ServerNamerRejectedError — the naming service refused this request
  • ServerScanAuthError — bad SERVER_SCAN_API_TOKEN

The list is built from the exception classes, not from strings — Temporal matches on the type name, so a typo in a literal would silently read as “retryable” with nothing to notice. A wrong name here is an ImportError at worker startup instead.

Failures the workflow itself raises

Decisions, not call failures — each one stops the run immediately: RegionMissingError, NotADellServerError, ServerAlreadyInstalledError, IdracUnreachableError, IdracCredentialsRejectedError, OmeDiscoveryFailedError, TemplateUnsafeError, RootPasswordNotSetError, TemplateDeployFailedError, TemplatePasswordNotAppliedError, ConfigurationDriftError, StorageLayoutUnsupportedError, StorageJobFailedError, StorageNotConvergedError, ServerNameNotAppliedError.

The failure mode to watch for

An unclassified permanent error retries every minute forever: the run sits RUNNING in the Temporal UI, not FAILED, with the real error on the activity. The fix is to classify it, never to add a deadline.

What a failed run leaves behind

Whatever it had already done — there is no compensating rollback, on purpose. Nothing it does is destructive, so a half-provisioned machine is safe to leave and safe to re-run: the next run finds the profile deployed, the RAID built, and carries on from the first thing that is missing.
