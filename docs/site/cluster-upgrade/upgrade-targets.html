upgrade-targets — what can this cluster go to?

One question about one HyperShift HostedCluster: which releases may a person pick as the target of an upgrade-cluster run? The answer is every ladder rung newer than the cluster’s mastertag, of a minor its MCE supports, to which an upgrade path resolves — newest first. It is what the “New upgrade” form draws its target list from.

It is the one synchronous route in the API. Every route that starts work answers 202 with a workflow id to poll. This one is a question, not a job: it runs a short, read-only workflow, waits up to 60 s for it, and returns the answer in the HTTP response. There is no run to poll. It changes nothing: two reads of day1 git, no commit, nothing read or written on an MCE or a cluster.

TriggerGET /workflows/cluster-upgrade/upgrade-targets?cluster=<cluster>
Workflow idone per cluster: upgrade-targets-<cluster>
Workflow queueupgrade-targets-workflow
Activity queueupgrade-gitops-activity (hub)
Answerin the response, within 60 s
What it reads

Two reads of day1 git, on the hub limb

Both reads are activities on upgrade-gitops-activity, served by upgrade-gitops-worker on the hub. Both read day1 at main. Nothing else is called: no MCE limb, no mirror, no agent.

1 · The cluster’s day1 file

read_day1_cluster finds <cluster>.yaml under sites/<site>/mces/<mce>/hostedClusters/. The folder names the hosting MCE, so the caller never gives one. The file gives the mastertag (the control plane’s release), each NodePool’s workertag (else the file’s, else the mastertag), and the NodePools themselves.

A file outside that layout names no MCE: the run fails (UpgradePlanningFailedError, “no MCE to run on”). A file the parser refused — a duplicate key, a NodePool named twice — fails it too, listing every problems line, before the rules are read. A wrongly read file would offer wrong targets.

2 · The upgrade rules for that MCE

read_upgrade_rules reads day1’s upgrade/ladder.yaml and upgrade/mces/<mce>.yaml, after day1’s own scripts/validate_upgrade_rules.py passed them. From them: the ladder (the releases the team mirrored and verified), maxWorkerSkew, the MCE’s version and its supportedHostedVersions, and the date the ladder was last checked against the upgrade graph.

Missing or invalid rules fail the run (UpgradeRulesInvalidError).

How it decides

Ladder rungs only, and only those a path reaches

The choice is pure code (target_options in upgrade_path.py), the same resolver an upgrade-cluster run plans with. For each candidate it works out the whole path, exactly as a run would, and keeps the candidate only if a path exists.

#rulewhy
1Only ladder rungs are candidates.The ladder is what the team mirrored and verified. A release in the registry that is not a rung is never offered, so a minor missing from the mirror never is either.
2Only rungs newer than the mastertag.There is no downgrade, and the current release is nothing to upgrade to.
3Only rungs of a minor in the MCE’s supportedHostedVersions.A minor the MCE cannot host is no target. An entry that does not read as a minor is ignored.
4Only rungs a path resolves to.The control plane through every minor, no must rung skipped, no NodePool more than maxWorkerSkew minors behind: the path rules. A rung the rules refuse is dropped, not reported.
5Newest first.The first entry is the furthest the cluster can go.

What each target says

  • version, minor — the rung, and its minor ("4.21").
  • control_plane_steps — how many of those steps move the control plane: at least one per minor it crosses.
  • steps — every step of that path, control plane and workers. A worker step counts once, however many NodePools it rolls. Counted with workers_to_target on, the run’s default.
  • newest_in_minor — the newest rung of its minor: the pick for that minor.
  • must — the rung is a must rung on the ladder.

An empty list is an answer, not an error

targets comes back empty when:

  • the cluster is already at the newest rung its MCE supports;
  • the file has no mastertag (control_plane_version is then null);
  • no path reaches any rung — a NodePool newer than its control plane, a NodePool already beyond maxWorkerSkew, or a workertag that is no release.

The response does not say which. To find out, start an upgrade-cluster run toward the target you expected: its planning fails naming the rule that refused, with nothing committed.

The NodePools, for the form’s order and maxUnavailable fields

The answer also carries the file’s nodepools (name, workertag, zone, replicas, max_unavailable, as written) and nodepool_order: the order a run would roll them in when its request names none — the file’s upgrade.nodePoolOrder, else by zone when every NodePool has one, else file order.

One difference from a run: when upgrade.nodePoolOrder does not name each NodePool exactly once, this answer offers file order instead of failing. An upgrade-cluster run fails planning on that file unless its request gives nodepool_order.

HTTP surface

How you call it

Served by workflows-orchestrator-api. The route starts an upgrade-targets run with a 60 s execution timeout and waits for its result. Two asks for the same cluster at the same time share one run: the id is upgrade-targets-<cluster>, and a second ask joins the run already under way.

GET /workflows/cluster-upgrade/upgrade-targets?cluster=<cluster> 200 · 404 · 409 · 422 · 504

cluster is the day1 cluster file’s name (also its Argo CD Application), without .yaml — not the HostedCluster’s name, which the chart derives from the file. It must match ^[a-z0-9]([-a-z0-9.]{0,251}[a-z0-9])?$, the same rule the upgrade-cluster start applies, and is checked before anything runs. No MCE: the run finds it.

// 200 — a cluster at 4.19.53 with three zoned NodePools, on today’s ladder
{
  "cluster":               "<cluster>",
  "mce_cluster":           "<mce>",             // from the folder the day1 file is in
  "mce_version":           "2.17.3",            // from upgrade/mces/<mce>.yaml
  "control_plane_version": "4.19.53",           // day1 mastertag; null when the file has none
  "supported_minors":      ["4.21", "4.20", "4.19"],
  "ladder_revision":       "…",                 // the day1 commit the rules were read at
  "verified_against_graph": "2026-10-31",       // ladder last checked against the upgrade graph
  "targets": [
    { "version": "4.21.40", "minor": "4.21", "steps": 3, "control_plane_steps": 2, "newest_in_minor": true, "must": true },
    { "version": "4.20.44", "minor": "4.20", "steps": 2, "control_plane_steps": 1, "newest_in_minor": true, "must": true }
  ],
  "nodepools": [
    { "name": "zone-a", "workertag": null, "upgrade_type": null, "zone": "a", "replicas": 1, "max_unavailable": "1" },
    { "name": "zone-b", "workertag": null, "upgrade_type": null, "zone": "b", "replicas": 1, "max_unavailable": "1" },
    { "name": "zone-c", "workertag": null, "upgrade_type": null, "zone": "c", "replicas": 1, "max_unavailable": "1" }
  ],
  "nodepool_order": ["zone-a", "zone-b", "zone-c"]
}

4.21.40 is three steps: control plane → 4.20.44, control plane → 4.21.40, then one worker step to 4.21.40. No 4.19 rung is offered: 4.19.53 is the cluster’s own.

answermeans
200the answer, as above. targets may be empty (why)
404day1 has no <cluster>.yaml under any MCE (ClusterFileNotFoundError)
409the run failed on something it cannot use; the detail is its reason. Among them: more than one <cluster>.yaml in day1 (AmbiguousClusterFileError); rules missing or invalid (UpgradeRulesInvalidError); a file outside sites/<site>/mces/<mce>/hostedClusters/ or one the parser refused (UpgradePlanningFailedError); a mastertag or a ladder rung that is no release, or a rung listed twice (UpgradePathRefusedError)
422cluster missing or not a valid name; nothing ran
504no answer in 60 s: “is the upgrade-gitops limb running?” A read that keeps failing for a passing reason (git unreachable) is retried until then and ends here too

The 60 s is the run’s own execution timeout, so a read that hangs ends on its own: nothing is left running after a 504.

No progress query, on purpose

An upgrade-targets run has no @workflow.query def progress. Nothing polls it: the caller already holds the HTTP request open and gets the result in the response. The run still shows in Temporal and on GET /workflows/runs/{workflow_id}, status only.

What happens with the answer

A choice for a person, then an upgrade-cluster run

The person picks a version from targets and starts an upgrade-cluster run with it as target_version. The NodePool list seeds the request’s nodepool_order and max_unavailable; the form sends them only where the person changed them.

The answer is git’s intent, not a promise

It is read from day1 only. The run that follows still does its own planning: it checks git against the HostedCluster and its NodePools, pins every release to a digest in the mirror, and checks the rules against the MCE. A target offered here can still fail there — a cluster that does not run what its file says, a release missing from the mirror.

Nothing to undo

Asking is free. The answer is not stored, nothing is reserved, and the next ask reads day1 again. To see the full plan for one target, start the upgrade-cluster run: starting it is the dry run, and an abort before approve ends it CANCELLED with nothing committed.

Reference

What it never does

  • No commit to day1, no push, no Argo CD sync.
  • No read or write on an MCE, a HostedCluster or a NodePool — only day1 git, on the hub limb.
  • No mirror lookup and no digest pinned: a target is a ladder rung, whatever the registry holds.
  • No release outside the ladder, no minor the MCE does not support, no downgrade.
  • No LLM call.
  • No run left to poll, and no run left running after its 60 s.
