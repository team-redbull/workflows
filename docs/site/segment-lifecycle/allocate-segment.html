allocate-segment — what actually happens

A single request — a cluster name and the site to allocate at — reserves a VLAN segment for that hosted cluster in the Segments Manager and verifies the reservation landed. Nothing is written to git: since 2026-11-11 the cluster file is provision-cluster's, which starts this workflow as an awaited child and records the allocation in the file it publishes. The route stays for a manual allocation, on the same id, so the two dedup.

The run, step by step

From “allocate for this cluster at this site” to “verified in the Segments Manager”

Three stages. Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run an allocation currently is. Verification is the last word: a VLAN is never recorded anywhere unless the Segments Manager confirms the reservation.

✓

Type check — HC only; a site is required

phase pending

Runs before anything is touched. This workflow allocates HC segments only; any other type fails immediately with UnsupportedSegmentType. A run with no site fails here too, as SiteMissingError — the API requires one, and there is nothing to derive it from any more (the run used to read it from where the cluster file sat on a day1 branch; provision-cluster reads the day1 folder now and passes the site on).

1

get_valid_sites

phase validating-site

The site is the caller's — provision-cluster passes the day1 folder the cluster file goes in (sites/<site>/mces/<mce>/) — cross-checked against the Segments Manager's site list, so a folder or spelling mismatch between day1 and the Segments Manager fails loudly as UnknownSite before anything is allocated.

GET/api/sites · the cross-check list
2

allocate_segment

phase allocating-segment

Reserves a segment for the cluster at the site, as the requested type. Available segments carry no type, so the pool is shared: the Segments Manager hands out any Available segment at the site and stamps the type onto it in the same atomic update (a release clears it again). It is idempotent per (cluster, site, type): a repeat call — a Temporal retry, or a whole re-run — returns the existing allocation, so double-allocation is impossible by construction.

POST/api/segments/allocate · Bearer · → { vlan_id, segment, epg_name, … }

An empty pool (503) fails loudly as SegmentPoolExhaustedError — a drained pool is refilled by an operator creating segments, not by retrying every minute forever.

3

get_segment

phase verifying-allocation

Reads the allocated CIDR back and requires status == Allocated, the exact cluster name, the exact VLAN and the requested type (the allocation wrote it). Any mismatch is AllocationNotConfirmed, so nothing downstream — provision-cluster's file, the DHCP scope — ever records a VLAN the Segments Manager doesn't confirm.

The type is checked only when the read-back carries the field. A payload without the key predates it — history replayed from the previous brain, or a limb one rollout behind (CI ships the brain first) — and says nothing about the allocation. A reported null still fails.

GET/api/segments/by-segment?segment=… · public GET
⏸

After the run — not part of it

no phase

provision-cluster writes the vlanId + dhcp_values block into the cluster file it pushes, the day1 CI chain renders the MachineConfigs from that vlanId on the branch, a human merges, Argo CD (which reads main only) renders the Crossplane Request, and Crossplane creates the DHCP scope.

Why the run doesn't wait for the scope. It used to — a bounded read-only poll of the DHCP API. But the scope needs the merge, and the merge is a person's, after this run: a deadlock, not a slow wait. So the run ends at the verified allocation.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async: the run outlives the request by design. Normally you do not call this: provision-cluster does, as a child.

POST /workflows/segment-lifecycle/allocate-segment 202 · 409 if already running

The body names the cluster and the site — the day1 folder the cluster file goes in, as the Segments Manager spells it. The site is required: a body without one is a 422, as is an unknown field, a site that is not a plain name token, or the retired values_branch (a 422 that says what replaced it).

// request
{
  "cluster": "ocp4-prep-herzi-site1-a",
  "site":    "site1",                 // required — the day1 folder, as the Segments Manager names it
  "type":    "HC"                     // optional — HC is the default and the only supported value
}

// 202 response
{ "workflow_id": "allocate-segment-HC-ocp4-prep-herzi-site1-a", "run_id": "…" }

The id carries the type on purpose. Allocation is scoped by (cluster, site, type) — one cluster can hold one segment per type at a site — so a type-less id would make two legitimate allocations collide. The site is deliberately not in the id: a cluster lives at one site, so two requests for one cluster — a manual one and provision-cluster's child — must collide on one run. Re-triggering while a run is in flight answers 409.

GET /workflows/runs/{workflow_id} 200 · 404 if unknown id

The same domain-agnostic status endpoint every workflow uses. While RUNNING it returns the live phase; when COMPLETED, the result.

// RUNNING
{ "workflow_id": "allocate-segment-HC-ocp4-prep-herzi-site1-a",
  "workflow_type": "AllocateSegmentWorkflow", "status": "RUNNING",
  "progress": { "phase": "verifying-allocation" } }

// COMPLETED
{ …, "status": "COMPLETED",
  "result": { "cluster": "ocp4-prep-herzi-site1-a", "site": "site1", "type": "HC",
              "vlan_id": 23, "segment": "10.20.90.0/24", "epg_name": "EPG_HC_23" } }
When things go wrong

Outages are out-waited. Real errors stop the run.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so a Segments Manager outage never fails a run. Retrying stops only for errors explicitly classified as permanent.

Classified as permanent — these fail the run

  • UnsupportedSegmentType — not HC (workflow-raised, before anything runs)
  • SiteMissingError — no site on the run (only possible outside the API)
  • UnknownSite — the site isn't in GET /api/sites
  • SegmentValidationError — the Segments Manager rejected the request (e.g. bad cluster name)
  • SegmentPoolExhaustedError — no Available segment at the site (the pool is shared by every type)
  • AllocationNotConfirmed — the read-back didn't match the allocation
  • SegmentsManagerAuthError · SegmentNotFoundError

Transient by classification

SegmentsManagerError — any other answer from the Segments Manager, or none. It retries forever; an unclassified permanent error shows as a run stuck RUNNING in the Temporal UI — the fix is to classify it, not to add a deadline.

Nothing to clean up

On failure or cancellation there is deliberately no compensating cleanup: the allocation is kept — a re-run idempotently reclaims it. When provision-cluster is the caller, its failure says which child failure it saw.

Operating it

What happens if you run the same cluster again

Idempotency is a rule of the orchestrator — see the three rules that surprise people. Here it is the Segments Manager's: the allocation is keyed server-side, so a re-run converges with no human in the loop.

Re-run after completion — the same allocation

The Segments Manager returns the same segment (idempotent per cluster/site/type) and the read-back verifies it again. provision-cluster relies on exactly this: a re-run of a cluster whose child already ran gets the allocation it recorded.

The one thing a re-run will not do

Allocate at a different site. The id has no site in it, and the Segments Manager holds one allocation per (cluster, site, type): a cluster that must move sites is released first (release-segment).
