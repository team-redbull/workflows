convert-segment — what actually happens

One request — site, source type, destination type, quantity — rebalances segment inventory between types. The workflow finds up to quantity Available, unassigned segments of the source type at the site and re-types each one in the Segments Manager. That is the whole operation: a converted segment stays Available and is immediately allocatable as its new type.

Fewer matching segments than requested is not an error: the run converts what exists and reports the shortfall in its result. Available and unassigned is the guard, asserted on every search hit rather than trusted from the filter. See why.

The run, step by step

From “convert N segments” to “N segments now carry the new type”

Three stages plus a per-segment loop. Every step is a machine op, so the run is bounded, fast and fails loudly — there is nothing to wait for. Selection is the workflow's own deterministic policy over the recorded search result: lowest vlan first, cut at quantity.

Segments Manager All machine ops — the run is bounded, records not a single timer, and fails loudly.

The same run, in detail

Each card carries a phase — read live off a running workflow through a Temporal query. The progress payload also carries the per-segment report so far, so even a run that fails mid-loop shows exactly which segments were already converted.

get_valid_sites

phase validating-site

Strict first check: a typo'd site must fail loudly as UnknownSite, not complete as “matched 0 segments, shortfall N”. (Source == destination is rejected even earlier, by the request model — converting a segment to its own type is a no-op.)

GET/api/sites · public GET
2

list_convertible_segments

phase searching-segments

Every segment of the source type at the site whose status is Available — Allocated segments are in use (why that is the whole rule). Selection is the workflow's deterministic policy over that result: lowest vlan_id first, cut at quantity.

GET/api/segments?site=…&type=…&status=Available · all three filters server-side

Both halves of “convertible” are asserted on every hit, not trusted from the filter. A segment in any other status fails the activity, and so does an Available segment carrying a cluster_name — that combination is a Segments Manager invariant violation (allocation assigns the cluster and sets the status in one update), and converting it would re-type a segment a cluster is actually using.

Fewer matches than requested → convert all of them and report the shortfall. Zero matches → an empty report with shortfall == quantity, still a COMPLETED run.

3a

convert_segment_type

phase converting-segments

One Segments Manager update, and the entire operation: set the new type. The segment stays Available, so it is allocatable as its new type the moment the call returns — which is the point of converting it. The manager applies the same Available-and-unassigned guard server-side, so the two agree.

PUT/api/segments/type · Bearer · { segment, type, expected_type }

expected_type is a compare-and-set. Two conversions racing for the same segment (say HC→MCE and HC→PXE at one site) cannot both win: whoever converts first changes the stored type, and the loser's call answers 409 → SegmentConversionConflictError, failing that run loudly instead of silently hijacking the segment.

!

There is no step 3b any more

removed

This loop used to have a second half: start initialize-segment-<DEST>-<network> as a detached child workflow (ParentClosePolicy.ABANDON) for every converted segment. The new type had different firewall peers, so its connectivity had to be opened from scratch — and the converted segment sat Locked until a human approved those rules.

Every firewall between segments is open now, so there is nothing to re-open and nothing to wait for. The fan-out, the already_running item and the Locked status all went with it. A converted segment is simply Available under its new type.

✓

Done — the segments carry their new type

phase completed

The result lists every conversion — the segment and its vlan — plus matched and shortfall. Each converted segment is now Available under the destination type and can be picked up by allocate-segment immediately.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async. There is deliberately no bulk variant — the request is already batch-shaped.

POST /workflows/segment-lifecycle/convert-segment 202 · 409 if already running 
// request
{
  "site": "site1",
  "source_type": "HC",
  "destination_type": "MCE",
  "quantity": 3
}

// 202 response
{ "workflow_id": "convert-segment-site1-HC-to-MCE", "run_id": "…" }

The id carries site and both types. Two identical conversion requests racing would select the same segments, so they dedup onto one id (the second answers 409). Conversions differing in either type are legitimately concurrent — the expected_type compare-and-set arbitrates if they grab the same segment.

When things go wrong

Outages are out-waited. Real errors stop the run — cleanly.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so a Segments Manager outage never fails a run. Retrying stops only for classified errors — and a mid-loop stop always lands on a clean per-segment boundary.

Classified as permanent — these fail the run

  • UnknownSite — the site isn't in GET /api/sites
  • SegmentConversionConflictError — the Segments Manager answered 409: the segment became Allocated, or a concurrent conversion re-typed it first (expected_type mismatch)
  • SegmentNotFoundError — a selected segment vanished between search and convert
  • SegmentsManagerAuthError — bad SEGMENTS_MANAGER_API_TOKEN

Source == destination and quantity < 1 never reach the workflow — the request model rejects them with a 422.

A failed or cancelled run needs no compensation

Conversions already performed stand: each converted segment is Available under its new type, exactly where a freshly created one would be. Nothing pending is half-applied — the per-segment loop is sequential on purpose, so a conflict stops the run at a clean boundary.

Re-running is the recovery path

A re-run's search no longer matches the segments that were already converted (their type changed), so it picks up exactly the remainder. Naturally convergent — no bookkeeping needed.

Why Available and unassigned

An Allocated segment is in use by a cluster: re-typing it would change what that cluster is running on, underneath it. So the search asks the Segments Manager for Available segments only, and the manager applies the same guard server-side when the conversion itself arrives — belt and braces, because the two checks are seconds apart and a segment can be allocated in between.

The unassigned half is the interesting one. An Available segment carrying a cluster_name should be impossible — allocation sets the cluster and the status in one update — so finding one means an invariant has broken somewhere. The activity fails loudly rather than converting it, on the principle that a segment a cluster is actually using must never be re-typed just because a status field disagrees.

This rule used to cost more. A third status, Locked, once existed for segments whose firewall rules were not yet approved, and those were excluded too — because re-typing one meant cancelling its live initialize-segment run, and a Temporal cancel cannot tell you whether anything was actually running (it is accepted against an already-closed execution). Narrowing the selection removed that interaction rather than trying to detect it — a move worth remembering. With the firewall flow gone, no such segment exists any more.
