allocate-segment — what actually happens

A single request — a cluster name and the branch its values file lives on — reserves a VLAN segment for that hosted cluster in the Segments Manager, verifies the reservation landed, and writes the vlanId + dhcp_values block into the cluster's values file on that branch of the day1 repo. It runs as a step inside the day1 pipeline and ends at the push; the DHCP scope follows when a human merges the branch.

The same run, in detail

Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run an allocation currently is.

✓

Type check — HC only

phase pending

Runs before anything is touched. This workflow allocates HC segments only; any other type fails immediately with UnsupportedSegmentType. Without the gate a non-HC run would still die — only hostedCluster files are named <cluster>.yaml — but as a misleading ClusterFileNotFoundError. Future segment types get their own functions when they arrive. A run with no values_branch fails here too, as ValuesBranchMissing — the API requires one, and there is no configured fallback that would quietly push to main.

1

get_valid_sites + locate_cluster_file

phase resolving-site

There is deliberately no site input. The workflow shallow-clones the day1 values repo at the run's branch — a new cluster's file exists only there until the merge — and requires exactly one sites/<site>/**/<cluster>.yaml; the site is the path segment under sites/, cross-checked against the Segments Manager's site list. The repo layout is the source of truth — a caller can never claim a site the cluster does not live in.

GET/api/sites · the cross-check list
GITls-remote refs/heads/<values_branch> → clone --depth 1 --branch <values_branch> · fresh temp clone, always discarded

A branch the repo doesn't have → ValuesBranchNotFoundError (checked with ls-remote first, so a typo fails instead of retrying forever as a clone error); zero matches → ClusterFileNotFoundError; more than one → AmbiguousClusterFileError; a site the Segments Manager doesn't know → UnknownSite. All fail the run before anything is allocated.

2

allocate_segment

phase allocating-segment

Reserves a segment for the cluster at the derived site, as the requested type. Available segments carry no type, so the pool is shared: the Segments Manager hands out any Available segment at the site and stamps the type onto it in the same atomic update (a release clears it again). It is idempotent per (cluster, site, type): a repeat call — a Temporal retry, or a whole re-run — returns the existing allocation, so double-allocation is impossible by construction.

POST/api/segments/allocate · Bearer · → { vlan_id, segment, epg_name, … }

An empty pool (503) fails loudly as SegmentPoolExhaustedError — a drained pool is refilled by an operator creating segments, not by retrying every minute forever.

3

get_segment

phase verifying-allocation

Reads the allocated CIDR back and requires status == Allocated, the exact cluster name, the exact VLAN and the requested type (the allocation wrote it). Any mismatch is AllocationNotConfirmed — and because this sits before the git write, the values repo never records a VLAN the Segments Manager doesn't confirm.

The type is checked only when the read-back carries the field. A payload without the key predates it — history replayed from the previous brain, or a limb one rollout behind (CI ships the brain first) — and says nothing about the allocation. A reported null still fails.

GET/api/segments/by-segment?segment=… · public GET
4

append_allocation_to_cluster_values

phase updating-values-repo

Fresh clone of the run's branch, append the marker block (see below), commit with [skip ci], push to the same branch — never main. The marker matters: the day1 pipeline runs on every non-main push, so without it our push would start a second pipeline that re-runs the allocator. Safe to run twice: a marker block already recording this vlanId on this network is a no-op success (values_updated: false, nothing pushed) — the comparison is the allocation, not the block's text, so a cluster whose scope an operator tuned by hand keeps that edit through every re-run. A different allocation — another vlan or network, a marker block too mangled to read one out of, or a dhcp_values/vlanId key some human wrote without the marker — is a hard ClusterValuesConflictError, because a duplicate top-level YAML key silently discards the first block. A rejected non-fast-forward push simply retries from a fresh clone and converges.

GITclone → append → commit [skip ci] → push origin <values_branch> · token scrubbed from every error
⏸

After the run — not part of it

no phase

The pipeline that started the run waits for it to complete, generates the MachineConfig files from the recorded vlanId and finishes. A human then merges the branch to main; Argo CD (which reads main only) renders the Crossplane Request, and Crossplane creates the DHCP scope.

Why the run doesn't wait for the scope. It used to — a bounded read-only poll of the DHCP API. But the scope needs the merge, the merge comes after the pipeline, and the pipeline is waiting on this run: a deadlock, not a slow wait. So the run ends at the push. When a create-cluster workflow owns the merge, it will verify the scope after that step.

✓

Done

phase completed

The result carries the segment, VLAN, EPG, the branch the block landed on, and the commit sha (or null on a no-op re-run). This phase is reached as soon as the push succeeds.

What gets written

The block appended to <cluster>.yaml

One blank line always separates the file's last content line from the marker; an empty file gets the marker as its first line. Everything else the DHCP stack needs — leaseDurationDays, dns, subnetMask, failover — is inherited from the upstream values layers; scopeName derives from the file name.

YAML sites/<site>/mces/<mce>/hostedClusters/<cluster>.yaml 
description: "prep workers"
                                  <- blank line, always present
# === Added By Segment-Allocation Workflow ===
vlanId: 23                        // audit only — no chart reads it

dhcp_values:
  network: "10.20.90.0"           // mask stripped; no startRange/endRange — the DHCP API derives .1-.253
  exclusions:                     // ascending — required by the DHCP API
    - startAddress: "10.20.90.1"
      endAddress: "10.20.90.10"
    - startAddress: "10.20.90.241"
      endAddress: "10.20.90.254"

A type whose policy excludes nothing drops the exclusions key too — the block is then just vlanId + network, and the scope distributes the whole derived range.

⚠ The DHCP block assumes a /24 — asserted, not silent

DHCP_EXCLUSION_OCTET_RANGES (the ONE policy knob, keyed by segment type, e.g. {"HC":[[1,10],[241,254]]}) speaks in last-octet values, and the workflow writes nothing but the network and those exclusions: the DHCP API derives .1-.253 when both bounds are absent, and the exclusions carve the ends back out of it. A non-/24 segment is rejected with UnsupportedSegmentPrefix rather than mis-rendered with half its addresses stranded.

Supporting another mask is a deliberate refactor, not a config change — it must also start emitting subnetMask and gateway, since the DHCP stack derives the .254 gateway for a /24 only and rejects any other mask without both keys explicit.

⚠ HC segments only

Any other segment type is rejected up front with UnsupportedSegmentType — the values-repo layout only defines file locations (and therefore sites and DHCP scopes) for hosted clusters. Future types will arrive as their own functions, not as flags on this one.

Why one knob instead of three

Deriving the range from the exclusions removes the class of bug where the two contradict each other — and a mid-range exclusion like [100,110] still yields .11–.240 with a hole punched in it, exactly how DHCP scopes work.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async: the run outlives the request by design.

POST /workflows/segment-lifecycle/allocate-segment 202 · 409 if already running

The body names the cluster and the branch its values file lives on — the site is derived from the values repo, the segment is whatever the Segments Manager reserves. The branch is required: a body without one is a 422, as is an unknown field or a branch name git could misread (a leading -, .., whitespace).

// request
{
  "cluster":       "ocp4-prep-herzi-site1-a",
  "values_branch": "feature/ocp4-prep-herzi-site1-a", // required — the pipeline's $CI_COMMIT_BRANCH
  "type":          "HC"                                // optional — HC is the default and the only supported value
}

// 202 response
{ "workflow_id": "allocate-segment-HC-ocp4-prep-herzi-site1-a", "run_id": "…" }

The id carries the type on purpose. Allocation is scoped by (cluster, site, type) — one cluster can hold one segment per type at a site — so a type-less id would make two legitimate allocations collide. Re-triggering while a run is in flight answers 409. The branch is deliberately not in the id: the Segments Manager allocates per cluster whatever the branch, so two branches for one cluster must collide on one run.

GET /workflows/runs/{workflow_id} 200 · 404 if unknown id

Where it runs

A step inside the day1 pipeline

Until a create-cluster workflow exists, allocate-segment is called by the day1 values repo's GitLab pipeline, in place of its old in-house VLAN allocator. That pipeline runs on a temporary branch only, never on main — so the run takes the pipeline's branch and records the allocation there.

CI generate_mc_files · for each changed hostedClusters/<cluster>.yaml
  1. POST /workflows/segment-lifecycle/allocate-segment with {"cluster": "<file stem>", "values_branch": "$CI_COMMIT_BRANCH"}.
  2. 202 → poll GET /workflows/runs/{workflow_id} until COMPLETED; fail the job on FAILED, CANCELED or TERMINATED, printing error and the last progress.phase. 409 → a run is already in flight; its id is allocate-segment-HC-<cluster>, so poll that.
  3. git pull --ff-only origin "$CI_COMMIT_BRANCH" before generating the MachineConfig files, so the workspace carries the block and its vlanId.

Re-running the pipeline re-POSTs and converges (values_updated: false). The workflow's commit carries [skip ci], so it never triggers a pipeline of its own.

The later push-back job must expect our commit

The pipeline's own commit-and-push step checks out the commit the pipeline started from, overlays the edited cluster files from artifacts, then runs git pull — which refuses, because the workflow's commit touched the same file. Pull with --autostash, or git fetch + git reset --soft FETCH_HEAD before the git add.

One remote for both

The worker pushes to DAY1_REPO_URL; the pipeline pulls from its own origin. They must be the same repository, and that host must accept a token as the password with x-access-token as the user name. If they differ, the fix is the chart's config.day1RepoUrl, not code.

When things go wrong

Outages are out-waited. Real errors stop the run.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so a Segments Manager or git-remote outage never fails a run. Retrying stops only for errors explicitly classified as permanent.

Classified as permanent — these fail the run

  • UnsupportedSegmentType — not HC (workflow-raised, before anything runs)
  • ValuesBranchMissing — no values_branch on the run (only possible outside the API)
  • ValuesBranchNotFoundError — the values repo has no such branch
  • ClusterFileNotFoundError — no <cluster>.yaml in the values repo
  • AmbiguousClusterFileError — more than one <cluster>.yaml
  • UnknownSite — the file's site isn't in GET /api/sites
  • SegmentValidationError — the Segments Manager rejected the request (e.g. bad cluster name)
  • SegmentPoolExhaustedError — no Available segment at the site (the pool is shared by every type)
  • AllocationNotConfirmed — the read-back didn't match the allocation
  • ClusterValuesConflictError — the file already carries a different allocation
  • UnsupportedSegmentPrefix / InvalidSegmentCidr — the pool handed back a non-/24
  • SegmentsManagerAuthError · SegmentNotFoundError

Transient by classification

ValuesRepoGitError — any git failure other than a missing branch: an unreachable remote, a rejected non-fast-forward push (the retry re-clones and converges). It retries forever; an unclassified permanent error shows as a run stuck RUNNING in the Temporal UI — the fix is to classify it, not to add a deadline.

Nothing to clean up

On failure or cancellation there is deliberately no compensating cleanup: the allocation is kept — a re-run idempotently reclaims it and converges the git write.

Operating it

What happens if you run the same cluster again

Idempotency is a rule of the orchestrator — see the three rules that surprise people. Here it is unusually cheap: a full re-run converges with no human in the loop at all.

Re-run after completion — everything converges

The Segments Manager returns the same allocation (idempotent per cluster/site/type), the values file already records that vlan and network so nothing is pushed (values_updated: false, commit_sha: null). A pipeline re-run on the same branch is therefore safe. Anything an operator tuned inside the block stays as written — which also means a later change to the exclusion policy is never retrofitted onto an allocated cluster.

The one thing a re-run will not do

Fix a conflict. If the values file carries a different allocation — another vlan or network under the marker, or a hand-written top-level dhcp_values — every run refuses with ClusterValuesConflictError until a human reconciles the file. That is the point: the workflow must never guess which of two allocations is the real one.
