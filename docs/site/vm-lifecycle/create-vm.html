Temporal workflow · domain: vm-lifecycle

create-vm — what actually happens

One request creates one VirtualMachine for a KubeVirt InfraEnv, on the oldest KV cluster of the InfraEnv’s zone that has room for it under the placement buffer. The VM is created Halted, with a fixed MAC and the label kubevirt-redfish exposes it by, named ocp-<flavor>-kv<cpu>-<site>-<serial>. add-server-to-mce runs this workflow as its child for a KubeVirt InfraEnv and installs exactly the VM it made, through Ironic and the KV cluster’s kubevirt-redfish, like a physical machine.

A bare-metal InfraEnv has servers to draw. A KubeVirt one — named <flavor>-kv<cpu>-<zone>, say c200-kv32-az1 — has nothing until a VM of <cpu> vCPUs and <cpu> × 7.5 GiB exists. This run is that step. The zone’s clusters come from day1, their numbers from the clusters themselves, only one run at a time chooses in a zone, and the chosen cluster builds the VM. It never starts the VM (Ironic does, later), never creates a namespace, and writes nothing on the MCE.

TriggerPOST /workflows/vm-lifecycle/create-vm
Workflow idcreate-vm-<mce_cluster>_<infra_env>_<slot>
Workflow queuescreate-vm-workflow · kv-zone-lock-workflow
Activity queuescluster-lifecycle-activity (the day1 list) · vm-lifecycle-activity-<kv cluster> (one worker inside each KV cluster)

A KV cluster is a hosted cluster whose nodes run the warm-pool VMs. A vm-lifecycle-worker runs inside each one, acts on its own API server as its own ServiceAccount, and dials out to the hub’s Temporal. The KV cluster exposes nothing, and nothing on the hub holds a credential for it. A cluster that day1 lists but whose worker is not running is skipped as no-worker, never a failure.

Read this first

Names carry everything: flavor, size, zone, site, lifecycle

Nothing is looked up to decide what to create; the InfraEnv’s and the MCE’s names say it, and the API derives it once (the run carries the derived values and never re-derives them). Every name follows the platform naming convention (Idan-Maimon/kubevirt-workflows, docs/naming-convention.md).

What the names say

  • InfraEnv <flavor>-kv<cpu>-<zone> → the flavor (with its optional variant letter: c200, c200n), the vCPUs and the zone, which is az<N> (c200-kv32-az1 → c200, 32 vCPU, 240 GiB, zone az1). Memory is vCPUs × 7.5 GiB, so the vCPU count is even; an odd size is a 422. The ratio is this repo’s (shared/infraenv_names.py): the naming convention names a size by its vCPUs only. No site: an InfraEnv belongs to one MCE, and so to its site. A -mtl- InfraEnv is bare metal and is refused: it takes servers, not VMs.
  • MCE ocp4-<lifecycle>-mce-<site>-<id> → the site (a VM boots on its own site’s inventory network) and the lifecycle (ocp4-prod-mce-five-a → site five, lifecycle prod).
  • (lifecycle, site, zone) → the zone’s seeds of that lifecycle, ocp4-<lifecycle>-seed-<site>-<zone>-<id> (a zone may have several), whose day1 folders list the zone’s KV clusters, ocp4-<lifecycle>-kv-<site>-<zone>-<id>. A prod MCE’s VMs go on prod KV clusters only. The id letter is given in creation order, so sorting by it is oldest first.
  • VM ocp-<flavor>-kv<cpu>-<site>-<serial> (ocp-c200-kv32-five-k7q2m9xd): 8 random lowercase letters and digits, also the VM’s SMBIOS serial, as a bare-metal node’s name carries its serial. The zone is a label, never in the name. (Until 2026-11-25 the convention’s name carried the full MAC; the change is still to be raised with the convention’s owner.)

What it never does

  • It never starts the VM: it is created runStrategy: Halted, and kubevirt-redfish powers it on when Ironic asks.
  • It never chooses a node: when the VM is started, the Kubernetes scheduler does.
  • It never moves a create to another cluster: the create on the chosen cluster is out-waited there.
  • It never overbooks a cluster when requests arrive together: runs of one zone choose and create one after another, under the zone’s lock.
  • It never leaves a VM behind when it does not complete: the root disk never binding, a wait that fails for good, or a cancel — the run removes its own VM first.
  • It never creates a namespace and never touches the MCE. A VM’s MAC is kept unique on its cluster by KubeMacPool, which every KV cluster must run.

Nothing is remembered between runs: a VM created a moment ago is a stopped VM on its cluster, and stopped VMs are counted in that cluster’s own figures.

Six phases, a seventh only when the run will not complete

What the run does

Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run it currently is. A run that has not started its first step reports pending.

1

list_kv_clusters

phase listing-kv-clusters

The zone’s KV clusters are the files of its seeds’ day1 folders at main, the seeds of the MCE’s lifecycle: sites/<site>/mces/ocp4-<lifecycle>-seed-<site>-<zone>-<id>/hostedClusters/. The cluster-lifecycle worker on the hub reads it (it holds the day1 token; the worker inside a KV cluster holds none) and answers the clusters oldest first, the commit they were read at, and the placement buffer the run must use. It happens before the lock, so the locked part stays short.

gitls-remote main every time · a clone only when main moved (the snapshot cached by commit) · DAY1_REPO_URL, read only

A file is usable only when day1 confirms it for this zone: every one of its NodePools labels its nodes topology.kubernetes.io/zone with the seed’s zone, and its name is ocp4-<lifecycle>-kv-<site>-<zone>-<id> with the seed’s site, zone and lifecycle. Any other file is a day1-problem row in the table and is never read. Only the files under the seed folders are KV clusters: the seeds sit beside the MCEs in mces/, and a file under any other folder there (an MCE’s) is not one, even one whose name mentions kubevirt. No usable cluster fails the run with NoKvClusterError, naming the folder, the commit and the files that had a problem. A new cluster file is seen by the first run after its commit lands.

2

the zone’s lock

phase awaiting-zone-lock

The run asks the zone’s lock — one long-lived kv-zone-lock workflow per (site, zone), described below — and waits for its grant. It starts the lock workflow with itself as the first waiter or, when the lock already runs, signals it. While it waits it asks again every 2 minutes (the lock keeps a run in its line once, however often it asks), so a lock workflow someone terminated is started afresh by the next ask.

signalrequest_lock → kv-zone-lock-<site>-<zone> · lock_granted {lease_id, lease_ends_at} ←

Bounded at 30 minutes. Then the run takes itself out of the line (withdraw) and fails with KvZoneLockTimeoutError; nothing was created. Runs of different zones never wait for each other.

3

read_kv_cluster_figures

phase choosing-kv-cluster

While it holds the lock, the run asks one cluster at a time, oldest first, for its current figures — on that cluster’s own queue, vm-lifecycle-activity-<kv cluster>, so Temporal delivers the question to the worker running inside that cluster — applies the fit rule, and stops at the first cluster that fits. The clusters after it are not read (not_read names them).

readnodes · unfinished pods · labelled VirtualMachines · VirtualMachineInstances · the worker’s own cluster, four list calls at once, cut off together at 20 s

A cluster that cannot answer is a row with a reason, never a failure and never a retry while the zone is held: nothing picked the read up within 30 s → no-worker; the worker could not read its cluster’s API, or is deployed under another name → unreachable; whatever else keeps the read from answering within 2 minutes → unreachable. No cluster fitting: the lock is released and the run fails with NoKvClusterFitsError, the table summarised per reason. Nothing was created.

4

create_vm_on_cluster

phase creating-vm

The run sends the chosen cluster’s worker what the VM is: flavor, vCPUs, memory, site, zone, MCE, namespace, this run’s id, and create_before: 90 seconds from now, or the end of the lease less 45 seconds if sooner. The worker builds the VM: it draws a serial, derives the name, assembles the VirtualMachine with no MAC and creates it Halted; KubeMacPool assigns the MAC. A taken name is drawn again by the worker, at most 3 draws, with no round trip to the hub.

createVirtualMachine · kubevirt.io/v1, runStrategy Halted, a blank root DataVolume, one interface with the fixed MAC

Idempotent by the run’s id: a retried attempt first looks for a VM labelled with it and returns that one (created: false). Nothing is created after create_before (VmLeaseExpiredError). Up to then the create is out-waited on this cluster — no schedule-to-start limit, so a worker that restarts inside the 90 seconds is waited for.

a cluster that fails the create is LEFT, not the run

phase checking-kv-cluster

When the create keeps failing to its deadline (the cluster’s API down, its worker gone) or is refused for good (the namespace missing, a 403, every MAC taken, a 400/422), the run does not fail: the cluster becomes a create-failed row and the run goes on to the next cluster (the operator, 2026-11-24). First it makes sure it leaves no VM behind there:

  1. The fence. It waits until 45 seconds after the create was over (its deadline, or the refusal). After that nothing of the run can still land on that cluster.
  2. The check. It sends the same create with a deadline that has already passed: the worker answers with the run’s VM if one is there, and can create nothing.
  3. A VM is there: the create landed after all, so the run keeps it and goes on with it. None is there: the cluster is clean, and the run moves on.
  4. No answer within a minute (the cluster is dark): nobody can know. The run moves on all the same and starts the child delete-stray-vm (delete-stray-vm-<cluster>-<run id>), which deletes every VM labelled with the run’s id on that cluster once it answers, however long that takes. Until then the run’s VM may exist there too — Halted, used by nobody, counted against that cluster — and the run’s result lists the cleanup in stray_cleanups.

A cluster whose API is down costs a run about 3¼ minutes (90 s + 45 s + 1 min). Only when every cluster has failed or does not fit does the run fail, NoKvClusterFitsError, each row saying why.

5

release

phase releasing-zone-lock

As soon as the VM object exists the run gives the lock back — and on every other path out of steps 3 and 4: nothing fits, a create that fails, a cancel. The next run’s figures already count this VM, as a stopped VM.

signalrelease {lease_id} → kv-zone-lock-<site>-<zone>

The lock is held for the figures of the clusters tried plus one create: a few seconds when every worker answers. The 10-minute disk wait below happens after the release, in parallel with every other run.

6

await_vm_ready

phase awaiting-root-disk

ONE heartbeating activity on the chosen cluster’s worker polls the VM every 8 s until its root disk’s DataVolume is Succeeded with its PVC bound and KubeVirt has admitted the VM. Its clock lives in the heartbeat, so a retry on a restarted worker resumes it rather than starting over.

readVirtualMachine · its root DataVolume · its PersistentVolumeClaim · every 8 s, a heartbeat each poll

Bounded at 10 minutes on the activity’s own clock. The VM vanishing meanwhile fails the run with VmDisappearedError (someone else deleted it; creating it again would be a second VM under a name the run no longer owns).

7

delete_vm_on_cluster

phase removing-vm · only when the run will not complete

No bound root disk after 10 minutes: the run deletes its own VM and its DataVolume — the VM labelled with this run’s id, and only while it is still the object the worker read (a delete by UID) — then fails with VmRootDiskNotBoundError quoting the last state seen. The same removal runs when the wait fails for good, and when the run is cancelled.

deleteVirtualMachine (by UID) · its root DataVolume · nothing there is success

Why delete rather than leave it: a re-run of the slot is a new execution with a new MAC. It cannot converge on the orphan; it would add one VM per attempt, and a stopped orphan is counted against its cluster for ever. The usual cause is a WaitForFirstConsumer storage class, which never binds a Halted VM’s disk: the cluster’s VM storage class must bind Immediately and allow a ReadWriteMany + Filesystem volume. A VM of that name carrying another run’s id or another MAC is someone else’s: the run leaves it and fails with VmIdentityConflictError.

✓

Result

phase completed

The VM’s vm_name and mac, its namespace, flavor and size, the kv_cluster it is on, the per-cluster table (every cluster the run judged, with its figures and its skip reason) and not_read, the buffer_percent and day1_revision the run decided with, draws, leases, root_disk_phase, and the request echoed back. The VM is Halted. Started by add-server-to-mce, that run now installs it: the name, the MAC and the KV cluster are all it needs (the Redfish host is a pattern on the MCE’s worker), and it keeps this run’s run id — the VM’s redbull.io/created-by label — to delete the VM if the install does not end with an Agent. Started from this route, nothing installs it.

kv-zone-lock · an internal workflow, no route

Why the zone is locked, and for how long

Each run reads the clusters’ figures and picks one. Ten runs reading at the same moment all see the same empty cluster and all pick it, even if it has room for two. So only the run holding the zone’s lock may read figures and choose, and it keeps the lock until its VM object exists.

What the lock workflow is

  • One per (site, zone): KvZoneLockWorkflow, id kv-zone-lock-<site>-<zone>, on its own queue kv-zone-lock-workflow in the brain. Long-lived; it never completes on its own.
  • It holds only the line of runs waiting and the lease in force. It never reads a cluster, never chooses, and calls no activity — so no limb can stall a zone’s lock.
  • No route starts it: the first create-vm run of a zone starts it as an abandoned child, every later one signals it. It outlives the run that started it, and a cancel of that run does not cancel it.
  • Its history stays bounded: it continues as new every 250 grants, or when the server suggests it, carrying the line and the lease. A signal arriving during the continue is not lost; every signal is sent to the workflow id, so it reaches the continued run.
  • Its progress query: the line, the holder, the lease’s end, and the counts of grants, leases that ran out (expired) and waiters found gone (skipped). Read it with GET /workflows/runs/kv-zone-lock-<site>-<zone>.

The rules it keeps

  • Arrival order, one holder at a time. A release passes the lock on at once.
  • The lease is 5 minutes. A holder that died or hangs never releases; when its lease ends the lock passes on, and its late release — it carries the old lease id — is ignored.
  • A run is known by its run id, not only its workflow id: a slot’s id is reused by later runs, and a grant is signalled to exactly the run that asked.
  • A waiter that is gone costs nothing. Signalling a closed run fails; the grant is skipped and the next run granted in the same workflow task, so a terminated waiter never costs the zone a lease.
  • A run that gives up (its 30-minute bound, a cancel) takes itself out of the line; a withdraw from the holder frees the lease. A grant a run is not waiting for is given straight back.

If a person terminates the lock workflow, nothing is lost that matters: the next ask starts a new one (waiting runs ask again within 2 minutes), and it needs no memory — the clusters’ own figures are the state.

The lease also bounds the run. The run never acts on figures once its lease is spent: before every read, and before the create, it checks the clock. A spent lease is given up and the lock asked for again; the scan carries on from the cluster it had reached and reads that one afresh. At most 3 leases per run, then KvZoneLeaseExpiredError. Only a zone where many clusters have no worker gets there: each costs 30 s, so ten of them are a whole lease.

The cost. Runs of one zone choose and create one after another. With several requests at once, a run waits behind the ones ahead of it, each a few seconds.

Placement

The capacity calculation: the cluster measures, the run decides

Each worker only knows its own cluster and only measures; “the oldest cluster that fits” can only be decided by whoever sees them all, the run, while it holds the zone’s lock. And the buffer is one value for every cluster, so it is applied in one place.

How big a VM is, in the scheduler’s terms

Capacity is measured by what the VM’s launcher pod requests, never in vCPUs: CPU vCPUs × 15 / 16 cores rounded down, at least one; memory the guest’s plus KubeVirt’s own overhead, counted as 300 MiB + 8 MiB × vCPUs + guest memory ÷ 512 — what KubeVirt adds to the launcher pod’s request (page tables, per-vCPU state, its own processes), measured on four VMs and rounded up by a few MiB, so it is never under what the pod asks for. Both sides use the one definition (shared/vm_requests.py): the worker for the stopped VMs, the run for the new one.

Why 7.5 GiB per vCPU and not 8. Every KV node has 8 GiB of RAM per core, and a node gives VMs less than its RAM: the kernel’s own share (about 1.6%), the kubelet reserve, the node’s own pods and each VM’s overhead. At 8 GiB per vCPU a VM had exactly the node’s ratio, so the last VM a node’s CPUs allowed never fitted on memory: a 128-core, 1,024 GiB node took 7 kv16, 3 kv32 or 1 kv64 where its CPUs allow 8, 4 and 2. At 7.5 it takes 8, 4 and 2. A 192-core, 1,536 GiB node takes 12, 6 and 3. Computed for those two node types: another node type needs the design’s table (docs/design/create-vm-placement.md §6.1.1) recomputed before it joins a KV cluster — at some sizes (64, 184, 200, 216, 232 CPUs) 7.5 still leaves a size one VM short.

What the worker reports — KvClusterFigures

figurehow
usable nodesThe nodes a VM’s launcher pod could be scheduled to: Ready, not cordoned, carrying no NoSchedule/NoExecute taint, and matching the VM template’s node selector when the cluster has one. Nothing else counts, on either side of the fraction.
allocatableThe sum of allocatable CPU and memory over the usable nodes.

These VMs have no pod yet, but kubevirt-redfish will start them, so their room is taken. This is how a VM created a moment ago is counted.

Every number is an integer, in millicores and bytes: nothing on the hub parses a Kubernetes quantity string. A worker asked for another cluster than its own, or one that could not read its API in time, answers readable: false with why — a value, never an exception, so the run neither retries it nor holds the lock while it does.

The fit rule, and why a cluster is skipped

A VM fits when all hold; the first that does not is the reason. The arithmetic is in integers, so the decision is exact: (requested + VM) × 100 ≤ allocatable × (100 − buffer).

reasonmeaning
day1-problemday1 lists the file with a problem (its NodePools name another zone, or none; a name outside the convention). Never read at all.
no-workerNothing polled the cluster’s queue within 30 seconds: its worker is not deployed, is down, or is deployed under another name.
unreachableThe worker answered but could not read its cluster in time, answered for another cluster, or gave no figures within 2 minutes.
no-nodesThe cluster has no usable node.
fit-nodeNo single node has room for the VM’s CPU and memory.
fit-bufferRequested plus the VM would pass 1 − buffer of the allocatable, on CPU or on memory.

The buffer is ONE value for every KV cluster, 15% by default: HEADROOM_BUFFER_PERCENT of the cluster-lifecycle-worker on the hub, handed to the run with the zone’s cluster list, so each run records the buffer it used and a changed value applies to the runs started after it. It applies to the whole cluster, never to one node: nodes may fill completely; the free share is the room live migration needs when a node is drained. Memory is checked as well as CPU — a VM asks for about 8 GiB per requested core, close to what a node of 8 GiB per core gives its VMs, so either can run out first.

Ten 32-vCPU VMs requested at once over two clusters of 100 cores each, with the 15% buffer (85 cores each): the runs take the lock one after another and each sees the VMs before it — -a, -a (60 cores), then -b, -b, then six runs fail with NoKvClusterFitsError. Never 90 on either.

The VM

Its MAC, its name, and who builds it

The chosen cluster’s worker builds the VM. The run sends only what the VM is; the MAC comes from KubeMacPool’s range on the cluster, and the VM template’s values (storage class, network, node selector, root disk size) are in the worker’s ConfigMap.

The serial is the worker’s, the MAC is KubeMacPool’s

  • The worker draws the serial: 8 characters of a-z0-9, uniform, from the system’s randomness — 2.8 trillion values. A name any VM of the cluster has, in any namespace, is drawn again; across a site’s clusters a clash is left to chance (about 1 in 55,000 for 10,000 VMs of one flavor and size at one site) and would fail add-server-to-mce on its existing BareMetalHost, loudly.
  • The VM is created with no MAC: KubeMacPool assigns one at admission, unique on the cluster and fixed across restarts (the operator, 2026-11-25). The worker reads it back for the BareMetalHost. It never requests one: KubeMacPool does not refuse a duplicate requested MAC (tested on cluster-qcl8n), it keeps unique only the MACs it assigns.
  • So every KV cluster must run KubeMacPool (OpenShift Virtualization does by default), and the VM namespace must not be labelled mutatevirtualmachines.kubemacpool.io=ignore. A VM that comes back without a MAC is deleted and the create fails (VmMacNotAssignedError).
  • Each cluster’s MAC range is to be set in its HyperConverged object (spec.networking.kubeMacPoolConfiguration), later and apart from this workflow. Until then each cluster keeps the random 02:xx:xx range KubeMacPool picked, and two clusters can share one.

How the worker creates it

  1. Has this run already created its VM? A VM labelled with the run’s id is returned and nothing is drawn. Checked first, so a retry finds it whatever the time. Should there be more than one, the oldest is kept and the rest deleted.
  2. Is the lease over? Past create_before nothing is created.
  3. Draw a serial; build the name from it. A name some VM of the cluster has is drawn again.
  4. Create the VM Halted, with no MAC. A name that exists is one more draw.
  5. At most 3 draws, then VmSerialExhaustedError.
  6. Read back: the VMs carrying the run’s id are listed again; the run must hold exactly one, with the MAC KubeMacPool gave it, before its name is recorded.

One attempt starts no call to the cluster’s API after 55 s, so it is over inside the activity’s 90 s and two attempts of one create never run side by side.

When it stops

Classified errors fail the run; everything else is out-waited

Every error below is a FAILED run on the status endpoint, never a 4xx on the trigger, and fails after one attempt — a retry would get the same answer. The lock is released first on every one of them.

Raised by the workflow itself

errorwhen
NoKvClusterErrorlisting-kv-clusters: the zone’s seed folders of the MCE’s lifecycle list no usable KV cluster. The message names the folder, the day1 commit and every file listed with a problem. Also a site or zone the convention does not know, for a run started around the API. Nothing was read from or written to any cluster.
Day1QueryInvalidErrorlisting-kv-clusters: a run that carries no lifecycle — one started before the lifecycle filter (2026-11-22). Refused rather than guessed: a prod MCE’s VM must not land on a test KV cluster. Start it again. Nothing was created.
KvZoneLockTimeoutErrorawaiting-zone-lock: the lock was not granted within 30 minutes. The run left the line first. Nothing was created.
NoKvClusterFitsErrorchoosing-kv-cluster: no cluster takes the VM under the buffer. The message names the VM’s size in request terms, the buffer, and the clusters grouped by reason. Nothing was created.
KvZoneLeaseExpiredErrorchoosing-kv-cluster: 3 leases ran out while the run was still reading clusters — a zone with many clusters without a worker. The message names them. Nothing was created; bring those workers back, then ask again.
VmRootDiskNotBoundErrorremoving-vm: the root disk did not bind within 10 min; the VM was deleted again. Check the storage class binds Immediately and allows RWX + Filesystem, then the DataVolume and the CDI log on that cluster.

Raised by the worker inside the KV cluster, non-retryable

On the create none of these fails the run any more: the cluster becomes a create-failed row carrying the error, and the run moves on to the next cluster (above). On the disk wait and the delete they fail it as before.

errorwhen
VmSerialExhaustedErrorcreating-vm: three serials drawn, each naming a VM that exists. Out of 2.8 trillion that means something else names VMs this way. Nothing was created.
VmMacNotAssignedErrorcreating-vm: the VM came back without a MAC, or KubeMacPool refused to give one — KubeMacPool is not installed, or the VM namespace is labelled mutatevirtualmachines.kubemacpool.io=ignore. The VM was deleted; the run leaves the cluster for the next.
VmLeaseExpiredErrorcreating-vm: the create reached the worker after create_before (the worker was restarting, its API was slow). Nothing was created; ask again.
VmNamespaceNotFoundErrorThe VM’s namespace does not exist on the chosen cluster. The platform creates chassis namespaces; this run never does.
VmRequestRejectedErrorThe cluster’s API server or an admission webhook refused the VirtualMachine (400/422), or the request cannot name a VM. The API’s own sentence is carried, bounded.
KvClusterAccessErrorThe cluster’s API refused the worker’s ServiceAccount (403): the chart’s ClusterRole is missing a verb. On the figures read this is an unreachable row instead.
KvClusterMismatchErrorThe worker was asked to act for another KV cluster, or another site or zone, than its own: its kvCluster value is not the day1 file name its queue was built from.
VmDisappearedErrorawaiting-root-disk: the VM is gone before its disk bound. Something else deleted it.
VmIdentityConflictErrorOn the delete only: the VM under that name carries another run’s id or another MAC, so the run leaves it.

Everything else is retried without bound, backing off from 1 s to at most 1 min between attempts: the day1 repo unreachable or without main (ValuesRepoGitError, ValuesBranchNotFoundError), and the chosen cluster’s own API failing during the create, the wait or the delete (KvClusterApiError: 5xx, 401, 429, a timeout, a dropped connection). The run stays RUNNING in its phase and the failure shows on the activity in the Temporal UI — except the create, which is retried to its own 90-second deadline and then leaves the cluster for the next.

The day1 read carries a 5-minute schedule-to-start timeout: with no cluster-lifecycle-worker polling, it fails the run saying so, before anything exists. The figures read carries its 30 s pick-up bound and a 2-minute bound as a whole, both answered as a row. The create, the disk wait and the removal carry no schedule-to-start timeout on purpose — Temporal never retries that timeout, and a worker pod away for five minutes after the create must not fail the run, or its rollback, and leave the VM behind. Those wait for a worker, visible as a pending activity.

Stopping a run

A run that does not complete leaves no VM

The caller learns the VM’s name only from a completed run. So a run that ends any other way removes what it created, or says exactly where it is.

how it endswhat is left
a failure before the createNothing: no cluster was written. The lock was released, or never asked for.
the root disk does not bind in 10 minNothing: the VM and its DataVolume are deleted (removing-vm), then VmRootDiskNotBoundError.
the disk wait fails for good (403, a mismatch)The run removes its VM, bounded at 10 minutes, then fails with the wait’s own error. If the removal fails too, the VM is still there; find it by its label (below).
a CANCEL while waiting for the lockNothing: the run leaves the line and ends CANCELED.
a CANCEL while choosingNothing: the lock is released at once; nothing was sent to a cluster.
a CANCEL during the createThe lock is released at once. A cancel stops waiting for the create, not the create itself, so the run waits 2 minutes for the call to settle, then deletes the VM labelled with its run id — whether or not it ever learned the name — and ends CANCELED.
a CANCEL during the disk waitThe VM is deleted at once; the run ends CANCELED.
a CANCEL whose removal cannot runThe removal is given up after 10 minutes (the cluster’s worker is away) and the run still ends CANCELED; progress.cancel_rollback says the VM could not be removed and names its label.
the brain restarting (a rollout, a crash)Nothing is undone and nothing is lost: the run is still open on the server and the next brain pod replays it from its history and carries on — in the line, under its lease, or in the disk wait. A run the old pod simply dropped does nothing on its way out of memory (it gives no lease back and rolls nothing back from there): only a cancel asked of that run, or its own failure, does. If its lease ends while no brain serves it, the lock passes on and the run asks for another.
TERMINATENo code runs. A lock it held passes on when its lease ends. A VM it created stays: find it with oc get vm -A -l redbull.io/created-by=<run id> on the cluster in progress.kv_cluster, and delete it.

progress.cancel_rollback says in words what a cancel undid. A completed run keeps its VM: a cancel of a closed run does nothing.

Running it twice

A re-run is a new VM; a retry is the same one

Temporal retries activities and operators re-POST things. The two are different here, on purpose.

Inside one run: idempotent by the run’s id

The create carries the run’s id, and the VM is labelled with it. Retried after a lost answer, the worker finds that VM and returns it: created: false in the result, nothing duplicated. If a create the API server finished after its caller had given up left two, whichever attempt meets them keeps the oldest and deletes the rest. The delete finds the VM by the same label, so a retried delete finds nothing — success. The ready wait resumes its clock from its last heartbeat. The figures read writes nothing.

Across runs: a slot, and a fresh draw

The id is create-vm-<mce>_<infra_env>_<slot>. Asking again while a run is in flight fills the next free slot — it is asking for one more VM, so it is never a 409 (only when all 100 slots are busy). A finished slot is free again, and a second run on it is a new run id: it creates a second VM and never returns the first. Which is why a run that does not complete leaves nothing behind: there would be no way back to it.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async: the POST hands back the workflow id at once and you poll it. The API has no auth of its own — anyone who can reach it can start a run.

POST /workflows/vm-lifecycle/create-vm 202 · 409 only when all 100 slots are busy · 502 when Temporal refuses

Two fields are required: the MCE and the InfraEnv. namespace defaults to inventory; count asks for several VMs. mce_cluster is accepted with or without its ocp4- prefix and must be named ocp4-<lifecycle>-mce-<site>-<id> (its site and lifecycle are the VM’s); infra_env must be a KubeVirt InfraEnv of the convention, <flavor>-kv<cpu>-<zone>.

GET /workflows/runs/{workflow_id} 200

Putting a KV cluster into placement, and the deploy order

All of it happens when the KV cluster is created; nothing is set on the hub per cluster.

  1. Its day1 file, in its zone’s seed folder (sites/<site>/mces/ocp4-<lifecycle>-seed-<site>-<zone>-<id>/hostedClusters/), named ocp4-<lifecycle>-kv-<site>-<zone>-<id>, every NodePool labelling its nodes topology.kubernetes.io/zone with that zone.
  2. The vm-lifecycle-worker chart on the cluster, through day2: kvCluster = the day1 file name, the Temporal host and CA, the storage class, the network. No MAC value: the MAC comes from the cluster’s KubeMacPool.
  3. The VM namespace existing there as a kubevirt-redfish chassis namespace.

Order for the code: the brain first (it holds both workflows), then the cluster-lifecycle-worker (the listing activity; its HEADROOM_BUFFER_PERCENT has a default, so the chart need not ship the key first), then the chart sync and the vm-lifecycle-worker image. A run of the workflow before this design cannot be replayed by this one: terminate any such run first (none could succeed — its agents were never deployed). The two agents (kv-capacity, kv-vm-api), their Routes and tokens, and the hub vm-lifecycle-worker are gone.

Known limits

  • Memory is vCPUs × 7.5 GiB (since 2026-11-24; it was × 8). The InfraEnv name carries the vCPUs only. Computed for KV nodes of 8 GiB per core with 128 and 192 CPUs; another node type needs the table recomputed first.
  • Halted VMs are on no node, so the one-node check cannot see them: a buffer can admit VMs that then fail to start.
  • A worker that is down slows the whole zone by 30 seconds per run until it is back. Nine or more dead workers ahead of a live cluster cost a run a second lease; thirty, the run (KvZoneLeaseExpiredError).
  • A create held up past the lease fails the run, with nothing created; the caller asks again.
  • Clock skew. The worker stops creating 45 s before the lock moves on: 25 s for one API call in flight, 20 s for the hub’s and the KV cluster’s clocks to disagree. Beyond that a VM could land after the next run measured the cluster.
  • A workflow RESET to before the create is a new run id: it creates a second VM and the first stays. Delete the first by its redbull.io/created-by label.
  • A VLAN freed by a deleted KV cluster can be given to a new one, which then gets the old prefix. That is safe only once the old cluster’s VMs, BareMetalHosts and Agents are gone.
  • The day1 seed folders do not exist yet. Until a zone has one, every run for it fails with NoKvClusterError.
  • Which namespace the VMs go in is not settled (inventory here; the kubevirt-redfish facade exposes server-scan-vms). Capacity is right either way: stopped VMs are counted in every namespace.
  • Making the VM installable is not this run’s: it is add-server-to-mce’s KubeVirt branch (since 2026-11-25), which starts this workflow as its child (create-vm-for-<its id>, cancelled with its parent, REQUEST_CANCEL). A VM made from this page’s own route has no install path yet.
