delete-vm — what actually happens

One run deletes one VirtualMachine, by name, from its KV cluster — a VM create-vm made — and completes only when nothing of it is left in Kubernetes, its PersistentVolumes included. “The PersistentVolume object is gone” is how it knows the volume left the storage array: it calls no storage system.

Without it a VM whose host left the MCE stays Halted on its KV cluster for ever: counted against that cluster’s capacity by every create-vm run, its disks in the array. When the storage cannot be proven clean — a Retain volume, a snapshot, a volume still there at the deadline — the run deletes everything it may and then FAILS, naming each volume. It is never a success with a note.

Triggernone — a child workflow (remove-server-from-mce is to start it)
Workflow iddelete-vm-<kv cluster>_<vm name>
Workflow queuedelete-vm-workflow
Activity queuevm-lifecycle-activity-<kv cluster> (the worker inside that KV cluster)

It has no route on purpose (decided 2026-11-26). delete-vm holds no credential for an MCE, so it cannot check that the VM’s BareMetalHost is gone — and metal3 needs the VM’s Redfish to release a host. remove-server-from-mce stays the one public way to remove a VM, and is to start this run as its child once the host is gone; that integration is a later change. Until then nothing starts delete-vm but a person with the Temporal CLI.

Three steps and a verdict

What the run does

Every call goes to the KV cluster’s own worker, which acts on its own API server as its own ServiceAccount. Each card carries a phase, read live through the progress query (GET /workflows/runs/{workflow_id}).

1

inspect_vm_for_deletion

phase inspecting

Is it the VM asked for? A VirtualMachine of that name must be one create-vm made, for the caller’s MCE: it carries redbull.io/created-by (a hand-made VM is never deleted) and redbull.io/mce equal to the request’s; the run id and the MAC must match too when the caller gives them, and a redbull.io/kv-cluster label must name this cluster. Otherwise the run fails VmIdentityConflictError with nothing touched.

What is there? The VM (and whether a guest is running), its DataVolumes, its claims, the PersistentVolumes behind them — each with its reclaim policy, CSI driver and volume handle — VolumeSnapshots of them, and the pods mounting them. All of it is recorded in the run’s history. Nothing of the VM anywhere: the run COMPLETES, found: false.

Observe-only. The one call with a schedule-to-start limit (5 min): nothing is written yet, so a KV cluster with no worker fails the run here (KvClusterWorkerAbsentError, naming the queue).

2

delete_vm_and_volumes

phase deleting

Everything is read again and the identity checked again, then deleted in this order: the VirtualMachine (by the UID read), its DataVolumes, each claim’s CDI VolumeImportSource, every claim of the VM (each by its UID). An object already gone is success, so a retry deletes what is left.

A RUNNING VM is deleted too, and the result says so (was_running). It is abnormal — after metal3 released the host the VM is Halted — but the worker has no verb to stop a VM, the caller has already proved the host left the MCE, and refusing would leave a powered-on VM nobody owns. KubeVirt shuts the guest down as part of the delete.

Never deleted by the run: a PersistentVolume (deleting a Retain one loses the only pointer to its volume in the array), a VolumeSnapshot (someone’s backup), a pod (a pod holding a claim is named in the failure), and a claim that only looks like the VM’s (below).

3

await_vm_gone

phase awaiting-release

ONE heartbeating activity polls every 8 s until the VirtualMachine, the DataVolumes, the claims and the PersistentVolumes are all gone. It answers done; left when only Retain volumes remain (they never go, so it does not wait for them); or deadline after 15 minutes, naming every object left, its finalizers and the pods holding it.

What it watches is the run’s own record, handed over in the request: a volume is found through its claim, so once the claim is gone only that record still names it — an attempt started after the claims went would otherwise report the VM gone over a volume still there.

The 15 minutes count only the time the cluster was seen — the seconds between two polls that both answered, kept in the heartbeat details. An outage of the cluster’s API, or a worker that was away, adds nothing: a cluster that comes back after twenty minutes gets its whole deadline to finish what it was doing.

4

The verdict

phase completed or failed

Completed: nothing is left and no snapshot of the VM’s disks stands. The result lists the PersistentVolumes that went with the VM, each with its CSI driver and volume handle — the record of what left the array.

Failed, after the deletes — VmVolumesLeftInStorageError when the storage is not provably clean, VmDeletionTimeoutError when the VM, a DataVolume or a claim is still there. Both below.

One rule, used by all three activities

Which volumes are the VM’s

A VM’s storage outlives the VirtualMachine object in several ways, so the rule must still find it once the VM — and then its claims — are gone.

rulea claim of the VM’s namespace is the VM’s when…
specthe VirtualMachine names it: dataVolumeTemplates, volumes[].dataVolume, volumes[].persistentVolumeClaim
root-diskits name is <vm>-root (what create-vm’s VM is built with)
boot-isoits name is kubevirt-redfish’s boot ISO claim, <vm>-bootiso-<unix seconds>-<6 digits> (or its fallback <vm>-bootiso). kubevirt-redfish deletes that claim on eject — which metal3 does while releasing the host — so it is a leftover only when that did not happen
labelit carries kubevirt-redfish’s own label vm.redfish: <vm> (set when the ISO is filled through CDI)
ownedan owner reference names the VirtualMachine, another of the VM’s claims or one of its DataVolumes (CDI’s prime-… claim)
cut-namea look-alike, reported and NEVER deleted. kubevirt-redfish cuts any name over 63 characters to its first 49 plus a hash and truncated. While the VM’s name is at most 40 characters the cut still holds all of <vm>-bootiso- and the claim is a boot-iso; past that, the cut name no longer says whose it is (two long names differing in their last characters cut to the same 49). Such a claim is the VM’s only by one of the rules above; alone, it is left and fails the run. Today’s VM names are about 27 characters.

A PersistentVolume is the VM’s when one of those claims is bound to it, or its claimRef names one of them — or names a claim the name rules recognise, which is how a re-run finds a volume after the VM and its claims are gone. A VolumeSnapshot is the VM’s when its source claim is, by the same two ways. A CDI VolumeImportSource is read from the claim’s dataSourceRef, never built from a name, and deleted before its claim: its name is only on the claim.

When it stops

Delete, then fail; everything else is out-waited

Every error below is a FAILED run. Two of the three the workflow raises come after every delete was sent; the worker’s fail the run after one attempt.

Raised by the workflow itself

errorwhenwhat a person does
KvClusterWorkerAbsentErrorinspecting: nothing polled vm-lifecycle-activity-<kv cluster> for 5 minutes. Nothing was read and nothing was deleted.The worker inside that KV cluster is not running, cannot reach Temporal, or is deployed under another kvCluster than the day1 file name. Bring it up, then run again.
VmVolumesLeftInStorageErrorThe VM, its DataVolumes and its claims are gone, and one of these stands: a PersistentVolume with reclaim policy Retain (now Released; its volume is kept by design); a PersistentVolume of another policy still there after the 15 minutes (the CSI driver has not deleted the volume); a VolumeSnapshot of one of the VM’s disks (the storage keeps the volume under a snapshot even after its PersistentVolume is gone); a look-alike claim. The message names each PersistentVolume with its CSI driver and volume handle, each snapshot and each such claim.Delete the volume in the array by its handle and then its PersistentVolume; or the snapshot, if nobody needs it; or see the CSI provisioner’s log. Then run again.
VmDeletionTimeoutErrorThe VirtualMachine, a DataVolume or a claim was still there after the 15 minutes. The message names each with its finalizers and the pods mounting it.Something holds the object: a guest that does not shut down, a pod still mounting a claim, a finalizer nobody removes. Fix that, then run again.

Raised by the worker inside the KV cluster, non-retryable

errorwhen
VmIdentityConflictErrorThe VirtualMachine of that name is not the one asked for: no redbull.io/created-by label, another MCE, another run id, another MAC, or another cluster’s redbull.io/kv-cluster. The message says which. Checked at the inspection and again at the delete. Nothing was deleted.
KvClusterAccessErrorThe cluster’s API refused the worker’s ServiceAccount (403): its ClusterRole predates delete-vm. The chart ships before the image (below).
KvClusterMismatchErrorThe worker on that queue is deployed for another KV cluster.
VmRequestRejectedErrorThe cluster’s API refused a request as sent (400/422).

Everything else is retried without bound, backing off from 2 s to at most 1 min: the cluster’s API failing or unreachable (KvClusterApiError: 5xx, 401, 429, a timeout, a dropped connection). The run stays RUNNING in its phase, the failure showing on the activity in the Temporal UI. The delete and the wait carry no schedule-to-start limit: once a delete was sent, a worker pod away for five minutes must not fail a run that only has to wait for it.

A cancel ends the run CANCELED and undoes nothing — a delete has no rollback. Nothing runs on an exit path.

Run it again

A re-run resumes

  • The id is the VM itself, delete-vm-<kv cluster>_<vm name>: a second start while one runs is refused, and a re-run of a closed id inspects again and removes whatever is still there — found by the same rule, whether or not the VirtualMachine still exists.
  • After a delete, then fail, a re-run fails the same way, deleting nothing, until a person has removed the snapshot or the Released volume. Then it completes, found: false.
  • After a VmDeletionTimeoutError, a re-run finds what is left and waits for it again, with a fresh 15 minutes.
  • Inside one run every activity is idempotent: the delete reads the cluster again on each attempt, and the wait resumes its watching from its last heartbeat.
  • No zone lock is taken: freeing room only makes a concurrent create-vm run’s figures err on the full side.
Child only

How it is started and how you watch it

No HTTP route starts it. Its parent starts it as an awaited child on delete_vm_workflow_id(kv_cluster, vm_name), queue delete-vm-workflow. By hand, for a VM whose host is already out of its MCE:

temporal workflow start --type DeleteVmWorkflow --task-queue delete-vm-workflow \
  --workflow-id delete-vm-ocp4-prod-kv-five-az1-a_ocp-c200-kv32-five-k7q2m9xd \
  --input '{"input": {"kv_cluster": "ocp4-prod-kv-five-az1-a", "namespace": "inventory",
            "vm_name": "ocp-c200-kv32-five-k7q2m9xd", "mce_cluster": "ocp4-prod-mce-five-a",
            "why": "its host was removed from the MCE on 2026-11-26"}}'

Watch it like any run: GET /workflows/runs/delete-vm-<kv cluster>_<vm name> answers its status, its progress and, once closed, its result or failure. Never start it for a VM whose BareMetalHost still exists: metal3 lets a host go only after powering it off through the VM’s own Redfish.

What vm-lifecycle-worker needs (inside each KV cluster)

No new setting. The chart’s ClusterRole gains, each from a call in kubevirt_api.py: persistentvolumeclaims list, delete (beside get), persistentvolumes get, list, snapshot.storage.k8s.io volumesnapshots list, cdi.kubevirt.io volumeimportsources delete. Still no verb on pods beyond list, none that patches, starts or stops a VM, and none that deletes a PersistentVolume or a snapshot.

Deploy order: the chart (its RBAC) on every KV cluster → the brain → the vm-lifecycle image. An old image answers “not registered” and the run waits; a new image on an old ClusterRole answers 403, which is permanent — so the chart goes first.

Known limits

  • “PersistentVolume gone” stands for “volume gone from the array”. A CSI provisioner removes a Delete-policy PersistentVolume only once its driver deleted the volume. Checked on ceph as far as the CSI driver’s own log goes (cluster-qcl8n, 2026-11-26): for cephfs the driver logs successfully deleted volume <handle> before the PersistentVolume goes; for rbd it only queues the image’s removal (ceph’s trash, emptied by a manager task) and then answers — there a PersistentVolume that is gone means its removal was handed to ceph, not that it has finished. The array itself was not listed. Not yet checked on Trident, in the air-gap: after a delete, oc get pv shows nothing and tridentctl get volume has no entry for the volume.
  • Two cases are known where it does not hold, and the run looks for both: Retain, and snapshots — seen on that cluster: with a VolumeSnapshot of the root disk, ceph’s driver reported the volume deleted and the PersistentVolume went, while the snapshot stood.
  • A DataVolume’s own claim also names a CDI VolumeImportSource (volume-import-source-<uid>, seen on that cluster for the blank root disk): it is deleted like a boot ISO’s, and listed in import_sources_deleted.
  • A VolumeImportSource whose claim is already gone is not found again (its name was on the claim). It is a small object, not storage.
  • Nothing starts delete-vm yet: wiring it into remove-server-from-mce is a later change.
