remove-server-from-mce — what actually happens

One request takes one named server out of an MCE’s inventory. The run powers the host off, then deletes its NMStateConfig, its BareMetalHost (with its BMC Secret) and its Agent, and clears its MACs from its site’s PXE VM. Afterwards the machine is no longer in that MCE’s InfraEnv.

Only inventory. If any Agent of the host is bound to a cluster (spec.clusterDeploymentName set), the run fails with AgentBoundToClusterError and changes nothing. It never touches a hosted cluster, a Machine or a Node. To take a node out of a hosted cluster as well, use uninstall-server-from-hc, which runs this workflow as its last step.

A server with nothing on the MCE is not an error: the run completes at once with found: false and touches nothing else.

Named remove-server until 2026-11-01. POST /workflows/server-lifecycle/remove-server now answers 410 naming this route and starts nothing — send the same body here. Runs started before the rename finish as they began: as RemoveServerWorkflow on the queue remove-server-workflow, under their remove-server-… ids.

The reverse of add-server-to-mce: it removes exactly what that workflow creates.

Eight steps, in order

What the run does

Each card carries a phase, read live off the running workflow through its progress query, together with activity_queue, the MCE queue it is working on. A step with nothing to act on is skipped, and its phase never appears.

1

inspect_inventory_host

phase inspecting

Reads only. The BareMetalHost <server> and the NMStateConfig nmstate-config-<server> (both lowercased) in namespace, and the host’s Agents. An Agent is matched by BMAC’s agent-install.openshift.io/bmh label, or by any MAC of the machine: the BMH’s, the NMStateConfig’s, and every MAC server-scan holds for the server’s name. server-scan’s MACs are what still find an Agent whose BMH is already gone.

GETbaremetalhosts/<server>
GETnmstateconfigs/nmstate-config-<server>
LISTagents · matched by bmh label or MAC
GET/servers?search=<name> · server-scan, confirmed by exact name

Any of the three may be missing. None of them found: the run completes here with found: false — no PXE cleanup and no lock read, because nothing then ties the machine’s MACs to this MCE.

2

Only inventory may be removed

still inspecting

If any Agent found is bound to a cluster (spec.clusterDeploymentName), the run fails with AgentBoundToClusterError, naming each bound Agent and its cluster. Nothing has been touched yet. Take the server out of that cluster first — uninstall-server-from-hc does both halves.

3

set_host_online · get_baremetal_host

phase powering-off

Only when a BareMetalHost was found. Sets spec.online: false, then reads the BMH every 15 s until metal3 reports status.poweredOn: false (or the BMH is gone), for up to 10 minutes. Right before it writes, the activity re-reads every Agent found in step 1 and refuses with AgentBoundToClusterError if one has been bound since.

PATCHbaremetalhosts/<server> · spec.online: false
GETbaremetalhosts/<server> · status.poweredOn, every 15 s

Why first. The host is still running the discovery image. Its agent re-registers with assisted-service when its Agent disappears — a fresh Agent would be back within a minute. Powered off, nothing can bring it back. Not off within 10 minutes: HostPowerOffTimeoutError. The BMH is left with online: false and nothing is deleted — check its BMC, then re-run.

4

teardown_bmh_resources

phase removing-host

Only when a BMH or an NMStateConfig was found. The same teardown add-server-to-mce uses to roll a candidate back, in this order:

  1. annotate the BareMetalHost baremetalhost.metal3.io/detached, so metal3 does not try to deprovision it through the BMC (the host is already off, so there is nothing for a deprovision to do);
  2. delete the NMStateConfig;
  3. delete the BareMetalHost and wait for it to go; if metal3’s finalizer still holds it, drop that finalizer;
  4. delete the BMC Secret if it outlives the host (normally it goes with the BMH through its ownerReference).
PATCHbaremetalhosts/<server> · annotation detached
DELETEnmstateconfigs/nmstate-config-<server>
DELETEbaremetalhosts/<server>
DELETEsecrets/<bmc secret> · only if it outlives the host

What was actually deleted is reported in resources_removed, as Kind/name. A resource already gone is success.

5

delete_agents

phase removing-agent

Only when Agents were found. Each Agent is deleted last, once nothing can boot the host into discovery to re-register it. Each one is re-checked as still unbound right before its delete; a bound one raises AgentBoundToClusterError and is left alone. An Agent already gone counts as success.

DELETEagents/<agent>

An Agent with no BareMetalHost (found only through server-scan’s MACs) is deleted too, but there was nothing to power the host off through — see step 7 for what happens if it comes back.

6

get_inventory_segment · remove_host_pxe_entries

phase removing-pxe-boot

Only when the host is known by at least one MAC. A host left mapped on the PXE VM would network-boot this MCE’s discovery image on its next power-on and re-register its Agent. So every MAC the host is known by (the BMH’s boot MAC, the NMStateConfig’s and server-scan’s) is cleared from the PXE VM of the MCE’s own site:

  1. the MCE’s inventory segment is read from the Segments Manager, on the segment-lifecycle-activity queue, and its cluster is checked to be this MCE. Its site is the one add-server-to-mce mapped the host on;
  2. on that site’s PXE VM, each MAC is deleted on condition of this MCE.
GETthe MCE’s INVENTORY segment · Segments Manager
DELETE/pxe-map/<mac>?mce_cluster=<mce> · on the site’s PXE VM

The PXE VM keeps a MAC that chains to another MCE’s boot entry (answered 409): the machine was mapped by that MCE since, and its boot is not this run’s to take. Those are reported in pxe_kept. Everything else is removed and reported in pxe_cleared as <site>/<mac key>.

Best effort. The host is already off the MCE by now, so nothing about the removal depends on this step. No inventory segment, a segment of another cluster, a rejected token or request, or a PXE VM unreachable for 10 minutes is written to pxe_failed and logged — the run carries on. The segment lookup and the PXE call are each bounded to 10 minutes; these are the only calls in the run that are not retried without limit.

7

inspect_inventory_host, again

phase verifying

The same read as step 1, every 10 s, until no BareMetalHost, NMStateConfig or Agent of the server is left. An Agent’s finalizer holds it for seconds after the delete, so this normally passes on the first or second look.

Anything still there after 5 minutes fails the run with ServerStillPresentError, naming what is left. It is never reported as removed. The usual cause is an Agent that re-registered because the host had no BMH to power it off through; the message then says to power it off through its BMC and re-run.

8

lookup_server_membership · release_server

phase releasing-server

Nothing of the host is left on this MCE, so add-server-to-mce’s day-long hold on it for this MCE protects nothing any more. The run reads server-scan’s install lock and gives it back — but only when it is that lock (the rules). The machine can then be drawn again at once. The operator’s decision, 2026-10-31.

GET/servers?search=<name> · /servers/{id} · the lock
DELETE/servers/{id}/reservation · {holder, workflow_id} as read

Never fails the run — the removal is done, and the lock expires on its own. lock_released and lock_detail say what was found. Skipped entirely (not even read) when the PXE cleanup failed: the host’s MACs may still chain to this MCE’s discovery image, so the hold stays.

✓

Result

phase completed

found, powered_off (false when there was no BMH to power off through), agents_removed, resources_removed, pxe_cleared, pxe_kept, pxe_failed, lock_released and lock_detail — example below.

Exactly what goes

What it removes, and what it leaves alone

Removed

  • the BareMetalHost <server>, after it is powered off;
  • its BMC Secret — with the BMH, or explicitly if it outlives it;
  • the NMStateConfig nmstate-config-<server>;
  • every unbound Agent of the host;
  • the host’s MACs on its own site’s PXE VM, where they chain to this MCE (best effort);
  • add-server-to-mce’s install lock in server-scan, when it is for this MCE.

Left alone

  • a bound Agent — the whole run is refused, nothing changed;
  • the InfraEnv’s boot entry on the PXE VM (<mce>/<infraenv>.ipxe), which every other host of the InfraEnv chains through;
  • a MAC on the PXE VM that chains to another MCE (pxe_kept);
  • PXE VMs of other sites;
  • another MCE’s lock, uninstall-server-from-hc’s lock, and any other holder’s;
  • everything when nothing of the server is on the MCE (found: false): no PXE write, no lock read;
  • hosted clusters, Machines, Nodes and NodePools — never read or written.
server-scan’s install lock

Which lock is given back, and which is not

add-server-to-mce holds its lock for a day after a success, until server-scan sees the machine in a cluster. A machine removed within that day used to stay undrawable for the rest of it. Now this run releases that lock — and only that one. It releases with the holder and workflow id it just read, so server-scan compares and deletes exactly that lock.

When it stops

Refused before anything is deleted, or stopped after

Every one is a FAILED run on the status endpoint, never a 4xx on the trigger. Nothing is ever undone: a failure leaves things as they are, and a re-run carries on from there.

Nothing deleted

errorwhen
AgentBoundToClusterErrorAn Agent of the host is bound to a cluster — found at inspecting, or bound since and caught by the re-check right before the power-off. Nothing was changed. Remove the server from that cluster first (uninstall-server-from-hc does both).
HostPowerOffTimeoutErrorThe BMH did not report poweredOn: false within 10 min. It is left with online: false; nothing was deleted. Usually an unreachable BMC: check it, then re-run.
ServerScanAuthErrorserver-scan rejected the worker’s token during the inspection, which reads server-scan’s MACs. (At releasing-server the same error is only recorded in lock_detail.)
InvalidServerNameErrorThe server name cannot be a Kubernetes resource name, even lowercased.
BmhPrerequisiteMissingErrorThe MCE refused a read or the power-off with 403 (the worker’s ServiceAccount lacks the verb) or a 404 meaning the resource type is not installed. Fix the worker’s RBAC or the MCE, then re-run.

Stopped after the deletes began — a re-run carries on

errorwhen
AgentBoundToClusterErrorAn Agent was bound between the power-off and its delete. The BMH and NMStateConfig are gone; the bound Agent is left alone.
BmhPrerequisiteMissingErrorA delete refused with 403 — typically the Agent delete, when the worker has no delete on agents. The BMH and NMStateConfig are already gone; grant the verb, then re-run.
ServerStillPresentErrorAfter the deletes, a BMH, NMStateConfig or Agent of the server was still there 5 min on; the message names it. An Agent that came back on a host with no BMH: power the host off through its BMC, then re-run.

Out-waited, never failed

Every call to the MCE and to server-scan retries without limit, backing off to once a minute: an MCE API server or server-scan that is down, or a BMH still deleting (BmhTeardownError). The run sits RUNNING on that phase, with the failure visible on the activity in the Temporal UI.

No worker polling the MCE’s queue shows the same way: the call times out after 5 minutes waiting to be picked up and is tried again. The progress query names the queue it is waiting on (activity_queue).

Best effort — recorded, never failed

  • The PXE cleanup: every failure goes into pxe_failed, and the run completes. A PXE VM unreachable for 10 min is given up on.
  • The lock release: every refusal goes into lock_detail, with lock_released: false; the lock then expires on its own.
Idempotency

Running it again

Every delete treats “already gone” as success, and the run decides what to do from what it finds on the MCE each time. So re-running is always safe.

situationwhat a re-run does
a removal of that server is still runningrefused with 409 — the id is one per server
the last run completedfinds nothing and completes with found: false
after HostPowerOffTimeoutErrorsets online: false again and waits again; once the BMC answers, removes the host
after ServerStillPresentErrorremoves what it finds now — power a re-registering host off through its BMC first, or the Agent comes back again
after AgentBoundToClusterErrorrefused again while the Agent is bound
after a PXE cleanup failurethe host is gone from the MCE, so it is found: false and the PXE map is not retried — clear the entries on the PXE VM by hand if needed
HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async: the POST hands back the workflow id at once and you poll it. The same API serves a temporary page at /ui/server-lifecycle, until the ClickCluster Platform UI exists; its Remove tab lists these runs and also starts one, after you type the server name a second time. The API has no auth of its own: anyone who can reach it can start a removal.

POST /workflows/server-lifecycle/remove-server-from-mce 202 · 409 if that server is already being removed · 422 on a bad body

One server, on one MCE. server_name is the server’s name; mce_cluster is accepted with or without ocp4- (the run always uses the prefixed name) and is needed because it names the activity queue of the worker inside that MCE; namespace, where the BMH, NMStateConfig and Agent live, defaults to inventory.

// request
{
  "server_name": "ocp-cisco-m6-bat-yam-64c-512gb-WZP12345",
  "mce_cluster": "mce-bat-yam-01",
  "namespace":   "inventory"                    // optional, default "inventory"
}

// 202 response
{ "workflow_id": "remove-server-from-mce-ocp-cisco-m6-bat-yam-64c-512gb-wzp12345", "run_id": "…" }

// 409 response — a removal of that server is still running
{ "detail": "A remove-server-from-mce run is already in flight for ocp-cisco-m6-bat-yam-64c-512gb-WZP12345" }

The body forbids unknown fields (422), and every field must be non-empty. The id is the machine, lowercased, so one server is one removal however its serial was typed — and the same id whether it was started here or as uninstall-server-from-hc’s child.

POST /workflows/server-lifecycle/remove-server, the name before 2026-11-01, answers 410 naming this route, whatever the body, and starts nothing.

Two things to have in place

The PXE VMs’ pxe-map-api must understand ?mce_cluster. An older one ignores the parameter and deletes the MAC unconditionally — including one that now chains to another MCE. Upgrade the PXE VMs first.

The worker needs delete on agents (agents.agent-install.openshift.io) in its RBAC; without it the Agent delete fails with BmhPrerequisiteMissingError.

Runs recorded before a change

Three changes are gated so runs already in flight replay unchanged: remove-server-pxe-cleanup (before it, no PXE cleanup), remove-server-pxe-own-site (before it, every PXE VM the worker knows was swept, and the first refusal failed the run) and remove-server-release-own-mce-lock (before it, the run ended at verifying and left the lock to its expiry).

What it never does

  • No removal of a bound Agent, and no power-off under a cluster — refused, nothing changed.
  • No hosted-cluster work — that is uninstall-server-from-hc’s.
  • No removal of the InfraEnv’s shared boot entry, or of another MCE’s PXE entry.
  • No release of a lock that is not add-server-to-mce’s for this MCE.
  • No undo — a failure leaves everything as it is, and a re-run carries on.
