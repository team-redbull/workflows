What Temporal is, and why this repo uses it

You don't need to be an expert. You need to know what problem it solves, and the dozen words that show up in our code. That's this section.

The problem it solves

Take a real job from this repo: create a network segment, ask another team's firewall service to open rules for it, wait for a human to approve them, then unlock the segment. That wait is minutes, hours, sometimes days.

Write that as a normal script and every one of these sinks it: the pod restarts mid-job and the state is gone; a dependency is down for five minutes and the job dies; the script is run twice and opens duplicate firewall rules; something fails at 3am and nobody can see how far it got. You end up hand-building retries, a state table, a scheduler and an audit trail — badly.

The one idea: durable execution

You write ordinary Python — await this, if that, sleep two minutes, loop until done. Temporal records the result of every step in a history. If the process dies, another worker picks the job up, replays the history to rebuild the exact state the code was in, and carries on from the next line.

So a function can run for a week across a dozen pod restarts and still be a single, readable function. That is the whole pitch. Everything else is detail.

Why it fits us specifically

  • The wait is unbounded. Approval is human. A durable timer costs nothing while it waits and survives every deploy — no cron, no polling table.
  • Our dependencies wobble. Retries with backoff are configuration, not code we write.
  • Every run must be visible. The Temporal UI shows each step, its input, its result, and exactly where a failed run stopped — that's our audit trail and our debugger.
  • Duplicate triggers must be harmless. A run gets a deterministic ID, so triggering the same segment twice while it's running is refused by the server, not by our code.

The one rule that will bite you: workflow code must be deterministic

Because a workflow is replayed, the same code re-run against the same history must make exactly the same decisions. Anything that could answer differently on a second run is banned inside workflow code — and Temporal's sandbox will stop most of it.

FINE IN A WORKFLOW

  • Branching, loops, arithmetic on your own state
  • await workflow.execute_activity(...)
  • workflow.now(), workflow.sleep(), workflow.logger
  • asyncio.gather over activity handles

MUST BE AN ACTIVITY

  • Any HTTP / DB / filesystem call
  • datetime.now(), random, uuid4
  • Reading env vars or settings
  • Anything whose answer could change between runs

Corollary that surprises everyone: changing workflow code is a compatibility question. Reordering steps or renaming an activity changes what replay expects, so runs already in flight can break. New workflows and bug-free additions are fine; reshaping an existing flow needs a look at what's running.

Architecture

Three layers, deliberately kept apart

The brain decides, the limbs do, and a thin typed contract sits between them. They are separate code, separate images, separate deployments, separate credentials — and they never call each other directly.

brain limbs contract Both sides depend on shared/. Neither depends on the other.
LayerHoldsMay depend onShips as
shared/ Pydantic models, activity signatures with empty bodies, task-queue constants, typed settings, error classes temporalio, pydantic, pydantic-settings — nothing else, ever baked into both images
workflow_domains/ One folder per domain (its workflows + its router), the worker entrypoint, and api.py shared + fastapi/uvicorn. No HTTP client, no cloud SDK workflows-orchestrator Deployment, plus -api from the same image
activities/<domain>/ The real implementations + that domain's worker entrypoint shared + whatever the domain needs (httpx today; heavier later) one Deployment + ServiceAccount + Secret per domain

How the contract actually works

A workflow never imports an implementation — it imports a signature. The signature and the implementation are registered under the same name, so Temporal matches them at runtime while your editor and type-checker still see real types.

1 · shared/interfaces/<domain>.py 
# signature only — no body
@activity.defn
async def unlock_segment(
    segment: str
) -> None:
    """Locked -> Available."""
    ...
2 · activities/<domain>/activities.py 
# the real thing, same name
@activity.defn
async def unlock_segment(
    segment: str
) -> None:
    async with _client() as c:
        await c.post(...)
3 · workflow_domains/<domain>/<workflow>.py 
# imports the SIGNATURE
await workflow.execute_activity(
    unlock_segment,
    segment,
    task_queue=SC_ACTIVITY_QUEUE,
    start_to_close_timeout=...,
    retry_policy=...,
)

Why bother? The brain image never pulls in the limb's dependencies or credentials, yet a typo in an activity name is a broken import instead of a runtime mystery, and both sides are type-checked against one definition.

Runtime

What happens when someone triggers a workflow

The single most useful thing to internalise: the brain and the limb never talk to each other. Both connect only to the Temporal server, and everything moves through task queues.

The same thing in words

#What happensWhere
1Someone POSTs to a trigger route. The API derives a deterministic workflow ID and asks Temporal to start a run on that workflow's queue. It answers 202 immediately — it never waits for the outcome.workflow_domains/<domain>/router.py
2Temporal writes the run into history and puts a task on the workflow queue.server
3The brain, polling that queue, executes workflow code until it needs something from the outside world. It doesn't perform the call — it returns a command: "schedule this activity on that queue".workflow_domains/<domain>/<workflow>.py
4Temporal puts that on the domain's activity queue. The limb picks it up, makes the real HTTP call, returns the result — retrying on its own if it fails.activities/<domain>/
5The result lands in history; the brain wakes and continues from the next line. Steps 3–5 repeat, including across sleeps that last hours.loop
6Meanwhile anyone can GET /workflows/runs/{workflow_id}, which reads run status and queries the workflow for live progress.workflow_domains/routers/runs.py

Why this shape pays off

  • The brain holds no credentials and no service SDKs — it only ever names activities.
  • A limb can be redeployed, scaled or crash-looped without touching workflow logic; queued work simply waits.
  • A new domain with heavy dependencies gets its own image and RBAC without bloating anything that exists.
  • Every step is in history, so "what did this run actually do?" is answered by the Temporal UI, not by log archaeology.
The routing rule

Activity queue per domain. Workflow queue per workflow.

These two are scoped differently on purpose, and it's the detail people get wrong first. A domain holds many workflows; the domain owns the limb, each workflow owns its own front door.

Why the activity queue follows the domain

A queue maps one-to-one onto a deployment, and what forces a separate deployment is a shared dependency and credential set — not where one workflow ends and the next begins.

Every segment-lifecycle activity needs the same two things: a Segments Manager URL with a bearer token, and the NEXT firewall endpoints. That set is the deployment, so that set is the queue. A second workflow in the domain reuses the same limb rather than duplicating the credentials.

Why the workflow queue follows the workflow

Workflow code is cheap and credential-free, so all of it lives in one brain deployment — but each workflow still gets its own queue.

That keeps workflows independently addressable: one can be paused by simply not polling its queue, moved to a dedicated worker if it ever needs isolation, or drained during a risky migration, without touching its siblings. Sharing one queue would tangle all of that together.

In code: queue names are constants in shared/consts.py, and every execute_activity call passes task_queue= explicitly. Forgetting it sends the activity to the workflow's own queue, where nothing can run it — the run then sits there with an activity that never starts.

Design decisions worth knowing

Three rules that surprise people

These are not open-segment-rules trivia — they apply to every workflow you will write here, and each one is the opposite of the instinct you arrive with.

1 · The workflow is the entry point — a dependency never triggers it

A caller POSTs the full definition of the thing to be built, and the workflow creates it as its first step. It used to be the other way round for segments: the Segments Manager created the segment, then fired a best-effort HTTP call at us. That left creation outside Temporal — invisible in the UI, no retries, and silently skipped whenever that call failed.

The general rule: anything a run's outcome depends on belongs inside the run, as a retried activity — not in a caller's fire-and-forget request. New domains follow the same shape.

2 · A run may last for days, and that is fine

Where a human has to approve something, there is no timeout on the wait, by design. Durable timers cost nothing while they wait, and continue_as_new every N cycles keeps history bounded — so a run waiting a week is no more expensive than one waiting an hour.

Never "fix" a slow run by adding a deadline. A deadline turns "the approver is on holiday" into a failed run and a half-built system. If a run looks stuck, read its phase on the status endpoint before assuming it is broken.

3 · Every activity must be idempotent — retries are constant, not exceptional

Activities retry with no attempt limit, so every one of them will eventually run twice. That makes idempotency a requirement, not a nicety: UPSERT, check-before-create, idempotency keys, and treat "already exists" or "already done" as success.

In practice that means a create call accepts an existing object that matches the definition and fails only on genuine disagreement; a state change accepts an object already in the target state; a publish is a replace-style PUT rather than an append.

Inside one run — a worker crash, a redeploy, a continue_as_new — finished steps are never redone: Temporal replays their recorded results from history. A brand-new run is different: it starts from step 1 with no memory of the last one, so re-running a completed workflow is only as safe as its activities are idempotent. While a run is still in flight there is no second run at all — the deterministic workflow ID makes the trigger answer 409.

A fourth one is already above: the brain and the limbs are separate deployments that never call each other — see Three layers and what happens when someone triggers a workflow.

Naming

Is this thing named after the domain, or after the workflow?

One test settles nearly every case: could a sibling workflow in this domain reuse it unchanged? Yes → it belongs to the domain. No → it belongs to the workflow.

Named after the DOMAINNamed after the WORKFLOW
segment-lifecycle-activity (activity queue) open-segment-rules-workflow (workflow queue)
activities/segment_lifecycle/ segment_lifecycle/open_segment_rules.py
shared/models|interfaces/segment_lifecycle.py OpenSegmentRulesRunArgs / ResumeState / Progress / Result
/workflows/segment-lifecycle (route prefix) /open-segment-rules (route under it)
the Deployment, ServiceAccount, ConfigMap, Secret open-segment-rules-<TYPE>-<network> (workflow ids)

Two traps worth knowing

  • A domain is a prefix, never an endpoint. If the first workflow claims the bare /workflows/<domain> path, the second one has nowhere to go.
  • Workflow IDs must carry the workflow name. Two workflows acting on the same segment would otherwise collide on one ID and the second would be refused as already-started.

A third case: named after the external system

Some things are neither — they're defined by whoever is on the other end of the wire. check_next_requests and NextRequestRef are named after NEXT because they speak NEXT's API and every workflow in the domain shares them.

Meanwhile anything mirroring a Segments Manager endpoint keeps that endpoint's name, because renaming it here would silently desync two repos.

Recipes

Adding your own

A new workflow in an existing domain

  1. Add its models to shared/models/<domain>.py — one RunArgs wrapper, plus Progress and Result.
  2. Add any new activity signatures to shared/interfaces/<domain>.py and implement them in that domain's activities.py — existing ones you just reuse.
  3. Add its queue name to shared/consts.py.
  4. Write workflow_domains/<domain>/<workflow>.py, routing every activity to the domain's activity queue.
  5. Register it in main_worker_init.py and add a route under the existing domain prefix.
  6. Register any new activity in that domain's worker_init.py.

No new deployment, no new chart, no new credentials.

A whole new domain

  1. Everything on the left, plus:
  2. shared/models|interfaces/<domain>.py and a domain activity queue constant.
  3. activities/<domain>/ with its own requirements.txt, Dockerfile and worker_init.py.
  4. A settings group in shared/settings.py for its endpoints and credentials.
  5. A new workflow_domains/<domain>/ folder with its workflows and a router.py, included in api.py.
  6. A build job in .github/workflows/build.yml and a new helm-charts-<domain> repo for Argo CD.

The brain is already deployed — a new domain registers against it, it doesn't fork it.

Hard-won

SDK rules that cost us time

Each of these has a failure mode that looks like something else. Worth reading once now rather than debugging later.

A plain exception does not fail a workflow

Raising a normal exception in workflow code fails the workflow task, which retries forever — the run hangs in RUNNING instead of failing. Deterministic failures raised from workflow code must be ApplicationError. From activity code, ordinary exceptions are fine: the SDK converts them, using the class name as the error type.

Unclassified permanent errors retry forever

Our activities retry with no attempt limit, so outages are simply out-waited. The flip side: an error that will never succeed also retries forever unless it's listed in non_retryable_error_types or raised as a non-retryable ApplicationError. Symptom: a run stuck RUNNING with a failing activity, not a FAILED run.

Wrap shared imports in the sandbox

Inside a workflow module, import shared/ under with workflow.unsafe.imports_passed_through(): — Pydantic's C extensions crash the sandbox otherwise. Worker entrypoints run outside it and import normally. And never import settings from workflow code.

Pass the Pydantic data converter everywhere

Every Client.connect(...) — both workers and api.py — must pass pydantic_data_converter. Miss one and payloads fail to serialize at the boundary it owns.

Give run() exactly one Pydantic argument

Typed conversion is silently skipped when the number of payloads doesn't match the number of declared parameters — you get a raw dict instead of your model, with no error. Wrap input plus internal state in a single RunArgs model.

Client timeouts must sit under activity timeouts

Give every HTTP client an explicit timeout below the activity's start_to_close_timeout (60 s vs 90 s here), so a network hang fails the call and frees the worker before Temporal reaps the activity. Create the client inside the activity so tokens never leak across runs.

Getting hands-on

Running it on your machine

Four processes: a Temporal dev server, the brain, the limb, and the trigger API — plus the mock when you want a full end-to-end run.

# 0 · deps + a local Temporal (UI on :8233)
pip install -r requirements-dev.txt
temporal server start-dev

# 1 · the brain — polls the workflow queue
PYTHONPATH=. python -m workflow_domains.main_worker_init

# 2 · the limb — polls the domain activity queue
PYTHONPATH=. python -m activities.segment_lifecycle.worker_init

# 3 · the trigger API — Swagger on http://localhost:8080/docs
PYTHONPATH=. uvicorn workflow_domains.api:app --port 8080

# 4 · optional: stand in for the NEXT firewall service
cd dev/mock-segment-connectivity && uvicorn app:app --port 9000

# tests — no server needed, the SDK ships a time-skipping test env
pytest -q

Config comes from .env (see .env.example); the settings classes fail fast at startup, so a missing or malformed key crashes the worker immediately rather than mid-run. In the mock, COMPLETION_DELAY_SECONDS stands in for the human approval — set it low and a full run finishes in seconds.
