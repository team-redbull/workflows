release-segment — what actually happens

A single request — a cluster name — gives that decommissioned hosted cluster's VLAN segment back to the shared pool. If the cluster's DHCP scope survived the Argo CD teardown, the run deletes it first; then it releases the segment in the Segments Manager and reads it back as Available. It starts only once the cluster's Application and everything it managed are gone — today from a PostDelete hook in the hostedcluster-setup chart.

⏸

Before the run — not part of it

no phase

A hosted cluster is decommissioned by deleting its <cluster>.yaml from the day1 values repo's main. The ApplicationSet deletes the Application named after the file; its resources finalizer deletes everything the Application manages — the Crossplane Request among them, whose deletion makes provider-http send the DHCP API its DELETE. Once every resource is gone, Argo CD runs the chart's PostDelete hook: a one-shot Job that POSTs the cluster name to this workflow's route.

Why a hook and not an Argo CD notification. The notification catalogue's on-deleted trigger fires when deletion starts (deletionTimestamp set), before the Request — and in production the HostedCluster and NodePool — are gone, and it is fire-and-forget. A PostDelete hook runs only after every resource is deleted, and a failed hook keeps the Application in DeletionError and is retried — visible, not silent.

✓

Type check — HC only

phase pending

Runs before anything is touched. allocate-segment only ever allocates HC, so any other type was not allocated by this system and its teardown is not this workflow's: it fails immediately with UnsupportedSegmentType.

1

find_cluster_allocation

phase locating-allocation

Lists the Segments Manager's Allocated segments of the type and keeps the one whose cluster_name is exactly the cluster. The match is ours on purpose: the list route has no cluster filter (a cluster_name parameter is silently ignored and returns every segment), and its search is a substring match — c1 would also hit c10.

GET/api/segments?status=Allocated&type=HC&fresh=true · public GET, no list cache

Nothing found is not a failure. The cluster was already released, or never allocated: the run completes with released: false and touches nothing else, so a retried hook or a second deletion stays green. Two matches is AmbiguousAllocationError — a data error in the Segments Manager a human resolves.

2

get_dhcp_scope → delete_dhcp_scope → get_dhcp_scope

phase removing-dhcp-scope

Looks the scope up by the segment's network address (the CIDR with its mask dropped). Normally it is already gone — the teardown deleted it — and this stage is one 404. If it survived (an orphaned Request, a cascade that never ran) this is the safety net: delete it, then read back its absence before the segment goes anywhere.

GET/api/v1/scopes/<network> · anonymous · 404 = already gone
DELETE/api/v1/scopes/<network> · Bearer DHCP_API_TOKEN · 204 whether or not it existed

A scope still there after the delete is DhcpScopeStillPresentError: something re-created it, almost certainly a Crossplane Request that still exists — the Application is not gone yet. The segment is not released. This is the only write the orchestrator ever makes to the DHCP API, and it is only ever a delete: Crossplane remains the one creator and updater of scopes.

3

get_segment → release_segment

phase releasing-segment

The Segments Manager's release checks nobody's ownership, and the whole DHCP stage — retries included — sits between the lookup and here. So the segment is read again first: held by another cluster means it was released and re-allocated in between (AllocationOwnerMismatchError, nothing released); already Available means someone released it first, which is success. Otherwise it is released.

GET/api/segments/by-segment?segment=… · public GET
POST/api/segments/release · Bearer · { "segment": <CIDR> } · 200 "released" or "already released"
4

get_segment

phase verifying-release

Reads the segment back and requires status == Available, no cluster_name and no type — release clears both, the way allocation wrote them. Any mismatch is ReleaseNotConfirmedError.

GET/api/segments/by-segment?segment=… · public GET
✓

Done

phase completed

The result names the segment, VLAN and site given back, and whether this run had to delete the DHCP scope itself (dhcp_scope_removed — normally false). There is no git step: deleting the cluster's file was the decommission.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async: the run outlives the request by design.

POST /workflows/segment-lifecycle/release-segment 202 · 409 if already running

The body names the cluster and, optionally, the type. The segment, its site and VLAN come from the Segments Manager, so a body carrying segment or site is a 422 rather than a field silently ignored.

// request
{
  "cluster": "ocp4-prep-herzi-site1-a",
  "type":    "HC"                       // optional — HC is the default and the only supported value
}

// 202 response
{ "workflow_id": "release-segment-HC-ocp4-prep-herzi-site1-a", "run_id": "…" }

Call it only after the cluster's Application is gone. The PostDelete hook does exactly that. A manual caller who posts too early can have the scope re-created by a Request that still exists. Re-triggering while a run is in flight answers 409, which the hook treats as success. The API has no auth of its own.

GET /workflows/runs/{workflow_id} 200 · 404 if unknown id

The same domain-agnostic status endpoint every workflow uses.

// COMPLETED — the segment went back to the pool
{ …, "status": "COMPLETED",
  "result": { "cluster": "ocp4-prep-herzi-site1-a", "type": "HC", "released": true,
              "segment": "10.20.90.0/24", "vlan_id": 23, "site": "site1",
              "dhcp_scope_removed": false } }

// COMPLETED — nothing was allocated (already released): a no-op

Where it is started from

A PostDelete hook in the hostedcluster-setup chart

Until a deprovision-cluster workflow exists, the chart every hosted-cluster Application renders carries one hook Job. Argo CD creates it only when the Application is deleted, and only after every resource the Application managed is gone.

JOB release-segment-<cluster> · argocd.argoproj.io/hook: PostDelete
  1. POST /workflows/segment-lifecycle/release-segment with {"cluster": "<clusterName>", "type": "HC"} — clusterName is the ApplicationSet's own parameter, so it survives the values file's deletion.
  2. 202 or 409 → the Job succeeds and Argo CD finishes deleting the Application. It does not wait for the run: the run is durable and answers on its own id.
  3. Anything else → a few retries, then the Job fails. The Application stays with a DeletionError condition and Argo CD retries the hook on its next reconcile.

Deleting a cluster now needs the workflows API

While the API is unreachable, a deleted hosted-cluster Application waits in DeletionError. Its resources are already gone; only the Application object lingers. Fix the API and Argo CD retries — or delete the hook Job by hand to let the deletion finish, then POST the release yourself.

A bridge, not the end state

A deprovision-cluster workflow will own the teardown: delete the file, wait for the Application to disappear, then start release-segment as a child. The hook is removed then — release-segment itself does not change.

When things go wrong

Outages are out-waited. Real errors stop the run.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so an outage never fails a run. Retrying stops only for errors explicitly classified as permanent.

Classified as permanent — these fail the run

  • UnsupportedSegmentType — not HC (workflow-raised, before anything runs)
  • AmbiguousAllocationError — the Segments Manager holds two segments of the type for the cluster
  • DhcpScopeStillPresentError — the scope came back after the delete; the Application is not gone
  • DhcpApiAuthError — the worker's copy of the DHCP API token is wrong or rotated
  • DhcpScopeInvalidError — the DHCP API rejected the network address (400)
  • AllocationOwnerMismatchError — the segment now belongs to another cluster; nothing released
  • ReleaseNotConfirmedError — the read-back is not Available with no owner and no type
  • SegmentsManagerAuthError · SegmentValidationError · SegmentNotFoundError

Transient by classification

DhcpApiError and SegmentsManagerError — an unreachable service, a 5xx, a lost release race. They retry forever.

A DHCP API outage holds the release back

The scope goes before the pool, so while the DHCP API is down — or answers 503 because no DHCP server is configured behind it — the run sits RUNNING in removing-dhcp-scope and the segment stays Allocated. That is deliberate: a segment is never handed out again on a guess about its old scope.

Operating it

What happens if you run the same cluster again

Idempotency is a rule of the orchestrator — see the three rules that surprise people.

Re-run after completion — a no-op

The cluster no longer holds a segment, so the run completes at once with released: false. A re-run after a failure picks up from where that one stopped: the scope delete answers 204 for an absent scope, and the release answers "already released" for an Available segment.

The one thing a re-run will not do

Release a segment another cluster now holds. If the segment was re-allocated in between, every run refuses with AllocationOwnerMismatchError — the cluster's own allocation is already gone, and the new owner's is not this run's to give back.
