provision-cluster — what actually happens

You send the hosted-cluster YAML you would have committed to day1 — owner, mastertag, the nodepools and their config names — plus the cluster's name and the MCE folder it goes in. The run reserves a VLAN segment for it, pushes the file with the allocation block to its own day1 branch, opens the merge request, waits for a person to merge it (no deadline), and then registers the cluster in the day2 sig repos. The orchestrator is the entry point for a new cluster; the merge, the Application sync and the MachineConfigs stay where they are today.

The run, step by step

From “here is the cluster file” to “merged, and known to day2”

Six phases. Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run a cluster currently is. The colour of a call is the system it talks to.

1

inspect_cluster_target

phase inspecting-target

A fresh clone of day1 main. The MCE folder is found by name among sites/*/mces/ — iterated, never globbed with your input, because real folders (ocp4-mce-site2, ocp4-mce-site4-prep) follow no convention a parser could trust. Exactly one site must hold it. The cluster must have no file there yet: this workflow creates cluster files and never rewrites one. Then your text is judged the way the chart would render it, merged with the value layers (configValues.yaml → site → MCE → your file): mastertag, a non-empty nodepool, owner.{merkaz,anaf,mador} required; vlanId, dhcp_values, mcConfigMap, AutomateAllocation forbidden (the run and the day1 chain write those); a clusterName only if it equals the one the file name derives; config names must be DNS-1123 labels; no key written twice. A nodepool without configs is fine (a KubeVirt pool has none). Every reason lands in one failure.

GITclone --depth 1 --branch main · fresh temp clone, always discarded

Also derived here: the config names (for the merge request's description), the day2 sigs the value layers list under day2.copy_to_sigs, and their environment folder (day2.env, else the first field of the cluster name, cross-checked against the MCE folder's when it is ocp4-<env>-mce-…). Nothing is written.

2

allocate-segment — an awaited child

phase allocating-segment

The allocate-segment workflow runs as a child on its own id, allocate-segment-HC-ocp4-<clusterName>, on its own queue, with the SITE the folder is in: the Segments Manager reserves any Available /24 at that site as HC and the child reads it back to verify. The parent waits for it. A child already running for the cluster (someone started it by hand) is AllocateSegmentAlreadyRunningError; a child that fails is AllocateSegmentFailedError carrying the child's own type and message (UnknownSite, SegmentPoolExhaustedError, …). The child is never cut off by the parent closing — it verifies by read-back, and must finish.

The segment-lifecycle limb holds the Segments Manager token; this limb never does. That is why the allocation is a child and not an activity here.

3

publish_cluster_file

phase publishing-cluster-file

Your text, byte for byte, one blank line, and the allocation block (below) — written as sites/<site>/mces/<mce>/hostedClusters/ocp4-<clusterName>.yaml and pushed to provision-cluster/ocp4-<clusterName>, a branch the push itself creates from main. The commit is feat: provision hosted cluster … [provision-cluster-workflow] with no [skip ci]: the day1 CI chain must run on the branch. It skips allocation (the file carries vlanId), renders the MachineConfigs from the config names and pushes its own CI: Update mcConfigMap from mc-files [skip ci] commit on top. The workflow never writes mcConfigMap.

GITls-remote refs/heads/provision-cluster/<stem> → clone main → write → commit → push HEAD:refs/heads/<branch>

Safe to run twice. A branch already there is a re-run: its file is compared semantically — its YAML mapping, with the mcConfigMap key the chain appended set aside, must equal this run's text — then nothing is pushed (file_changed: false). A different spec, vlan or network, a branch without the file, or one that does not parse is ClusterFileConflictError: a human decides, the workflow never overwrites.

4

ensure_merge_request

phase opening-merge-request

The open merge request from the branch to main: found by source branch when one is open, else created — on GitLab (production) with remove_source_branch, on GitHub (dev) a pull request, delete-on-merge being the repository's setting. Which API is DAY1_GIT_PROVIDER. The description tells the reviewer what was written (site, folder, mastertag, config names, segment, vlan, day2 sigs) and to merge only once the branch pipeline is green and its mcConfigMap commit is on the branch.

GET…/merge_requests?source_branch=&state=opened · GitLab  |  …/pulls?head=&state=open · GitHub
POST…/merge_requests · remove_source_branch  |  …/pulls
⏸

get_merge_request_state, every 5 minutes

phase awaiting-merge

A human wait, so it has no deadline: the merge request is read every five minutes on a durable timer, for as long as the review takes. Every 48 polls (four hours) — or sooner when Temporal suggests it — the run continues as new, carrying everything it did so far, so its history stays short however long the wait; a continued run picks up at the wait and calls nothing twice. The status endpoint shows the merge request's URL, its state, since when and how many polls.

merged → on to day2. closed without merging → MergeRequestClosedError: a person decided against the cluster; the branch and the allocation stand (release-segment gives the segment back if the cluster is abandoned). A provider outage is retried, never a failure.

5

register_cluster_in_day2_sig — one per sig, in parallel

phase registering-day2

Only after the merge. For every sig the value layers listed under day2.copy_to_sigs, the folder sites/<site>/<env>/mces/<mce>/ocp4-<clusterName>/ with a .gitkeep is pushed to that sig repo's default branch (read from the remote). That folder is how day2 learns a cluster exists. Already there is success. After the merge because day2 renders the cluster's mastertag from day1 main: a folder created before the merge breaks the sig's whole render. No sigs listed → nothing to do, day2: [].

GITls-remote --symref HEAD → clone <default> → mkdir + .gitkeep → commit → push · per sig
✓

Done

phase completed

The result carries the file's path and branch, the commit (or null on a re-run), the segment, vlan, EPG and network, the merge request's URL, whether it was created or found, the merge commit, and each day2 registration. What it does not do: sync the Application — in production a person does, by hand, after the merge.

What gets written

The file on the branch, before and after the day1 chain

Your text is never re-serialised: comments, quotes and layout reach day1 as you typed them. The run appends the allocation block; the chain appends the MachineConfigs in its own commit.

YAML sites/<site>/mces/<mce>/hostedClusters/ocp4-<clusterName>.yaml 
owner:
  merkaz: "unit-a"
  anaf: "unit-b"
  mador: "unit-c"

mastertag: 4.22.8

nodepool:
- infraEnvName: dell-r660-site4-128c-1024gb-5tb
  replicas: 2
  labels:
    allowDeletion: false
  configs:
  - name: nm-conf
  - name: worker-kubeletconfig-reserved
  - name: nic-ring-buffer
  - name: workers-chrony-configuration

vlanId: 23

dhcp_values:
  network: "10.20.90.0"
  exclusions:
    - startAddress: "10.20.90.1"
      endAddress: "10.20.90.10"
    - startAddress: "10.20.90.241"
      endAddress: "10.20.90.254"

mcConfigMap:
- name: nm-conf
  config: |
    …

Everything above vlanId is your text, byte for byte. One blank line separates it from the allocation block, which carries no marker comment. The chain renders nm-conf from vlanId. network is the segment with its mask stripped, with no startRange/endRange: the DHCP API derives .1-.253. The exclusions are the type's DHCP_EXCLUSION_OCTET_RANGES, ascending. mcConfigMap arrives in the day1 chain's own [skip ci] commit, with no header.

The block assumes a /24 — asserted, not silent: a non-/24 segment fails the run with UnsupportedSegmentPrefix. A type whose policy excludes nothing drops the exclusions key. In dev, where the day1 copy has no MachineConfig chain, the file stays without the mcConfigMap section.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). The body is the cluster file itself — Swagger's “Try it out” opens a text area holding the example below for you to edit. Starting is always async: the run outlives the request by days.

POST /workflows/cluster-lifecycle/provision-cluster?cluster=<name>&mce=<folder> 202 · 409 if already running · 422 if the body or a name is unusable

cluster: the hosted cluster's name, with or without ocp4- — a lowercase DNS-1123 label of at most 24 characters (so hcp-<name>-openshift-<name> fits a label). mce: the MCE folder name under sites/<site>/mces/, verbatim. The body, Content-Type: application/yaml, must be non-empty, at most 256 KiB, UTF-8 and ONE YAML mapping; everything else about it is judged in the run, where a rejected file is a FAILED run naming every reason — never a 4xx here.

When things go wrong

Outages are out-waited. Real errors stop the run.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so a day1, git-provider or sig-repo outage never fails a run. Retrying stops only for errors classified as permanent. No activity here has a schedule-to-start timeout: a run spans days, and a limb pod away for five minutes must not fail it.

Classified as permanent — these fail the run

  • MceFolderNotFoundError · AmbiguousMceFolderError — no such folder under any site, or under two
  • ClusterAlreadyProvisionedError — the cluster's file is already on main
  • ClusterValuesRejectedError — the file would not render; the message lists every reason
  • AllocateSegmentAlreadyRunningError · AllocateSegmentFailedError — the child (workflow-raised; the second carries the child's own type)
  • ClusterFileConflictError — the branch carries a different file
  • GitProviderAuthError — the token, or its scope (GitLab needs api)
  • GitProviderRequestRejectedError — no such project for this token, no main, a merge request gone
  • MergeRequestClosedError — closed without merging (workflow-raised)
  • Day2EnvMissingError — sigs listed but no environment folder (a limb older than the field)
  • UnsupportedSegmentPrefix / InvalidSegmentCidr — the pool handed back a non-/24

Transient by classification

ValuesRepoGitError (an unreachable day1 or sig repo, a rejected non-fast-forward push — the retry re-clones), ValuesBranchNotFoundError (a repo without main yet) and GitProviderError (the provider down, a 5xx, a merge request born between the find and the create — the retry finds it). They retry forever; an unclassified permanent error shows as a run stuck RUNNING in the Temporal UI — the fix is to classify it, not to add a deadline.

Nothing to clean up

On failure or cancellation there is deliberately no compensating cleanup: the allocation is idempotent per (cluster, site, type), the branch and the merge request converge on a re-run, day2 folders are “already there = success”. Cancelling the merge wait is an operator's action in the Temporal UI.

Operating it

What happens if you run the same cluster again

Idempotency is a rule of the orchestrator — see the three rules that surprise people.

Re-run after a failure, or after completion — it converges

The child returns the same allocation (idempotent per cluster/site/type), the branch's file is recognised as this run's — the chain's mcConfigMap and its blank-line re-spacing set aside — and nothing is pushed (file_changed: false), the open merge request is found (merge_request_created: false), folders already in the sig repos are success. A cluster whose file is already on main fails ClusterAlreadyProvisionedError: provisioning is done, and changing a cluster is an edit on day1, not a run here.

The two things a re-run will not do

Overwrite a branch that carries a different file — every run refuses with ClusterFileConflictError until a human reconciles or deletes the branch. And re-open a merge request that a person closed: the run fails MergeRequestClosedError, and the next run on the cluster opens a new one for the same branch — if that is what is wanted; otherwise release the segment (release-segment) and delete the branch.
