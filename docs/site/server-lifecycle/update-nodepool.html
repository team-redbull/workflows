Temporal workflow · domain: server-lifecycle

update-nodepool — what actually happens

One request sets how many workers one NodePool of a hosted cluster runs. You name the MCE, the cluster, the NodePool and its replicas; the run checks the NodePool in day1 and on the MCE agree, writes the new replicas into the cluster’s day1 file, has Argo CD apply that commit, and checks that the NodePool on the MCE shows it. The number is set exactly: the cluster’s other NodePools are left as they are.

The day1 file owns replicas. Nothing on the MCE is written directly: the change is one commit to day1 main, synced by Argo CD. The run scales up or down through a child workflow — scale-up-nodepool or scale-down-nodepool.

On a scale-down you can say which servers leave (the operator, 2026-11-18): server_names — exactly those — or a scale_down_policy that ranks them. Either way they are marked first, and only then is the change pushed. Without either, the NodePool’s own policy applies, and without one CAPI picks at random. A run that scales up ignores both fields and says so in its result; it never fails over them.

Done means the NodePool shows the new replicas, not that new nodes are Ready (decided with the operator, 2026-11-03). After a scale-up HyperShift creates the Machines, and each one takes a free Agent of its InfraEnv when there is one. The servers a scale-down removes stay in the MCE’s inventory, free Agents again.

Which NodePool

One NodePool of this cluster, by name

nodepool is the NodePool’s name (oc get nodepool -n <hc namespace>), and replicas its own number. Only the NodePools of the cluster you name count: those in its HostedCluster’s namespace whose spec.clusterName is that HostedCluster. Any platform works — an Agent NodePool or a KubeVirt one.

infra_env_kind was removed on 2026-11-18 (the operator: “no need infraenv kind”). It set a TOTAL over every NodePool of one InfraEnv kind, spread at most one replica apart. The API now answers it with a 422 saying to name the NodePool. A run recorded with a kind before that day still finishes as it began — see runs recorded by kind.

update-nodepool, then its child

What the run does

Each card carries a phase, read live through the progress query of the run it belongs to. The parent also reports direction and, while its child runs, child_workflow_id.

1

read_day1_nodepools

phase reading-day1

The cluster’s file in day1 main, read by the MCE’s server-lifecycle worker: its path, its git blob, the HostedCluster it renders (openshift-<clusterName> in hcp-<clusterName>), and each nodepool[] entry’s name, replicas (the chart’s default 1 when absent) and InfraEnv (infraEnvName, else agentLabelSelector.nodeLabelValue).

The file must sit under sites/<site>/mces/<mce_cluster>/, or the run stops with ClusterNotOnMceError before reading anything on the MCE. A file the chart would refuse (a key written twice, a NodePool named twice) stops it with Day1ClusterProblemsError.

2

read_hosted_cluster

phase reading-nodepools

The HostedCluster’s NodePools on the MCE, read by the same worker: spec.replicas, the InfraEnv of the selector, and the redbull.io/scale-down-policy label or annotation. The named NodePool is selected here; one the cluster has on neither side is NodePoolNotFoundError.

The selector’s InfraEnv is its matchLabels InfraEnv label, else the first value of its In expression on that label: the shape the hostedclusters-setup chart renders for a nodepool with additionalInfraEnvNames, infraEnvName first. That first one is the InfraEnv compared with day1; the additional ones are not compared. DoesNotExist expressions (excludeAgentLabels) name no InfraEnv and change nothing here.

Live and day1 must agree: the NodePool is in day1 under its name with the same replicas and InfraEnv, and on the MCE. Anything else stops the run with NodePoolReplicasDriftError before anything is written — a NodePool made by hand, one Argo CD has not created yet, replicas someone changed on the cluster.

3

The plan

phase planning

The NodePool takes exactly the number asked. More replicas than now is a scale-up, fewer a scale-down, the same completes here, direction: "none", nothing written.

On a scale-down, server_names must name exactly as many servers as the replicas removed (5 → 3: two), or the run stops with ScaleDownServersInvalidError before the child starts. A scale_down_policy goes on the NodePool’s plan, ahead of its own.

Not a scale-down (up, or no change): server_names and scale_down_policy are ignored, never refused, whatever they hold. The result lists each in ignored, with why.

4

The child

phase scaling-up · scaling-down

scale-up-nodepool or scale-down-nodepool, awaited, on its own id and queue. Its result is the parent’s scale. It is abandoned, never cancelled, if the parent is closed: it marks Machines and writes git in an order that must not be cut.

5

read_scale_down_candidates · mark_machines_for_deletion

phases selecting-servers · marking-machines — scale-down, with names or a policy

The MCE’s server-lifecycle worker reads the NodePool’s Machines (by HyperShift’s hypershift.openshift.io/nodePool annotation) and the run chooses the ones that leave — the named servers’ Machines, or the ones a policy ranks first. It then puts cluster.x-k8s.io/delete-machine: scale-down-nodepool-<cluster> on each chosen Machine and reads it back. CAPI deletes a marked Machine before any other, so the commit that follows removes exactly those.

Refused with nothing written: a Machine already deleting, a delete mark this run did not write, a Machine count that is not the replicas, Machines in two MachineSets (a rollout) — and what each way of choosing refuses. A mark an earlier attempt of this run left on a Machine not chosen now comes off first. With neither names nor a policy this step is skipped: nothing is marked.

6

commit_day1_replicas

phase committing-day1

The NodePool’s new replicas in one commit to day1 main, nodepool(<cluster>): replicas c 3→2 [<run id>]. Only that replicas: line changes; comments and quoting stay. Compare-and-set on the blob read in step 1: a file someone else changed since is never committed over (Day1FileChangedError). day1’s validator runs first when one is configured.

On a scale-down, a refused commit takes the run’s marks off again (unmarking-machines) before it fails.

7

sync_argo_application · read_hosted_cluster

phases syncing-argo · verifying-nodepools

The cluster’s Argo CD Application synced to exactly that commit. Only the moved NodePool may be out of sync; anything else pending is someone else’s change and the sync is refused (ArgoSyncRefusedError). Then the NodePool is read back: it must show its planned spec.replicas, or NodePoolsNotReconciledError.

8

watch_marked_machines

phase verifying-machines — scale-down, with marks

One heartbeating watch, every 15 s for up to 10 minutes, until every marked Machine is deleting or gone. An unmarked Machine of the NodePool deleting instead is ScaleDownWrongMachineError — named, and it cannot be undone. The run does not wait for the drain or for the Agent to come free.

scale-down-nodepool

Which servers leave

The first of these that applies (the operator, 2026-11-18; until then only the NodePool’s own policy, 2026-11-03). server_names and scale_down_policy together are a 422.

the request / the NodePoolwhich servers leave
server_namesExactly those servers. The NodePool’s own policy is not read.
scale_down_policyThe first ones by that policy, whatever the NodePool says — even a value of its own that is no policy.
the NodePool’s redbull.io/scale-down-policyThe first ones by that policy. A value that is no policy is ScaleDownPolicyInvalidError.
none of theseNothing is marked. CAPI’s MachineSet picks — at random, HyperShift’s default.

Named servers

Server-scan names, one or a list, compared case-insensitively. For each Machine of the NodePool the worker reads which server it is: the Machine’s AgentMachine, the Agent its status.agentRef names, and that Agent’s agent-install.openshift.io/bmh label — the BareMetalHost add-server-to-mce named after the server — else the Agent’s hostname, else the Machine’s Node. Nothing is ranked, so the hosted cluster is not read at all. Each named server’s Machine is marked, in the order you gave.

Refused with nothing marked or written (ScaleDownServersInvalidError, the message says which):

  • the list is not as long as the replicas removed — checked by update-nodepool itself, before the child starts;
  • a server is named twice;
  • no Machine of the NodePool is a named server — the message lists the NodePool’s servers;
  • two Machines are one named server;
  • an unnamed Machine CAPI counts unhealthy would be taken in place of a named one. In OpenShift 4.18’s CAPI a marked and an unhealthy Machine rank the same, and the tied ones go by Machine name: if such a Machine sorts before a named one, CAPI would delete it instead. Name that server instead, or bring it back to health first. One that sorts after the named ones is no reason to refuse;
  • the MCE’s server-lifecycle-worker predates server_names and cannot say which server a Machine is — upgrade it.

A policy

valuewhich servers leave first
fewest-podsThe fewest workload pods: the least for the drain to move. Workload means not a DaemonSet’s, not a mirror pod, not finished — the drain’s own rules.
least-requestedThe lowest share of the Node’s allocatable its pods request, the larger of CPU and memory. From the pods’ requests, as the scheduler counts them; no metrics needed.
least-utilizedThe lowest live use of allocatable, the larger of CPU and memory, from metrics.k8s.io on the hosted cluster. A cluster with no metrics API fails the run (NodeMetricsUnavailableError); a Node that just joined is waited for until its metrics appear.

A policy reads the Machines’ Nodes, Pods and — for least-utilized — NodeMetrics through the hosted cluster’s admin kubeconfig. Under every policy the order is:

  1. Machines CAPI counts unhealthy — no nodeRef, a failure, or NodeHealthy / HealthCheckSucceeded False, read off the Machine exactly as CAPI’s isMachineHealthy does — by name;
  2. a Machine already carrying this run’s mark, so a re-run keeps its choice;
  3. a Node the hosted cluster does not have, or has NotReady or cordoned, while CAPI still counts the Machine healthy;
  4. the policy’s reading. Ties go by Machine name.

Why the mark decides which servers go

HyperShift backs an InPlace NodePool with one CAPI MachineSet and a Replace one with a MachineDeployment, sets their replicas from the NodePool, and sets no delete policy — so CAPI’s default, Random, applies. On a scale-down the MachineSet ranks its Machines and removes the top ones, ties by name. Under Random a Machine annotated cluster.x-k8s.io/delete-machine outranks every healthy one in every CAPI version, and an unhealthy one from CAPI 1.9 on (OpenShift 4.19 and later). In 4.18’s CAPI a marked and an unhealthy Machine rank the same, which is why a policy takes CAPI-unhealthy Machines first, in CAPI’s own order, and why named servers are refused when an unnamed unhealthy one would be taken in their place: the Machines CAPI removes are then exactly the marked ones in every version.

The mark only orders Machines inside one MachineSet. A Replace NodePool in the middle of a rollout has two, and its MachineDeployment may scale down the other one: a NodePool whose Machines span two MachineSets is refused (ScaleDownRolloutInProgressError). HyperShift leaves annotations on Machines alone; its own docs annotate them with another CAPI annotation (machine.cluster.x-k8s.io/exclude-node-draining). The watch after the sync still checks that the marked Machines are the ones deleting.

Setting the NodePool’s own policy in day1. As an annotation of the NodePool’s nodepool[] entry. The hostedclusters-setup chart renders an entry’s annotations onto the NodePool (since 2026-11-08, GitHub copy); its labels stay allowDeletion, maxReplicas and minReplicas:

nodepool:
  - infraEnvName: dell-r660-128c-1024gb
    replicas: 3
    labels:
      allowDeletion: false
    annotations:
      redbull.io/scale-down-policy: fewest-pods

The air-gapped GitLab copy of the chart renders no entry annotations until it gets the same change. There, set the key on the NodePool directly (oc annotate nodepool <name> -n hcp-<cluster> redbull.io/scale-down-policy=fewest-pods) or send scale_down_policy; Argo CD leaves an annotation it never set alone. The run reads a label of that key too, for one set by hand.

The maxReplicas / minReplicas labels are not the run’s (the operator, 2026-11-08). The commit changes replicas only. Left unwritten, the chart derives them from replicas (replicas and replicas − 1), so they follow; written in the entry, they keep the value written.

When it stops

Refused before anything is written, or stopped after

Every one is a FAILED run on the status endpoint. A child’s failure fails the parent with ScaleNodePoolFailedError, whose message carries the child’s own type and message.

After the commit — the commit stays in day1

errorwhen
ArgoSyncRefusedErrorSomething else in the Application is out of sync. The marks stay: when the commit is applied, CAPI removes the marked Machines first.

Out-waited, never failed

Every call retries without limit, backing off to once a minute: day1 unreachable or a push that lost a race with another commit, an MCE or hosted API server that is down, an Argo CD sync that failed or found another operation in progress. The run sits RUNNING with the failure on the activity. A call no worker picks up within 5 minutes — that worker not deployed, or not on this MCE — fails the run instead.

A worker from before 2026-11-18 cannot read a named scale-down’s request: that read is retried, RUNNING, until the new worker polls.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async: the POST hands back the workflow id at once and you poll it. The children have no route of their own. The API has no auth of its own: anyone who can reach it can change a cluster’s workers.

POST /workflows/server-lifecycle/update-nodepool 202 · 409 while a run or an upgrade of the cluster runs · 422 on a bad body 
// request
{
  "mce_cluster": "mce-bat-yam-01",                 // with or without ocp4-
  "cluster":     "ocp4-prod-alpha",                // the day1 file's name, without .yaml
  "nodepool":    "prod-alpha-zone-c",
  "replicas":    3,                                // that NodePool's, set exactly; 0 allowed

  // optional, read only on a scale-down — at most one of:
  "server_names":      ["ocp-r660-bat-yam-HP0001592", "ocp-r660-bat-yam-HP0001611"],
  "scale_down_policy": "fewest-pods"               // fewest-pods | least-requested | least-utilized
}

// 202 response
{ "workflow_id": "update-nodepool-ocp4-prod-alpha", "run_id": "…" }

mce_cluster, cluster, nodepool and replicas are required; cluster and nodepool must be Kubernetes names, replicas 0 or more. server_names is one name or a list of up to 20, each once (case-insensitively). server_names with scale_down_policy, a policy that does not exist, and infra_env_kind (removed on 2026-11-18) are each a 422 that says why; the body forbids unknown fields.

Before 2026-11-18

Runs recorded by kind

A run started with infra_env_kind before the field was removed still finishes as it began: replicas is the TOTAL over the cluster’s NodePools of that kind — those whose selector’s InfraEnv is the kind, or the kind followed by - and anything — refused when they are already more than one replica apart (NodePoolsUnbalancedError), and spread one replica at a time: up to the NodePool with the fewest, down from the one with the most, ties by InfraEnv then NodePool name. Each shrinking NodePool is scaled down by its own policy. Nothing new can start that way; the code goes once no such run is left.

What it never does

  • No write to a NodePool, HostedCluster or Node on the MCE — the change is day1’s, applied by Argo CD.
  • No commit over someone else’s edit, and no sync of someone else’s pending change.
  • No change to another NodePool of the cluster.
  • No scale-down that could take a server other than the ones named: it is refused instead.
  • No removal of a server from the MCE: the servers a scale-down frees stay in the inventory.
  • No wait for new nodes to be Ready, or for a drain to finish.
