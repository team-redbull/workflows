publish-infraenv-to-pxe-server — what actually happens

One request writes an InfraEnv’s boot entry, /var/www/pxe-map/<mce_cluster>/<infra_env>.ipxe, onto the PXE VM of the MCE’s site. It holds the InfraEnv’s current iPXE script URL, and every IPMI blade that add-server-to-mce mapped to that InfraEnv chains to it when it boots from the network.

add-server-to-mce already makes this same publish itself, once per IPMI host. This workflow is that publish on demand, tied to no host: to seed the entry before the first install, to repair one deleted or corrupted on the VM, or to point it at a regenerated discovery image without installing anything. It writes nothing on the MCE, maps no MAC, deletes no entry, and can never roll an entry back to an older image.

Read this first

One InfraEnv, one file, one PXE VM

An IPMI (UCS) blade has no virtual media, so it boots from the network. The site’s PXE VM answers its boot MAC with a small per-MAC file that chains to the InfraEnv’s boot entry. That boot entry is one file per (MCE, InfraEnv), shared by every host mapped to the InfraEnv — so pointing all of them at a new image is one write.

When to run it

  • Seed the entry before the first install into an InfraEnv.
  • Repair an entry that was deleted or corrupted on the PXE VM.
  • Refresh the entry after the InfraEnv’s discovery image was regenerated, without installing a server.

You do not need it for a normal install: add-server-to-mce publishes the entry itself for every IPMI blade, in its phase publishing-pxe-boot (its phases).

What it never does

  • It writes nothing on the MCE: it only reads the InfraEnv.
  • It reads no NMStateConfig: it publishes the InfraEnv’s current image as soon as that image is ready.
  • It maps no MAC and removes no entry.
  • It can never roll an entry back: the PXE VM keeps a newer image if it already holds one.

The iPXE script URL is read and written inside the activity, so it never enters Temporal history or the run’s result.

Three phases, in order

What the run does

Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run it currently is. A run that has not started its first step reports pending.

1

get_inventory_segment

phase resolving-site

The MCE’s INVENTORY segment in the Segments Manager, found by cluster name. Its site decides which PXE VM is written to — the same rule add-server-to-mce maps hosts by, so this run always writes to the VM those hosts boot from.

GET/api/segments?type=INVENTORY · once per run, on the SEGMENT-LIFECYCLE queue

On the segment-lifecycle queue because the Segments Manager token lives on segment-lifecycle-worker. The cluster match is made client-side, so the workflow checks it again: a segment allocated to another cluster would publish to another site’s PXE VM, and fails the run with InventorySegmentMismatchError before anything else happens.

2

check_infra_env

phase validating-infraenv

The InfraEnv must exist on the MCE, in namespace. A missing one fails the run with InfraEnvNotFoundError, before anything is published.

GETinfraenvs/<infra_env> · on the MCE’s queue, server-lifecycle-activity-<mce_cluster>

Steps 2 and 3 run on the server-lifecycle-worker inside that MCE. The hub never talks to the MCE’s API server; the worker in the MCE polls its own queue.

3

publish_infra_env_boot

phase publishing

The activity reads the InfraEnv and checks that it has a ready discovery image — all three of:

  1. its ImageCreated condition is True;
  2. it publishes status.bootArtifacts.ipxeScript;
  3. it has a status.createdTime.

If not, it writes nothing and answers “not yet”, with the reason. The workflow waits 10 s on a durable timer and asks again. Once the image is ready, the activity writes the iPXE script URL to the PXE VM, with the image’s createdTime as its version.

PUT/pxe-map/<mce_cluster>/<infra_env> · {"ipxe_url", "image_created_at"} to PXE_MAP_URLS[site]

Bounded at 10 minutes, counted from the first attempt in this phase. No ready image by then fails the run with InfraEnvImageNotUpdatedError, quoting what was still awaited — for example “InfraEnv condition ImageCreated is not True: …” with assisted-service’s own message. ImageCreated False means the last image generation failed, so check that condition and the assisted-service log. Nothing was written to the PXE VM.

The PXE VM compares image_created_at before it writes. If it already holds a newer image it keeps it and answers 409. The activity treats that as success and the run completes with superseded: true: the entry is current either way.

✓

Result

phase completed

The MCE, InfraEnv and namespace that were published, the site whose PXE VM was written, image_created_at (the createdTime of the image this run read) and superseded. With superseded: false the entry now holds that image. With superseded: true the VM kept a newer one and this run wrote nothing.

When it stops

Classified errors fail the run; everything else is out-waited

Every error below is a FAILED run on the status endpoint, never a 4xx on the trigger, and fails after one attempt — a retry would get the same answer. Nothing is undone, because nothing before the final PUT writes anything.

Raised by the workflow itself

errorwhen
InventorySegmentMismatchErrorresolving-site: the segment returned is allocated to another cluster than the requested MCE.
InfraEnvImageNotUpdatedErrorpublishing: the InfraEnv showed no ready image (ImageCreated True, an ipxeScript, a createdTime) within 10 min. The message names what was still awaited and says nothing was written to the PXE VM.

Raised by an activity, non-retryable

errorwhen
InventorySegmentNotFoundErrorThe MCE has no INVENTORY segment allocated in the Segments Manager. An operator allocates one.
AmbiguousInventorySegmentErrorMore than one INVENTORY segment is allocated to the MCE. A human resolves the duplicate.
SegmentsManagerAuthErrorThe Segments Manager rejected the token (401/403).
InfraEnvNotFoundErrorNo InfraEnv of that name in namespace on the MCE.
BmhPrerequisiteMissingErrorThe MCE cannot answer the read at all: the worker’s ServiceAccount lacks get on infraenvs (403), or the Assisted Installer or the namespace is missing (404).
PxeSiteNotConfiguredErrorPXE_MAP_URLS on this MCE’s worker has no entry for the segment’s site. An operator adds it. This fails the run — unlike add-server-to-mce, where it is a skip, because there it only rules out one candidate.
PxeMapAuthErrorThe PXE VM rejected PXE_MAP_TOKEN (401/403).
PxeMapRequestRejectedErrorThe PXE VM refused the PUT (400/404/422). A 404 here most likely means that PXE VM’s pxe-map-api predates InfraEnv boot entries and must be upgraded.

Everything else is retried without bound, backing off from 1 s to at most 1 min between attempts: the Segments Manager, the MCE’s API or the PXE VM unreachable or answering a server error (for the PXE VM that is PxeMapError). The run stays RUNNING in its phase and the failure shows on the activity in the Temporal UI.

Steps 2 and 3 also carry a 5-minute schedule-to-start timeout. If no worker polls server-lifecycle-activity-<mce_cluster>, the run does not fail: it stays in validating-infraenv with repeated timeouts in its history, and its progress names the queue it is waiting on.

Running it twice

Safe to repeat, and never a step backwards

Temporal retries activities and operators re-POST things. Both are safe here.

The PXE VM compares-and-sets on the image time

Every write carries the image’s createdTime as image_created_at. The PXE VM writes when that time is the same as or newer than what it holds, and refuses an older one with 409.

  • Same time: overwritten with the same content — so a retried activity or a second run converges.
  • Newer on the VM: kept. The run completes with superseded: true. This is the case where an install of the same InfraEnv published a later image first.

So running it again is always safe, and it can never replace a newer image with an older one.

The id is the file it writes

publish-infraenv-to-pxe-server-<mce_cluster>-<infra_env> — one boot entry per (MCE, InfraEnv). A second trigger for the same entry while a run is in flight gets 409. Once that run has closed, the same id can be started again.

The same InfraEnv name on two MCEs is two different files, so those runs do not block each other. The id is dedup, not a safety lock: two runs racing would still be harmless, because of the compare-and-set on the left.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async: the POST hands back the workflow id at once and you poll it. The API has no auth of its own — anyone who can reach it can start a run.

POST /workflows/server-lifecycle/publish-infraenv-to-pxe-server 202 · 409 if a run for that entry is in flight

Two fields are required: the MCE and the InfraEnv. namespace defaults to inventory. mce_cluster is accepted with or without its ocp4- prefix and always becomes the prefixed name before the run starts — it finds the site, names the MCE’s queue and is the entry’s directory on the PXE VM, so both spellings must land on the same file.

// request
{
  "mce_cluster": "mce-bat-yam-01",
  "infra_env":   "cisco-m6-bat-yam-64c-512gb"
}

// request — the InfraEnv lives in another namespace
{
  "mce_cluster": "ocp4-mce-bat-yam-01",
  "infra_env":   "cisco-m6-bat-yam-64c-512gb",
  "namespace":   "multicluster-engine"
}

// 202 response — both requests above get this id
{ "workflow_id": "publish-infraenv-to-pxe-server-ocp4-mce-bat-yam-01-cisco-m6-bat-yam-64c-512gb", "run_id": "…" }

// 409 response — the same entry is already being published
{ "detail": "A publish-infraenv-to-pxe-server run is already in flight for ocp4-mce-bat-yam-01/cisco-m6-bat-yam-64c-512gb" }

The body forbids unknown fields: anything besides mce_cluster, infra_env and namespace is a 422. Each field must be non-empty.

The old path, POST /workflows/server-lifecycle/publish-infraenv-boot, answers 410 whatever the body, and starts nothing: "publish-infraenv-boot was renamed to publish-infraenv-to-pxe-server — POST /workflows/server-lifecycle/publish-infraenv-to-pxe-server with the same body".

GET /workflows/runs/{workflow_id} 200

Domain-agnostic: workflow ids are globally unique, so one route serves every domain. It addresses the progress query by name, so the response carries the live phase and the MCE activity queue this run dispatches to. A completed run carries the result instead; a failed one carries its error.

// 200 while running
{
  "workflow_id":   "publish-infraenv-to-pxe-server-ocp4-mce-bat-yam-01-cisco-m6-bat-yam-64c-512gb",
  "workflow_type": "PublishInfraEnvToPxeServerWorkflow",
  "status":        "RUNNING",
  "progress": {
    "phase":          "publishing",
    "activity_queue": "server-lifecycle-activity-ocp4-mce-bat-yam-01"
  }
}

// 200 when completed
{
  "status": "COMPLETED",
  "result": {
    "mce_cluster":      "ocp4-mce-bat-yam-01",
    "infra_env":        "cisco-m6-bat-yam-64c-512gb",
    "namespace":        "inventory",
    "site":             "bat-yam",
    "image_created_at": "2026-10-19T10:00:05Z",

  }, …
}

A phase that does not advance past validating-infraenv usually means nothing is polling activity_queue: that MCE has no server-lifecycle-worker deployed, or it cannot reach Temporal.

A missing InfraEnv, a site with no PXE VM configured and an image that never becomes ready are all FAILED runs on the status endpoint — not 4xx on the trigger. Everything the outcome depends on happens inside the run, as a retried activity.
