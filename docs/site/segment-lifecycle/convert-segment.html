convert-segment — what actually happens

One request — site, source type, destination type, quantity — rebalances segment inventory between types. The workflow finds up to quantity Available segments of the source type at the site, re-types each one in the Segments Manager (which re-locks it and clears the old type's pending firewall request ids), and starts one open-segment-rules run per converted segment — the new type has different peers, so connectivity is re-established from scratch.

Fewer matching segments than requested is not an error: the run converts what exists and reports the shortfall in its result. Available only is deliberate: Allocated segments are in use, and Locked ones may still have a live open-segment-rules run — re-typing under it would mean cancelling it, which this workflow never does. See why.

The run, step by step

From “convert N segments” to “N open-segment-rules runs are on their way”

Three stages plus a per-segment loop. The parent never waits for the firewall approvals: each converted segment gets its own detached open-segment-rules run — its own workflow id, its own human approval, its own failure — exactly like the bulk trigger route, and the parent completes with a fan-out report.

Segments Manager Temporal itself (detached child workflows) All machine ops — the run is bounded and fails loudly; the human approvals live in the children.

The same run, in detail

Each card carries a phase — read live off a running workflow through a Temporal query. The progress payload also carries the per-segment report so far, so even a run that fails mid-loop shows exactly which segments were already converted.

get_valid_sites

phase validating-site

Strict first check: a typo'd site must fail loudly as UnknownSite, not complete as “matched 0 segments, shortfall N”. (Source == destination is rejected even earlier, by the request model — converting a segment to its own type is a no-op.)

GET/api/sites · public GET
2

list_convertible_segments

phase searching-segments

Every segment of the source type at the site whose status is Available — Allocated segments are in use, and Locked ones are excluded by design (why). Selection is the workflow's deterministic policy over that result: lowest vlan_id first, cut at quantity.

GET/api/segments?site=…&type=…&status=Available · all three filters server-side

A returned segment in any other status fails the activity rather than being quietly skipped — it would otherwise enter the conversion loop, which is exactly what must not happen.

Fewer matches than requested → convert all of them and report the shortfall. Zero matches → an empty report with shortfall == quantity, still a COMPLETED run.

3a

convert_segment_type

phase converting-segments

One atomic Segments Manager update: set the new type, set status back to Locked, and clear every segment_connectivity_* field — the pending request ids belong to the old type's requests, and a stale “Workflow failed” note has no other clearing path. Re-locking matters: an Available-looking converted segment could be allocated to a cluster before its new-type firewall rules exist.

PUT/api/segments/type · Bearer · { segment, type, expected_type }

expected_type is a compare-and-set. Two conversions racing for the same segment (say HC→MCE and HC→PXE at one site) cannot both win: whoever converts first changes the stored type, and the loser's call answers 409 → SegmentConversionConflictError, failing that run loudly instead of silently hijacking the segment.

3b

Start open-segment-rules, detached

phase converting-segments

The replacement run — open-segment-rules-<DEST>-<network> — starts as a detached child workflow (ParentClosePolicy.ABANDON): it survives however this parent ends, because it answers to its own id, its own human approval and its own failure, exactly as if the bulk route had started it. Its create_segment first step accepts the existing (now destination-typed) segment idempotently and proceeds: peers → submit rules → await approval → unlock.

If a destination-type run for this segment already exists, that run is the desired outcome — the report marks the item already_running and the loop continues.

✓

Done — the children run on alone

phase completed

The result lists every conversion — the segment, its vlan, and the child workflow id to poll — plus matched and shortfall. Poll each child on the same GET /workflows/runs/{workflow_id} endpoint as any other run.

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async. There is deliberately no bulk variant — the request is already batch-shaped.

POST /workflows/segment-lifecycle/convert-segment 202 · 409 if already running 
// request
{
  "site": "site1",
  "source_type": "HC",
  "destination_type": "MCE",
  "quantity": 3
}

// 202 response
{ "workflow_id": "convert-segment-site1-HC-to-MCE", "run_id": "…" }

The id carries site and both types. Two identical conversion requests racing would select the same segments, so they dedup onto one id (the second answers 409). Conversions differing in either type are legitimately concurrent — the expected_type compare-and-set arbitrates if they grab the same segment.

When things go wrong

Outages are out-waited. Real errors stop the run — cleanly.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so a Segments Manager outage never fails a run. Retrying stops only for classified errors — and a mid-loop stop always lands on a clean per-segment boundary.

Classified as permanent — these fail the run

  • UnknownSite — the site isn't in GET /api/sites
  • SegmentConversionConflictError — the Segments Manager answered 409: the segment became Allocated, or a concurrent conversion re-typed it first (expected_type mismatch)
  • SegmentNotFoundError — a selected segment vanished between search and convert
  • SegmentsManagerAuthError — bad SEGMENTS_MANAGER_API_TOKEN

Source == destination and quantity < 1 never reach the workflow — the request model rejects them with a 422.

A failed or cancelled run needs no compensation

Conversions already performed stand: their detached children run on regardless of the parent, and each converted segment is exactly where a freshly created one would be (Locked, awaiting its rules). Nothing pending is half-applied — the per-segment loop is sequential on purpose.

Re-running is the recovery path

A re-run's search no longer matches the segments that were already converted (their type changed), so it picks up exactly the remainder. If a child run already exists for a segment, the report says already_running and moves on.

Why Available only — and what it costs

A Locked segment has no established connectivity and may still have a live open-segment-rules-<SRC>-<network> run. Re-typing it underneath that run would leave the old run fighting the replacement over the request-ids display (replace semantics, keyed by CIDR) and wrongly unlocking the segment when the old approval finally lands. Handling that means cancelling the sibling and waiting out its cleanup.

And a cancel cannot even tell you whether a run was live: Temporal accepts a cancel against an already-closed execution and reports it accepted, failing only for an id that never existed. Restricting the search to Available removes the interaction at the source — every match is a segment whose own run has completed, since that completion is what unlocked it. No cancellation, no grace pause, no stale-note race, and not a single timer in the loop.

The cost, stated plainly: a Locked segment cannot be re-typed by this workflow at all — including one whose open-segment-rules run failed terminally, which stays Locked by design. Such a segment is neither allocatable nor convertible; re-driving it through open-segment-rules for its current type is the way back.
