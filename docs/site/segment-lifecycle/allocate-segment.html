allocate-segment — what actually happens

A single request — just a cluster name — reserves a VLAN segment for that hosted cluster in the Segments Manager, verifies the reservation landed, writes the dhcp_values block into the cluster's values file in the day1 repo, and waits until Argo CD + Crossplane have turned that commit into a live DHCP scope. The cluster gets its network and its DHCP scope from one durable run.

It replaces the GitLab CI bash pipeline outright — the one with no durable retry, no verification, and a failure mode of “cluster created without a VLAN”.

The run, step by step

From “allocate for this cluster” to “DHCP scope is live”

Five stages, left to right. The colour of each box is the system it talks to. Verification sits before the git write on purpose: a VLAN is never recorded in the values repo unless the Segments Manager confirms the reservation.

Segments Manager git / DHCP stack (Argo CD → Crossplane → DHCP API) Stages 1–5 all run inside one Temporal workflow; each is a retried activity.

The same run, in detail

Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run an allocation currently is.

✓

Type check — HC only

phase pending

Runs before anything is touched. This workflow allocates HC segments only; any other type fails immediately with UnsupportedSegmentType. Without the gate a non-HC run would still die — only hostedCluster files are named <cluster>.yaml — but as a misleading ClusterFileNotFoundError. Future segment types get their own functions when they arrive.

1

get_valid_sites + locate_cluster_file

phase resolving-site

There is deliberately no site input. The workflow shallow-clones the day1 values repo and requires exactly one sites/<site>/**/<cluster>.yaml; the site is the path segment under sites/, cross-checked against the Segments Manager's site list. The repo layout is the source of truth — a caller can never claim a site the cluster does not live in.

GET/api/sites · the cross-check list
GITclone --depth 1 $DAY1_REPO_URL · fresh temp clone, always discarded

Zero matches → ClusterFileNotFoundError; more than one → AmbiguousClusterFileError; a site the Segments Manager doesn't know → UnknownSite. All three fail the run before anything is allocated.

2

allocate_segment

phase allocating-segment

Reserves a segment of the requested type for the cluster at the derived site. The Segments Manager is idempotent per (cluster, site, type): a repeat call — a Temporal retry, or a whole re-run — returns the existing allocation, so double-allocation is impossible by construction.

POST/api/segments/allocate · Bearer · → { vlan_id, segment, epg_name, … }

An empty pool (503) fails loudly as SegmentPoolExhaustedError — a drained pool is refilled by an operator creating segments, not by retrying every minute forever.

3

get_segment

phase verifying-allocation

Reads the allocated CIDR back and requires status == Allocated, the exact cluster name, and the exact VLAN. Any mismatch is AllocationNotConfirmed — and because this sits before the git write, the values repo never records a VLAN the Segments Manager doesn't confirm.

GET/api/segments/by-segment?segment=… · public GET
4

append_allocation_to_cluster_values

phase updating-values-repo

Fresh clone, append the marker block (see below), commit, push to main. Safe to run twice: the identical block already present is a no-op success (values_updated: false, nothing pushed); a block with different values — or a dhcp_values/vlanId key some human wrote without the marker — is a hard ClusterValuesConflictError, because a duplicate top-level YAML key silently discards the first block. A rejected non-fast-forward push simply retries from a fresh clone and converges.

GITclone → append → commit → push origin main · token scrubbed from every error
⏸

Wait for the DHCP scope

phase awaiting-dhcp-scope

Argo CD syncs the commit; the hostedclusters chart renders a Crossplane Request; Crossplane creates the scope on the DHCP server. The workflow observes, read-only — polling the DHCP API on durable timers until the scope exists with exactly the range it wrote.

Poll loop — machine convergence, so the wait is BOUNDED
  1. get_dhcp_scope → GET /api/v1/scopes/{network}; a 404 is a normal “not yet”, never an error.
  2. Scope found and startRange/endRange match the block → done.
  3. Every 15 s on a durable workflow.sleep timer, up to 15 minutes.
  4. Deadline exceeded → DhcpScopeNotConverged. The commit stands — check the Argo Application and the Crossplane Request.

Why poll instead of POSTing the scope? Posting would make two writers for one resource: Crossplane keeps reconciling from git, so any disagreement (exclusion order, the derived gateway) becomes a PUT every 60 seconds, forever. Read-only observation keeps git the single source of truth, Crossplane the only writer — and needs no write credential.

✓

Done

phase completed

The result carries the segment, VLAN, EPG, the commit sha (or null on a no-op re-run), and dhcp_scope_ready: true.

What gets written

The block appended to <cluster>.yaml

One blank line always separates the file's last content line from the marker; an empty file gets the marker as its first line. Everything else the DHCP stack needs — leaseDurationDays, dns, subnetMask, failover — is inherited from the upstream values layers; scopeName derives from the file name.

YAML sites/<site>/mces/<mce>/hostedClusters/<cluster>.yaml 
description: "prep workers"
                                  <- blank line, always present
# === Added By Segment-Allocation Workflow ===
vlanId: 23                        // audit only — no chart reads it

dhcp_values:
  network: "10.20.90.0"           // mask stripped — the scope's identity
  startRange: "10.20.90.11"       // derived: first non-excluded octet
  endRange: "10.20.90.240"        // derived: last non-excluded octet

  exclusions:                     // ascending — required by the DHCP API
    - startAddress: "10.20.90.1"
      endAddress: "10.20.90.10"
    - startAddress: "10.20.90.241"
      endAddress: "10.20.90.254"

⚠ The DHCP block assumes a /24 — asserted, not silent

DHCP_EXCLUSION_OCTET_RANGES (the ONE policy knob, e.g. [[1,10],[241,254]]) speaks in last-octet values, and startRange/endRange derive from it: every host octet of the /24 that is not excluded is distributable. A non-/24 segment is rejected with UnsupportedSegmentPrefix rather than mis-rendered with half its addresses stranded.

Supporting another mask is a deliberate refactor, not a config change — it must also start emitting subnetMask and gateway, since the DHCP stack derives the .254 gateway for a /24 only and rejects any other mask without both keys explicit.

⚠ HC segments only

Any other segment type is rejected up front with UnsupportedSegmentType — the values-repo layout only defines file locations (and therefore sites and DHCP scopes) for hosted clusters. Future types will arrive as their own functions, not as flags on this one.

Why one knob instead of three

Deriving the range from the exclusions removes the class of bug where the two contradict each other — and a mid-range exclusion like [100,110] still yields .11–.240 with a hole punched in it, exactly how DHCP scopes work.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async: the run outlives the request by design.

POST /workflows/segment-lifecycle/allocate-segment 202 · 409 if already running

The body names the cluster, nothing else — the site is derived from the values repo, the segment is whatever the Segments Manager reserves.

// request
{
  "cluster": "ocp4-prep-herzi-site1-a",
  "type":    "HC"                  // optional — HC is the default and the only supported value
}

// 202 response
{ "workflow_id": "allocate-segment-HC-ocp4-prep-herzi-site1-a", "run_id": "…" }

The id carries the type on purpose. Allocation is scoped by (cluster, site, type) — one cluster can hold one segment per type at a site — so a type-less id would make two legitimate allocations collide. Re-triggering while a run is in flight answers 409.

GET /workflows/runs/{workflow_id} 200 · 404 if unknown id

When things go wrong

Outages are out-waited. Real errors stop the run.

Same rule as every workflow here: retries are unbounded (1 s → doubling → capped at 1 min), so a Segments Manager, git-remote or DHCP-API outage never fails a run. Retrying stops only for errors explicitly classified as permanent — with one deliberate exception: the DHCP wait itself is bounded, because it is machine convergence, not human approval.

Classified as permanent — these fail the run

  • UnsupportedSegmentType — not HC (workflow-raised, before anything runs)
  • ClusterFileNotFoundError — no <cluster>.yaml in the values repo
  • AmbiguousClusterFileError — more than one <cluster>.yaml
  • UnknownSite — the file's site isn't in GET /api/sites
  • SegmentValidationError — the Segments Manager rejected the request (e.g. bad cluster name)
  • SegmentPoolExhaustedError — no Available segment of that type at the site
  • AllocationNotConfirmed — the read-back didn't match the allocation
  • ClusterValuesConflictError — the file already carries a different allocation
  • UnsupportedSegmentPrefix / InvalidSegmentCidr — the pool handed back a non-/24
  • DhcpScopeNotConverged — the bounded 15-minute DHCP wait expired
  • SegmentsManagerAuthError · SegmentNotFoundError

Transient by classification

ValuesRepoGitError (any git failure, including a rejected non-fast-forward push — the retry re-clones and converges) and DhcpApiError (the DHCP API failing; a scope that simply doesn't exist yet is NOT an error). Both retry forever; an unclassified permanent error shows as a run stuck RUNNING in the Temporal UI — the fix is to classify it, not to add a deadline.

Nothing to clean up

On failure or cancellation there is deliberately no compensating cleanup: the allocation is kept — a re-run idempotently reclaims it and converges the git write — and unlike open-segment-rules there is no pending-request display to clear.

Operating it

What happens if you run the same cluster again

Idempotency is a rule of the orchestrator — see the three rules that surprise people. Here it is unusually cheap: a full re-run converges with no human in the loop at all.

Re-run after completion — everything converges

The Segments Manager returns the same allocation (idempotent per cluster/site/type), the values file already ends in the identical block so nothing is pushed (values_updated: false, commit_sha: null), and the DHCP scope already exists so the wait finishes on the first poll.

The one thing a re-run will not do

Fix a conflict. If the values file carries a different allocation — an edited marker block, or a hand-written dhcp_values — every run refuses with ClusterValuesConflictError until a human reconciles the file. That is the point: the workflow must never guess which of two allocations is the real one.
