uninstall-server — what actually happens

One request takes one named server all the way out of an MCE, whatever state it is in — what an operator otherwise does by hand from the console’s host list: take the node out of its hosted cluster, then Remove host.

A node of a hosted cluster: the run deletes its Machine itself — nothing has to be done first — then CAPI drains the Node, the Agent provider releases the Agent and the host reboots into discovery. An inventory host (Agent Available) has no hosted-cluster half. Then, for both, remove-server runs as an awaited child: power off, then delete the NMStateConfig, the BareMetalHost with its BMC Secret, and the Agent. Both cases, step by step.

With "keep_inventory": true it stops after the hosted cluster: the server stays in the MCE’s inventory as a free Agent, as the console’s Remove from the cluster leaves it. How.

When a HyperShift deletion broke half-way — an AgentMachine with no Machine, a Machine with no AgentMachine, a Node with neither — it finishes what the controllers could not, and checks that every one of them is gone before the server leaves the MCE. How.

The way in is install-server.

What happens to your server

Two cases, end to end

The run picks the path from what it finds on the MCE, never from a field in the request. Nothing has to be done to the server first — no scale-down, no annotation, no Machine already deleting.

A node running in a hosted cluster

Its Agent is bound to the hosted cluster, an AgentMachine and a Machine stand behind it, and its Node is Ready.

  1. Reads server-scan and the MCE, and finds the server’s Node in the hosted cluster. Nothing is written.
  2. Locks the server in server-scan.
  3. Deletes the Machine — DELETE machines/<machine> in the control-plane namespace, the run’s own write.
  4. CAPI drains the Node: cordon, then evictions that respect PodDisruptionBudgets (20 min).
  5. The Agent provider releases the Agent, the host reboots into the discovery image, and CAPI removes the Machine and the Node (1 h, until the Agent is known-unbound).
  6. Verifies that no Machine, AgentMachine or Node is left and that the Agent is clean.
  7. remove-server — exactly as for an inventory host →

An inventory host — Agent Available

A BareMetalHost, an NMStateConfig and an unbound Agent in the InfraEnv — the host the console offers Remove host for.

  1. Reads server-scan and the MCE: no AgentMachine names the Agent, no Machine is linked to it (owner, infrastructureRef or providerID agent://<agent>), no binding. So the hosted-cluster half is skipped and named in skipped.
  2. Locks the server in server-scan.
  3. Checks again, fresh, right before removing it: still no AgentMachine, no Machine, no binding. An Available Agent is free for any NodePool to take at any moment; if one took it, the run stops (AgentRetakenError) and touches nothing.
  4. remove-server, awaited:
    1. power off — spec.online: false on the BareMetalHost, then wait for status.poweredOn: false (10 min). A host left running discovery would register a new Agent within a minute;
    2. delete the NMStateConfig nmstate-config-<server>;
    3. delete the BareMetalHost — marked detached first, so metal3 does not try to deprovision it through the BMC — and its BMC Secret if that outlives the host;
    4. delete the Agent, last;
    5. clear the host’s MACs from its site’s PXE VM;
    6. verify that no BareMetalHost, NMStateConfig or Agent of it is left (5 min).

"keep_inventory": true — out of the hosted cluster, still in the inventory

Everything up to the end of the hosted-cluster half runs exactly as above — Machine deleted, Agent released and back in discovery, Machine, AgentMachine and Node verified gone, the Agent verified known-unbound and approved — and the lock is held for a day. Then the run stops: no remove-server. The host stays powered on in discovery, a free Agent of the InfraEnv; its BareMetalHost, NMStateConfig, Agent and PXE mapping are left as they are. The result says kept_in_inventory: true, with remove_server: null.

On a server that is already only inventory there is nothing to do: the run completes after its reads, with no lock and nothing written. Being a free Agent, a kept server is one any NodePool may take next — including the replacement for the Machine just deleted, when it is the only one. The default, false, takes the server out of the MCE too.

NodePool replicas are never changed — so a node is replaced

The NodePool still wants the same number of nodes, so it creates a new Machine as soon as the old one is deleted, and the Agent provider binds it to another free Agent the NodePool matches. The hosted cluster keeps its size, on a different server; this one leaves the MCE.

Shrinking a hosted cluster needs someone to own NodePool.spec.replicas. That is not decided, so this run never touches them.

When this server is the only free Agent

The new Machine takes any free Agent the NodePool matches — this server’s too, once it is released. The run then stops with AgentRetakenError, naming the new AgentMachine, and writes nothing more: releasing the Agent again would pull out a node the provider is installing. Free another Agent the NodePool matches, or lower its replicas, then re-run.

A Machine someone else already started deleting is not deleted again: the run waits for it and records the no-op in skipped.

How the path is chosen

By the binding it observes — never by a state string

The run inspects the host once and picks one of two shapes. A third case — nothing of the server on the MCE — is not a path of its own: the child finds nothing and completes with found: false.

When HyperShift leaves things behind

Every finalizer’s job is checked, and done where its owner cannot

Each object here is normally cleaned up by a finalizer or a hook: CAPI drains and deletes the Node through the Machine; the Agent provider unbinds the Agent through its hook on the Machine and its finalizer on the AgentMachine. A deletion that broke half-way leaves exactly the shapes where that chain cannot run any more, and then nothing ever finishes it. So the run never assumes the chain worked.

Checked, never assumed

Before remove-server starts, each is re-derived fresh, not from what inspection saw — for an inventory host too, whose free Agent any NodePool may take:

  • no Machine — by the AgentMachine’s owner, an infrastructureRef, or the providerID;
  • no AgentMachine names the Agent — by status.agentRef or the Agent’s label;
  • no Node is the server — by providerID, nodeRef, hostname or the server’s name;
  • the Agent is unbound, unlabelled, known-unbound and approved.

Said, every time

The result’s leftovers_at_start lists what HyperShift had left, in words, and cleaned_up every write the run made on a controller’s behalf — each with why that controller could not.

Only the Agent provider’s own hook and finalizer are ever removed, and only once their one job — the unbind — is done. Two Machines, two Nodes, or links into two control planes are refused (ConflictingHostedObjectsError): the run cannot tell which is real.

Seven steps, in order

What the run does

Each card carries a phase, read live off the running workflow through its progress query — with a sub_phase while it waits for the Machine, and the Agent’s last agent_state.

1

lookup_server_membership

phase checking-inventory

server-scan is the authority on where a server is. The run reads its record by exact name: a search narrows, the server’s own document confirms the name (case-insensitively) and carries openshift.{lifecycle_state, cluster_name, mce_name, contested_with}, maintenance and the srv_… id the lock is keyed on. Never /servers/available, which hides exactly the claimed and reserved machines an uninstall is about.

GET/servers?search=<name>
GET/servers/{id} · per exact-name hit

Refused only on a contradiction, with nothing written: an unknown name (no lock could be taken on it), a record contested_with another claim, or one placing the server on another MCE (compared with or without ocp4-). AVAILABLE is accepted — it is what an unbound host often reads as between membership runs. Maintenance is logged, not refused.

2

inspect_bound_host

phase inspecting

Reads only. The BareMetalHost <server>; the host’s Agents, matched by BMAC’s bmh label or by any MAC (the BMH’s, the NMStateConfig’s, server-scan’s); for each, its binding, status.debugInfo.state, hostname and the AgentMachine behind it. For the one hosted Agent: its Machine by any link — the AgentMachine’s owner, an infrastructureRef naming it, or the providerID agent://<agent> — with its deletionTimestamp, nodeRef, pending delete hooks, deletion conditions and whether its AgentMachine still exists; and the HostedCluster its links point into. The Node name is captured now: the Machine is about to go.

LISTagentmachines.capi-provider.agent-install.openshift.io · all namespaces
LISTmachines.cluster.x-k8s.io · all namespaces
GETmachines.cluster.x-k8s.io · the AgentMachine’s owner, by its own apiVersion
LISThostedclusters.hypershift.openshift.io · all namespaces

Refused here, still with nothing written: two bound Agents (MultipleBoundAgentsError); a binding into no HostedCluster’s control plane with nothing behind it, or links into a namespace no HostedCluster uses (NotHostedClusterNodeError); two Machines, or links into two control planes (ConflictingHostedObjectsError); server-scan naming another cluster than the Agent’s, or reading INSTALLED_TO_INVENTORY while the Agent is bound (ClusterMembershipMismatchError). An INSTALLED record that has not caught up with an unbinding is not a contradiction — an unbound Agent names no cluster, and that is a re-run’s normal view.

3

find_hosted_nodes

phase checking-hosted-node

Reads only, through the hosted cluster’s admin kubeconfig: which Node is this server — by CAPI’s own providerID agent://<agent>, or by name (the Machine’s nodeRef, the Agent’s hostname, the server’s own name) when the Node carries no other providerID. With nothing on the MCE linking the host, it looks in the cluster server-scan says the server is INSTALLED in — the only trace left of a Node whose Machine, AgentMachine and binding are all gone.

LIST/api/v1/nodes · on the hosted cluster

Refused here, nothing written: two Nodes that are the server (ConflictingHostedObjectsError), or a Ready Node nothing on the MCE links any more — there is nothing to take the host out of it through (HostedNodeStillPresentError; drain it and power the host off, then re-run).

4

reserve_server

phase reserving-server

server-scan’s install lock, holder uninstall-server and this run’s workflow id, taken always and before the first write. Its TTL covers the whole hosted-cluster half — a lost Node’s 20-minute drain, the Machine’s 20-minute drain, the 1-hour reboot, three 5-minute verifications and a margin: 2 h 5 min. Why an uninstall needs a lock at all is below.

POST/servers/{id}/reservation

A lock another run holds fails the run here (ServerReservedError), nothing changed. The common case is install-server’s day-long hold after it installed the machine: release that hold in server-scan, then re-run.

5

the hosted-cluster half

hosted nodes, and what is left of one

An inventory host has none of this but its last check: verifying-agentmachine inspects it again, fresh, with the same links as step 2 — an Agent now bound or held by an AgentMachine fails AgentRetakenError, any other AgentMachine, Machine or control-plane link ServerStillPresentError, with nothing on the MCE written.

draining-node — only for a Node no Machine stands behind, which nothing else will drain: cordon it, then evict every Pod CAPI’s drain would (all but DaemonSet and mirror Pods) through the Eviction API, pass after pass every 30 s. 20 minutes, else NodeDrainTimeoutError naming the Pods left and why. A NotReady Node is not drained, as CAPI skips an unreachable one.

deleting-machine — ensure_machine_deleting, the run’s own DELETE of the Machine. That is the normal case: a running node’s Machine has no deletionTimestamp until this step gives it one. A Machine someone else already started deleting (an operator, an earlier run) or one already gone is left alone and named in skipped.

awaiting-machine-deletion — every 30 s, until the Machine is gone and the Agent is known-unbound, in two sub-phases with their own clocks, each started when this run first sees it:

  • draining while the Agent is still bound — pre-drain hooks, the Node drain, volume detach. 20 minutes, else MachineDrainTimeoutError.
  • unbinding once the Agent is released — the host reboots into the discovery image, on bare metal the same POST-and-boot install-server allows an hour for. 1 hour, else AgentUnbindTimeoutError (or MachineDeletionTimeoutError if the Agent is free but the Machine never went).
  • releasing when the provider cannot release it: no Machine is left, or the Machine waits at its pre-terminate hook with its AgentMachine gone. The run makes the provider’s own unbind of the Agent, and — once the Agent is in a state the provider itself would release in — removes the provider’s hook from the Machine.

Every pass also checks that no other AgentMachine holds the Agent. One that does is the NodePool’s replacement Machine taking this same server (above): the run stops with AgentRetakenError and writes nothing more. The release itself refuses an Agent a live Machine holds, too (AgentBindingChangedError).

verifying-agentmachine — re-derived fresh: no AgentMachine names the Agent. One with no Machine is deleted; one stuck deleting on the provider’s finalizer (it drops it only through a Machine) has that finalizer dropped after a minute; a Machine still linked fails the run (5 min, polled every 10 s). verifying-node — no Node of the hosted cluster is the server: a stale one, NotReady with no Machine left to delete it, is deleted; one still Ready fails the run (5 min). verifying-agent — unbound, no agentMachineRef label, known-unbound, approved, its BareMetalHost present and not in error (5 min): what remove-server needs to power it off and take it.

EVICTpods/eviction · a lost Node’s Pods, on the hosted cluster
DELETEmachines.cluster.x-k8s.io/<machine> · unless already deleting
PATCHagents/<agent> · the provider’s unbind, only when it cannot
PATCHmachines/<machine> · the provider’s hook off, only when its AgentMachine is gone
DELETEagentmachines/<am> · one with no Machine
DELETE/api/v1/nodes/<node> · a stale Node, once NotReady

Every failure after the delete leaves things as they are — a Machine delete cannot be undone — and a re-run of the same id resumes: it finds the Machine deleting and skips the write.

6

reserve_server, again

phase holding-server

The lock extended to 24 hours — the ceiling server-scan accepts, and install-server’s precedent — before the child starts, so the hold covers the inventory half too and outlasts the membership jobs that will report the machine free.

Refused now (the lock lapsed and another run took the machine), the run logs it, reports reservation_expires_at: null and still removes the host: it must not stay in this InfraEnv either way.

Held with keep_inventory too: the server stays in this InfraEnv, and server-scan may read it AVAILABLE until the MCE’s agents job reports it INSTALLED_TO_INVENTORY. With it, the run ends here.

7

remove-server, as a child

phase removing-from-inventory

execute_child_workflow on remove-server-<server> and its own queue, awaited; its RemoveServerResult is embedded in this run’s result. This is where the server leaves the MCE, for a hosted node and an inventory host alike — remove-server’s own rules, unchanged:

  1. powering-off — spec.online: false, then status.poweredOn read until false (10 min, else HostPowerOffTimeoutError with nothing deleted). It re-checks right before that no Agent of the host is bound.
  2. removing-host — the BareMetalHost annotated detached, the NMStateConfig deleted, the BareMetalHost deleted and waited on (a stuck metal3 finalizer is dropped), and its BMC Secret deleted if it outlives the host.
  3. removing-agent — the Agent deleted last: nothing can boot the host into discovery to re-register it any more.
  4. removing-pxe-boot — every MAC the host is known by, cleared from its own site’s PXE VM (best effort).
  5. verifying — no BareMetalHost, NMStateConfig or Agent of it left (5 min, else ServerStillPresentError).
PATCHbaremetalhosts/<server> · spec.online: false, then annotation detached
DELETEnmstateconfigs/nmstate-config-<server>
DELETEbaremetalhosts/<server>
DELETEsecrets/<bmc secret> · only if it outlives the host
DELETEagents/<agent>
DELETE/pxe-map/<mac>?mce_cluster=<mce> · on the site’s PXE VM

Nothing of the server on the MCE is its found: false, and this run completes. Never started with keep_inventory.

Parent-close policy ABANDON: closing this run never cuts the child off between its power-off and its deletes. A remove-server already running on that id fails this run (RemoveServerAlreadyRunningError, naming it); a child that fails fails it too (RemoveServerFailedError, carrying the child’s own error).

When it stops

Refused before anything is written, or stopped after the Machine

Every one is a FAILED run on the status endpoint, never a 4xx on the trigger, and its message says what to do. Nothing is ever undone.

Refused — nothing changed

errorwhen
ServerNotInServerScanErrorserver-scan has no server of that exact name, so no lock can be taken on it. A host that is only on the MCE is remove-server’s.
ClusterMembershipMismatchErrorserver-scan contradicts the request or the MCE: the server is on another MCE; INSTALLED in another cluster than the one the Agent belongs to; INSTALLED_TO_INVENTORY while the Agent is bound (its agents job re-reads the MCE every 15 min — re-run once it agrees); or contested between two claims.
MultipleBoundAgentsErrorMore than one of the host’s Agents is bound, or has an AgentMachine. One machine is one node.
NotHostedClusterNodeErrorAn Agent bound into no HostedCluster’s control plane with no AgentMachine or Machine behind it (ACM/ZTP); links into a namespace no HostedCluster uses; or an Agent bound to a ClusterDeployment other than its AgentMachine’s or Machine’s hosted cluster.
ConflictingHostedObjectsErrorTwo Machines linked to the Agent, two Nodes that are the server, or links into two control planes. The run cannot tell which is real.
HostedNodeStillPresentErrorA Ready Node of the hosted cluster is the server, but nothing on the MCE links it any more — no Machine, AgentMachine or binding to take the host out through. Drain it and power the host off (or boot it into discovery), then re-run: the stale Node is deleted then.
ServerReservedErrorAnother run holds server-scan’s lock — typically install-server’s day-long hold. Release it in server-scan, then re-run.
AmbiguousServerNameErrorTwo server-scan documents carry the name.

Transient trouble is retried without bound, as everywhere in this repo: server-scan unreachable, the MCE’s API, and a hosted API server that cannot be reached (HostedClusterUnreachableError). A hosted cluster whose admin kubeconfig cannot be used is permanent (HostedClusterAccessError).

The window it closes

Why an uninstall takes server-scan’s install lock

Two jobs see the machine, neither sees the whole move

The hosted cluster’s nodes job frees the server the moment its Node disappears. The MCE’s agents job re-claims it as INSTALLED_TO_INVENTORY on its own 15-minute cadence. Between the two the document can read AVAILABLE while the host is still in this MCE’s InfraEnv — and another MCE’s install-server would draw it, putting two clusters on one BMC.

Taken first, held a day, never released by a failure

Taken before the first write, with a TTL covering the hosted-cluster half; extended to 24 h before the inventory half; on a failure left to its TTL, because the host may still be half-way out.

The flip side of the day-long hold: a machine uninstalled now is not drawable by install-server for a day, unless someone releases it in server-scan.

Reading a Node

How the run reaches the hosted cluster — and what it never keeps

The admin kubeconfig, pointed at the in-cluster Service

The worker reads the Secret the HostedCluster names in status.kubeconfig (in the HostedCluster’s namespace, key kubeconfig) and replaces its server with the control plane’s Service on the MCE, https://kube-apiserver.<hc-ns>-<hc>.svc:6443. The kubeconfig names the external endpoint, which the pod network may not reach; the Service always is reachable from the MCE, and the API server’s certificate covers it, so TLS is still verified — against the kubeconfig’s own CA.

The limb parses the kubeconfig itself and writes the CA, certificate and key into a per-call temporary directory that is deleted when the call returns — the Kubernetes client’s own loader caches those files for the life of the process. Nothing from the kubeconfig enters an error, a log line or workflow history; errors name the hosted cluster and what was wrong.

Read off the upstream code

Two facts the design had to be corrected for

Neither shape is documented as an API; both were taken from the code that writes it, and both changed what the run does.

The binding names the control-plane namespace

HyperShift creates the AgentCluster — and through it the ClusterDeployment an Agent binds to — in the hosted control-plane namespace, named after the HostedCluster (hypershift-operator/…/platform/agent/agent.go; cluster-api-provider-agent’s AgentCluster controller). So an Agent’s clusterDeploymentName.namespace is <hc-ns>-<hc>, never the HostedCluster’s own namespace.

The HostedCluster is found by HyperShift’s own rule — <namespace>-<name with dots as dashes> (pkg/manifests.HostedControlPlaneNamespace) — matched against a list of HostedClusters, because clusters-a-b could be clusters/a-b or clusters-a/b. Hence list on hostedclusters, not just get.

The provider releases the Agent before the Machine is gone

On a Machine deletion, cluster-api-provider-agent clears the Agent’s clusterDeploymentName, its agentMachineRef label and namespace annotation first, then holds the Machine on pre-terminate.delete.hook.machine.cluster.x-k8s.io/agentmachine until the Agent reaches an unbound state (controllers/agentmachine_controller.go).

For that whole stretch only the AgentMachine’s status.agentRef still links the two. So “a hosted node” includes an AgentMachine whose agentRef names the Agent — otherwise a re-run mid-unbinding would read an inventory host and skip straight to remove-server.

The provider unbinds only through a Machine

Its whole unbind lives in handleDeletionHook, which runs only for an AgentMachine whose owner Machine exists and has reached its pre-terminate hook. An AgentMachine whose owner is gone has its agentmachine.agent-install.openshift.io/deprovision finalizer dropped without the unbind; one with no owner at all keeps it for ever.

That is why a half-deleted node never finishes on its own, and why the run makes the provider’s write itself — the same fields, with the resourceVersion it read.

The providerID ties the Machine and the Node

The provider sets the AgentMachine’s — and so the Machine’s — spec.providerID to agent://<agent name>, and CAPI links a Machine to the Node whose spec.providerID matches. The Node registers under the Agent’s hostname (spec.hostname, else the discovered one).

So a Machine whose AgentMachine is gone is still found, and a Node with no Machine is still recognised as this server — never by a guess on its name alone.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async throughout: the POST hands back the workflow id at once and you poll it.

POST /workflows/server-lifecycle/uninstall-server 202 · 409 if that server is already uninstalling · 502 if Temporal refuses

Which machines, and on which MCE — nothing else. server_names is one name or a list of 1–20, each once (case-insensitively); mce_cluster is accepted with or without ocp4- and is needed because it names the activity queue of the worker inside that MCE; namespace (the InfraEnv’s, where the BMH and Agent live) defaults to inventory; keep_inventory (default false) stops the run after the hosted cluster, leaving the server in the inventory (above). The reply follows what was sent: one name is {workflow_id, run_id}, a list is a per-run report — even a list of one.

The body forbids unknown fields: there is no count, node_pool or hosted_cluster — server-scan and each Agent’s own binding say where a server is, and a caller-supplied cluster could only contradict them. Each is a 422, and so is server_name (singular), pointing at server_names.

One ClusterRole, cluster-wide because Machines live in each control-plane namespace and kubeconfigs in each HostedCluster’s — neither an InfraEnv namespace, neither named in the request. Rendered by rbac.hostedClusters (default true); off, any host with an Agent fails its inspection with a 403 before anything is written, so use remove-server on such an MCE. The worker’s pods also need network access to each kube-apiserver.<hc-ns>-<hc>.svc:6443 — check NetworkPolicies on the control-plane namespaces if verifying-node keeps retrying HostedClusterUnreachableError.

Roll the limb out first. CI ships the brain before the limb, and a brain that reaches activities an old limb does not register retries them until it does — the run sits in checking-inventory. Upgrade each MCE’s server-lifecycle-worker and apply its ClusterRole before using this route. Production’s chart is vendored in redbull-platform (gitops/charts/server-lifecycle-worker/) and needs the same ClusterRole there.

What it never does

  • No NodePool or replicas change — who owns replicas is not decided (above).
  • No fight with the NodePool — an Agent its replacement Machine took is left to it.
  • No drain or Node delete where CAPI can still do it — only for a Node no Machine stands behind, and a Node is deleted only once NotReady.
  • No finalizer or hook of anyone but the Agent provider’s, and those only once its unbind is done.
  • No PXE map write — the PXE cleanup stays in remove-server.
  • No undo — a Machine delete cannot be undone, so a failure leaves everything as it is and a re-run resumes.
