create-upi-cluster — what actually happens

You send a name, a site and a kind (mce or standalone). The run allocates the cluster's segments, runs the team's bootstrap-installer as two Jobs on the hub (prepare, install), waits until the cluster serves, registers it in the hub's Argo CD — and, for an MCE, opens the merge request adding it to day1's MCEs and waits for a person to merge it. This is the operator's "Creation MCE 4.20" runbook, steps 1–9, end to end.

The run, step by step

From a name to a cluster Argo CD manages

Each card carries a phase, read live through the run's progress query on GET /workflows/runs/{workflow_id}.

1

allocate-segment — awaited children

phase allocating-segment

The node network: an MCE segment for an MCE (kind: mce, the default), a UPI segment for a standalone cluster. An MCE also gets its INVENTORY segment — the BareMetalHost boot network add-server-to-mce resolves by the MCE's name. Each is allocate-segment as a child on its own id (allocate-segment-<TYPE>-<cluster>), idempotent per (cluster, site, type).

2

run_installer_step(prepare) — a Job on the hub

phase preparing

The upi-provisioning worker writes the cluster's work volume (upi-<cluster>-work, kept for ever: terraform's state), its cluster YAML (upi-<cluster>-config: your install_config plus the run's keys — segment, VLAN, port group, secret paths) and the Job upi-<cluster>-prepare-<token> running bootstrap-installer (bootstrap.py --skip-terraform --skip-argocd): the IPs from the segment (infra .1–.3, masters .4–.6, bootstrap .7, gateway .254 unless the site profile says otherwise), install-config, the v4InternalSubnet CR, the ignition configs and the *.apps DNS record. The Job then stores the admin kubeconfig and the node IPs in upi-<cluster>-kubeconfig. A volume whose terraform state still lists VMs is refused — destroy the cluster first.

K8SPVC, ConfigMap, Job in the worker's namespace · the Job polled every 15 s, heartbeating
3

run_installer_step(install)

phase installing

Job upi-<cluster>-install-<token>: bootstrap.py --skip-ignition --skip-dns --skip-argocd — terraform apply of the VMs and their DNS records (the script answers its "yes" prompt) and bootstrap-installer's own CSR loop. A loop that times out exits 0, so the next step decides.

4

await_upi_cluster_ready

phase verifying-cluster

As the cluster's admin: every 20 s, approves pending CSRs of a node bootstrapper or a system:node:* user, reads the Nodes and ClusterVersion. Done when every recorded node IP is a Ready Node and ClusterVersion is Available with a version. Up to 2 h, its clock in the heartbeat.

K8Sthe new cluster's API (its kubeconfig's own server and CA)
5

register_upi_cluster_in_argocd

phase registering-argocd

bootstrap-installer's registration, as the worker: kube-system/argocd-manager, its token Secret and a cluster-admin binding on the cluster; on the hub, the Argo CD cluster Secret cluster-<cluster> with name: <cluster> — the destination name the hub's ApplicationSets target — read back. A Secret of that name for another server is ArgoClusterSecretConflictError.

6

publish_mce_folder → merge request → a person merges (MCE only)

phase publishing-mce-folder / opening-merge-request / awaiting-merge

The MCE joins day1's list of MCEs: sites/<site>/mces/<cluster>/values.yaml (your mce_values, or a header only) and version.yaml (mastertag: the installed version) on create-upi-cluster/<cluster>, through the cluster-lifecycle limb; its merge request; and a human wait for the merge, polled every 5 min, no deadline. Once merged, the hub's <site>-mces ApplicationSet makes the MCE's Application with the cluster as destination, and from there its own Argo CD deploys day2 in-cluster. Already at main with this content (a re-run past the merge): nothing pushed, no merge request.

GET /workflows/runs/create-upi-cluster-ocp4-prod-mce-tlv-a

A 422 for a name bootstrap-installer refuses, install_config setting a key the run owns (cluster_name site segment vlan_id vm_network pull_secret_path additional_trust_bundle_path ssh_public_key_path terraform_dir argocd_*), or mce_values on a standalone cluster. A second request while the run goes is a 409. The API has no auth: this route creates VMs.

Failures — outages are out-waited, real errors stop the run

  • AllocateSegmentFailedError / AllocateSegmentAlreadyRunningError — the child's own type in the message.
  • InstallerConfigRejectedError — a run-owned key, or a site with no profile in the sites ConfigMap.
  • InstallerJobFailedError — a Job failed; its last log lines are in the message. Read the Job's log, fix, destroy what terraform made if the install failed, start again.
  • UpiClusterNotReadyError — 2 h after the install, a node not Ready or ClusterVersion not Available: named.
  • UpiClusterAccessError, HubAccessError — a missing kubeconfig Secret, a 403, a TLS failure.
  • ArgoClusterSecretConflictError, MceFolderConflictError, Day1SiteNotFoundError — never overwritten.
  • MergeRequestClosedError — a person closed the merge request; the cluster stands, registered.
  • Anything transient (the hub's or the cluster's API, git, GitLab) is retried without end and shows on the activity.

Run it again

Inside one run nothing is done twice: every phase's outcome is in its state, kept across continue-as-new. A new run of the same cluster re-allocates idempotently and makes new Jobs (the run's token is in their names); its prepare refuses a work volume whose terraform state still lists VMs, so a failed install is destroyed (bootstrap.py --destroy against that volume) before it is created again. Past the merge, a re-run finds the folder at main and opens nothing.

Not this run's

The bootstrap VM is not removed (bootstrap-installer has no step for it). Workers are added by add-server-to-upi. Nothing is ever destroyed.

Dependencies

  • upi-provisioning-worker (hub, deploy/charts/upi-provisioning-worker): INSTALLER_IMAGE (bootstrap-installer main), the install Secret, the sites ConfigMap, Argo CD's namespace.
  • cluster-lifecycle-worker: the day1 token and GitLab merge requests (publish_mce_folder).
  • segment-lifecycle-worker: the Segments Manager, through allocate-segment.
