open-segment-rules — what actually happens

A single request creates a network segment in the Segments Manager, sends a request to NEXT to open every firewall rule it needs against its same-site neighbours, waits for a human to approve those rules — for as long as that takes — and only then flips the segment from Locked to Available.

One segment = one durable Temporal run, from creation to unlock.

The run, step by step

From “create this segment” to “segment is Available”

Five stages, left to right. The colour of each box is the system it talks to, and the segment stays Locked the whole way across until the last one. The cards underneath expand each numbered stage — what it calls, what it returns, and why it's built that way.

Segments Manager NEXT Stages 1–5 all run inside one Temporal workflow; each is a retried activity.

The same run, in detail

Each card carries a phase — the workflow's own progress marker, held in the workflow object and updated as it moves between stages. It is not a Temporal status (those are RUNNING, COMPLETED, FAILED); it is read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run a segment currently is.

✓

Type check

phase pending

Runs before anything is created. Supported types are HC, INVENTORY, PXE, MCE — anything else fails the run immediately with UnsupportedSegmentType. Nothing exists yet, so there is nothing to clean up.

1

create_segment

phase creating-segment

The workflow creates the segment itself — the Segments Manager is a dependency, never the trigger. The segment is born Locked. This call is also what validates the definition (site, CIDR, overlap, VLAN): a bad definition surfaces here as a FAILED run, not as a 4xx on the trigger.

POST/api/segments · Bearer
GET/api/segments/by-segment?segment=… · only on 400/409/422, to tell “already created” from “invalid”

Safe to run twice. Temporal retries this call, so “that CIDR already exists” must not be an error. When the create comes back rejected, the activity sends a second request — GET /api/segments/by-segment?segment=… — to see whether the segment is in fact already there, and decides from what comes back: if it matches the definition you sent, it counts as done and the run continues; if the CIDR exists with a different type, site, VLAN or EPG, it's a real clash and fails with SegmentConflictError; if it isn't there at all, the definition itself was rejected. dhcp isn't compared — it's editable after creation, so a changed value is a legitimate edit, not a clash.

When does that actually happen? Mostly when the create succeeded but this side never found out: the response was lost, the worker was killed mid-call, or the activity timed out after the Segments Manager had already committed. It also covers an operator re-triggering a segment an earlier run created, and a segment somebody created by hand in the Segments Manager before running this.

2

list_peer_segments

phase listing-peer-segments

Finds every same-site segment this type must peer with. Which types those are isn't hardcoded — it's derived from the configured PORTS_<SRC>_TO_<DST> profiles. The port policy is the peering topology.

GET/api/segments?type=<PEER_TYPE> · one per peer type, filtered to site in code
2b

get_bmc_segment MCE only

MCE segments also need a rule to their site's BMC network. BMC isn't tracked by the Segments Manager, so this is a pure config lookup from the shared SITE_NETWORKS topology. Resolved before any submission, so a missing site fails cleanly instead of halfway through.

CONFIGSITE_NETWORKS[<site>].bmc · missing → BmcSegmentNotConfiguredError
3

submit_open_rules × N

phase submitting-rules

Two requests per peer — one in each direction — plus one MCE → BMC request if the segment is MCE. All submitted in parallel. Each submission renews a token to NEXT first, then posts the rule with the port profile for that direction. NEXT answers with a request id.

POST$NEXT_URL$NEXT_TOKEN_RENEWAL_URI · fresh token per call
POST$NEXT_URL$NEXT_OPEN_RULES_URI · → { id, status }

Zero submissions (no same-site peers found) is a hard failure: NoPeerSegments. A segment with nothing to connect to is a mistake, not a no-op.

4

publish_request_ids

Mirrors the pending NEXT request ids into the Segments Manager UI (behind the segment's “Requests ID” button), together with submitted_at so the UI can show elapsed time. Replace-semantics PUT — republished every time the pending set shrinks, and finally with an empty list, which removes the display.

PUT/api/segments/segment-connectivity-requests · { segment, request_ids, submitted_at }
⏸

Wait for human approval

phase awaiting-completion

Somebody has to approve those NEXT firewall requests. That takes minutes, hours, or longer — so the workflow has no deadline here at all. It polls the request status on durable Temporal timers, which survive worker restarts and deploys.

Poll loop — repeats until nothing is pending
  1. Sleep NEXT_CHECKING_REQUEST_INTERVAL_SECONDS (read once per run via get_next_checking_request_interval).
  2. check_next_requests → GET $NEXT_CHECK_STATUS_URI/{id} for every pending id, concurrently.
  3. Statuses are pending or complete. Anything else fails the run loudly (UnexpectedRequestStatus).
  4. If the pending set shrank → republish the ids so the UI stays accurate.
  5. After 48 h of wall-clock time → continue_as_new, carrying pending ids + submitted_at, so history stays bounded no matter how long approval takes.
5

unlock_segment

phase unlocking-segment → completed

All rules open. The segment flips Locked → Available and the run returns its result. Already-unlocked counts as success.

POST/api/segments/unlock · { segment }
Who connects to whom

Peering matrix — one cell = one open-rules request

Read a row as the source. Every ✓ is a separate submission to NEXT with its own request id and its own approval. The matrix is not written in code — it is exactly the set of PORTS_* keys present in the ConfigMap.

bidirectional — a rule is opened each way one-way, MCE runs only

It works in both directions, by construction

Adding an HC segment discovers the site's existing MCE segments and opens HC↔MCE for each. Adding an MCE segment discovers every existing HC, INVENTORY and PXE segment on that site and opens all of those pairs. So a site converges to full connectivity whatever order segments are added in.

With one exception: a site needs its MCE segment first. HC, INVENTORY and PXE peer only with MCE, so on a site that has none there is nothing to open rules against — the run fails with NoPeerSegments rather than creating a segment nothing can reach.

How many requests will a run make?

2 × (same-site peers found), plus 1 if the segment is MCE (the BMC rule). A new HC segment on a site with 3 MCE segments submits 6 requests; a new MCE segment on a site with 2 HC + 1 PXE submits 7.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Starting is always async — approval is human-driven, so nothing here ever blocks on the outcome.

POST /workflows/segment-lifecycle/open-segment-rules 202 · 409 if already running

Body is the full segment definition — you are not referencing an existing segment, you are asking for one to be created and connected.

// request
{
  "segment":  "130.154.20.0/24",   // CIDR
  "type":     "HC",                // MCE | HC | INVENTORY | PXE
  "site":     "site-a",
  "vlan_id":  412,                 // 1–4094
  "epg_name": "epg-hc-412",
  "dhcp":     true                 // optional, defaults true
}

// 202 response
{ "workflow_id": "open-segment-rules-HC-130.154.20.0", "run_id": "…" }

Deduplication is free. The workflow id is derived from type + network address (the CIDR mask is dropped), so re-triggering the same segment while a run is in flight returns 409 instead of starting a second run.

POST /workflows/segment-lifecycle/open-segment-rules/bulk 202 · always

Takes { "segments": [ …definitions… ] } and starts one workflow per segment, never one batch workflow — each segment gets its own dedup id, its own approval, and its own failure. Row 7 being bad must not sink row 8.

// 202 response — a per-item report, not a single pass/fail
{
  "started": 2, "already_running": 1, "failed": 0,
  "results": [
    { "segment": "130.154.20.0/24", "workflow_id": "open-segment-rules-HC-130.154.20.0",

When things go wrong

Outages are out-waited. Real errors stop the run and get published.

The single most important rule: retries are unbounded. Every activity retries forever (1 s → doubling → capped at 1 min, 90 s per attempt), so a Segments Manager or NEXT outage never fails a run — it just waits. Retrying stops only for errors explicitly classified as permanent.

Classified as permanent — these fail the run

  • SegmentValidationError — the Segments Manager rejected the definition
  • SegmentConflictError — that CIDR exists with different attributes
  • SegmentNotFoundError — segment vanished mid-run
  • SegmentsManagerAuthError — 401/403; check SEGMENTS_MANAGER_API_TOKEN
  • BmcSegmentNotConfiguredError — site missing from SITE_NETWORKS
  • UnsupportedSegmentType · NoPeerSegments — raised by the workflow itself
  • PortProfileMissing · PeerTypesNotConfigured — a PORTS_* config gap
  • UnexpectedRequestStatus — NEXT reported something other than pending/complete

Anything unclassified retries forever

This is deliberate, and it has a diagnostic signature worth recognising: a run that is genuinely stuck on a permanent-but-unclassified error shows as RUNNING in the Temporal UI, not FAILED, with the error attached to the retrying activity. If you see that, the fix is to classify the error — not to add a deadline.

Timeout budget

HTTP client 60 s < activity start_to_close 90 s, so a hung connection fails the call and frees the worker before Temporal reaps it.

Terminal failure is surfaced, never silent

If a run fails after the segment exists — or is cancelled — a best-effort compensation step clears the pending-ids display and publishes an open-segment-rules workflow failed note carrying the orphaned request ids, so the segment isn't left looking Locked for no reason. The segment stays Locked on purpose: connectivity was never established.

PUT/api/segments/segment-connectivity-requests · { request_ids: [] } — clear the display
PUT/api/segments/segment-connectivity-failure · { segment, message }

Best-effort means best-effort: 3 quick attempts, and any error is swallowed so it can never mask the real failure. Note that terminating a workflow (as opposed to cancelling it) skips this cleanup entirely — prefer cancel.

Operating it

What happens if you run the same segment again

Idempotency is a rule of the orchestrator — see the three rules that surprise people in the guide. What it buys you here, and the one part that is not free, is worth being precise about.

Retried inside a live run — nothing is redone

A worker crash, a redeploy, a continue_as_new: finished steps are never re-executed. Temporal replays their recorded results from history, so NEXT is not asked to open the same rules twice and the approval you are already waiting on is not restarted.

And while a run is in flight there is no second run at all — the deterministic workflow id open-segment-rules-<TYPE>-<network> makes the trigger answer 409 (already_running in the bulk report).

A brand-new run costs a second approval

Trigger the same segment again after the previous run ended and it starts from step 1 with no memory of it. create_segment and unlock_segment no-op, and publish_request_ids is a replace-style PUT — but it will submit fresh open-rules requests to NEXT, with new request ids that need new human approval.

The firewall converges to the same state and the old ids are simply orphaned, so nothing breaks. It is not destructive — it is just slow, and it puts a human back in the loop.

Per-activity behaviour: create_segment accepts an existing segment that matches the definition and fails with SegmentConflictError only on genuine disagreement (dhcp excluded — it is editable after creation); unlock_segment treats "already unlocked" as success; submit_open_rules converges, worst case leaving an orphan request id nobody polls.
