add-server-to-mce — what actually happens

One request makes a physical server installable in an MCE InfraEnv: server-scan allocates the run one healthy, unclaimed machine matching that InfraEnv — locked for it and live-checked — and the workflow picks two NICs for a bond and creates the three Kubernetes resources the Assisted Installer needs: a BareMetalHost, its BMC Secret and an NMStateConfig.

It replaces bmh-generator-operator (BareMetalHostUCS), a Kopf operator that queried HP OneView, UCS Central, Dell OME and Intersight live on every reconcile. server-scan already collects all of that on a 6-hour cron, so one HTTP call replaced four vendor SDKs.

The way back out is uninstall-server-from-hc: out of its hosted cluster first, if a NodePool took it, then out of the MCE’s inventory.

The first thing to know

Two ways to trigger it: name a server, or don’t

server_names is optional, and leaving it out is the normal mode. The InfraEnv’s agent labels are then the hardware query, so you ask for “a server for this InfraEnv” and the workflow decides which one. Either way one run installs one server; several servers are several runs (below).

Naming a server narrows the pool — it does not lower the bar

Every other rule applies identically in both modes: server-scan allocates only a HEALTHY server with at least two NIC MACs and a healthy network (two link-up ports actually read), and the run still needs a bmc_vendor this orchestrator has an Ironic driver for. So a named server that cannot carry a bond is refused exactly as it would have been inside a pool draw.

The only behaviour a name changes is the already-installed refusal. Naming a machine is a request to converge that machine, so an existing BareMetalHost is the expected state rather than a reason to give the server back.

The pool: the InfraEnv’s flavor, size and site labels

Under the naming convention (since 2026-11-22) a server is named ocp-<flavor>-<size>-<site>-<serial> and an InfraEnv <flavor>-<size>-<zone>, so the InfraEnv’s name no longer says which servers are its: the zone is in no server’s name, and the site is in no InfraEnv’s. Each InfraEnv carries every part as an agent label, so the query is built from three of its spec.agentLabels:

# InfraEnv c200-mtl-az1
spec:
  agentLabels:
    redbull.io/flavor: c200
    redbull.io/size: mtl
    redbull.io/site: five
    topology.kubernetes.io/zone: az1   # not part of the query

draws from ^ocp-c200-mtl-five-. The trailing - is load-bearing (the operator, 2026-11-17): the site must end where the server’s next word begins, so five never draws a server of five2. Each of the three must be present and one lowercase word of letters and digits, or the run fails before anything is allocated (InfraEnvAgentLabelsError, naming each label). A named install needs none of them.

A server-lifecycle-worker older than this rule reports no labels; a run against it, and every run started before it, still draws from the InfraEnv name’s first three words (c200-mtl-haifa-az1 → ^ocp-c200-mtl-haifa-). The zone is not filtered on yet: drawing only servers whose zone in server-scan matches the InfraEnv’s waits on server-scan’s allocation taking a zone.

Read this first

One run, start to finish — in plain terms

The phase-by-phase detail is further down. This is the shape of it: who checks what, which machine is touched when, and what happens when something goes wrong.

server-scan allocates the run one server, already locked

Say you ask for a server for InfraEnv x on MCE-A. The run asks server-scan for one (POST /servers/available, its ADR-0063). server-scan picks a candidate, locks it for this run (2 h, as “being installed into MCE-A”), live-checks it against its vendor manager while locked, and hands it over — or releases it and tries its next, up to five. Call the server it hands over S1: no other run can be given S1 now.

  1. Check S1 (seconds, nothing written): a usable name, a known BMC vendor, a BMC address, and no BareMetalHost for it already in MCE-A. Its NICs and MACs are not checked again — server-scan did that while it held the lock — but the run picks which two of them form the NMStateConfig’s bond. Fails any of these → S1’s lock goes back and the run fails, saying which.
  2. Create S1’s Secret, BareMetalHost and NMStateConfig in MCE-A. Ironic powers the machine on and boots it from the discovery ISO.
  3. Wait up to 1 hour for an Agent. An Agent is the machine phoning home from the ISO — proof that the BMC, the bond, the VLAN and DHCP all worked. The lock is renewed for 2 h as this wait starts.
  4. Agent appears → extend S1’s lock to 24 h: the install succeeded. Then read server-scan every 5 minutes until it shows S1 INSTALLED_TO_INVENTORY or INSTALLED, release the lock, and finish — usually 5–15 minutes. Not seen within the 24 h, the lock is left to expire and the run still completes.
    No Agent after 1 h → delete S1’s resources from MCE-A, put S1 in maintenance in server-scan, release its lock and fail, saying where the host’s own state points. No run is given S1 again until someone ends its maintenance in server-scan.

One server per run (the operator, 2026-11-17). Until then a run drew several candidates and tried the next whenever one was unusable — an hour-deep missing Agent included. Now a failed run has given its server back, and asking again starts a new run with a new allocation. A run started before 2026-11-17 still finishes the old way.

Why the lock exists, and what the 24 h hold is

server-scan learns a machine is taken only when a cluster reports it — its membership jobs, every 5 minutes where they are enabled. Until then the machine still reads AVAILABLE. The run’s “already has a BareMetalHost?” check only sees its own MCE, so without a lock a run for MCE-B could draw S1 minutes after MCE-A installed it, and two clusters would drive one BMC.

The lock closes that gap: server-scan never allocates a locked machine, and takes the lock in the very call that allocates one, so no two runs can be handed the same server. The 24 h hold after success writes nothing to any cluster. It only keeps S1 out of every other run’s draw until server-scan can see it in a cluster for itself — and the run waits for exactly that (phase awaiting-server-scan): once server-scan shows S1 INSTALLED_TO_INVENTORY or INSTALLED it hides S1 from every draw itself, so the run gives the lock back (phase releasing-lock; the operator, 2026-11-09).

remove-server-from-mce does not give this lock back (it did from 2026-10-31 until the operator removed that on 2026-11-17): a lock is its holder’s. Taken out of MCE-A before server-scan reported it, S1 stays locked until this run sees server-scan report it, or the lock expires.

One precondition, and one known gap

The 24 h hold relies on server-scan’s agents job. Every MCE add-server-to-mce targets runs the Agent stack (an InfraEnv and an AgentServiceConfig), and server-scan’s nodes-status agents job runs there every 5 minutes: it matches each Agent to its server by hardware serial (else by its hostname, which the BareMetalHost sets to the server name) and marks a server with an unbound Agent INSTALLED_TO_INVENTORY (a bound one INSTALLED), after which it is never drawn again. So the hold only has to last a few minutes — which is what the run now waits for before it gives the lock back. An MCE without that job would read the machine as AVAILABLE again once the 24 h — server-scan’s ceiling — ran out; the run then completes keeping the lock, and says so.

A crash mid-create strands resources. The BareMetalHost stays on the MCE while the lock expires after 2 h, so after that the machine is drawable while still pointing at one cluster. Clean these up by hand, or re-run the same named install (server_names set to that machine) to converge on them. server-scan’s allocation refuses a locked machine even to the run that holds the lock, so a named run it refuses reads the machine’s record and goes on when the only reason is its own workflow id’s lock, which it then extends. Any other refusal of a named server — another run’s lock, a cluster’s claim, maintenance, its health — fails saying which.

Five phases, in order

What the run does

Each card carries a phase — read live off a running workflow through a Temporal query, which is how GET /workflows/runs/{workflow_id} can tell you where inside the run an install currently is.

1

get_inventory_segment

phase resolving-vlan

The MCE’s INVENTORY segment, found by cluster name — one inventory network per cluster, so the VLAN is a property of the MCE this run targets and of nothing else. It is read before a server is allocated, because no machine could make a missing allocation usable — and one allocated first would sit locked for nothing.

GET/api/segments?type=INVENTORY · once per run, on the SEGMENT-LIFECYCLE queue

On the other domain’s queue on purpose: the Segments Manager token already lives on segment-lifecycle-worker, and routing one activity there beats a second copy of that credential on this limb. The endpoint has no cluster_name filter, so the cluster match is made client-side — and re-checked in the workflow, because this is the one value that decides which VLAN a host is tagged onto.

No segment for this MCE → InventorySegmentNotFoundError; two → AmbiguousInventorySegmentError; one belonging to another cluster → InventorySegmentMismatchError. All three non-retryable — an operator fixes the allocation, retrying does not. There is deliberately no vlan_id input: a caller-supplied VLAN could contradict the segment the cluster owns.

2

allocate_server

phase acquiring-server

ONE call to server-scan, which allocates the run one server (its ADR-0063, since 2026-11-17): it draws a candidate that is unclaimed, reachable, not in maintenance and at the requested health, locks it for this run — holder add-server-to-mce, this run’s workflow id, 2 h — live-checks it against its vendor manager while locked, and returns it; a candidate failing the check is released and its next tried, up to five. So the server that comes back is already the run’s, and freshness is server-scan’s problem rather than ours.

POST/servers/available {pattern | name, max_health: HEALTHY, min_nic_macs: 2, holder, workflow_id, mce_cluster, infra_env, namespace, ttl_seconds: 7200}

max_health: HEALTHY — that tier only; server-scan also requires its network category healthy at every setting, and min_nic_macs: 2 skips a machine that could not carry a bond. Every “nothing could be reserved” is server-scan’s 503 NO_AVAILABLE_SERVER, its reasons named (INSTALLED, RESERVED, HEALTH, VENDOR_ERROR, …) → ServerNotAvailableError, and the run fails; a 503 without that code (a proxy, a restart) is waited out. A name spanning several documents → AmbiguousServerNameError. It takes seconds as a rule and up to ~22 minutes at server-scan’s worst (five live checks), so the activity heartbeats and allows 30.

Not idempotent: server-scan matches a lock to the request that took it, so a retry after a lost answer is allocated another server, and the first frees itself at its 2 h TTL; a cancel during the call leaves the same. A run started before 2026-11-17 still asks GET /servers/available (stored data, unlocked) for several candidates, as it did.

3

Checking the allocated server

phase selecting-server

The server is installed only if it passes every one of these. Most of it is pure workflow logic — no activity, no round trip, and it replays identically:

  1. its server-scan name can be a Kubernetes resource name once lowercased;
  2. its bmc_vendor is one this orchestrator has an Ironic driver for — a STANDALONE machine reports null, and guessing IPMI would be silently wrong for a Redfish-only BMC;
  3. server-scan actually collected a BMC host for it;
  4. it does not already have a BareMetalHost — one read, skipped when the server was named.

Its NICs and MACs are not judged again: server-scan allocated it with its network healthy (two link-up ports read) and its MACs normalized (the operator, 2026-11-17). The run only picks the two bond members (below) — the NMStateConfig and the BareMetalHost’s boot MAC are written from them — and a MAC the limb cannot use is refused there, InvalidMacError, before the BareMetalHost or the NMStateConfig is written.

GETbaremetalhosts/<server> · on the MCE’s queue

One that fails a check is given back, and the run fails with that check’s error type (UnknownBmcVendorError, InvalidServerNameError, NoBondableInterfacesError for fewer than two ports with a MAC, …), naming the server: one server per run (the operator, 2026-11-17). Nothing was written for it, so its lock goes straight back. A run started before then skipped it for its next candidate instead.

The lock is the guard across MCEs. server-scan lists a machine AVAILABLE until a cluster reports it, and the probe above only sees this MCE — so without it a server installed into MCE-A is drawn again by a run for MCE-B, and both clusters drive one BMC (server-scan’s ADR-0035). The allocation took it for this run’s holder and workflow id, so the run’s own renewals extend it: renewed as the Agent wait begins, extended to a day on success (phase holding-server) and released once server-scan shows the server installed (awaiting-server-scan, releasing-lock), or after a rollback’s teardown. A failure anywhere else leaves it to expire, because half-created resources may still name the machine. Phase reserving-server is left only for a NAMED server the allocation refused that the run takes anyway: its own leftover lock (a re-run), or allow_unhealthy — the lock is then taken here, before anything is written.

4

create_bmc_secret → create_baremetal_host → create_nmstate_config

phases creating-secret / -baremetalhost / -nmstateconfig

In dependency order: the BareMetalHost references the Secret by name, so the Secret goes first. All three are idempotent — an existing resource is success, never an overwrite, so a BMC credential or a bond an operator corrected by hand survives a re-run.

POSTsecrets/<vendor>-cred-<server> · credentials from THIS worker’s Secret
POSTbaremetalhosts/<server> · customDeploy: start_assisted_install
POSTnmstateconfigs/<server> · 802.3ad bond + tagged VLAN

The NMStateConfig is named after its server, like the BareMetalHost (since 2026-11-25). Until then it was nmstate-config-<server>, and a host installed then keeps that object: nothing renames it. One still under the old name that matches the install is success and is left where it is; one that differs is replaced, under the server’s own name; a server never ends with two.

The Secret’s and the BareMetalHost’s names are byte-identical to the operator’s, so a cluster already holding resources bmhgen created is converged rather than duplicated. The one difference: names are lowercased, because server-scan names carry an uppercase vendor serial (…-HP0001592) and Kubernetes rejects any uppercase letter in a resource name outright. bmhgen never met this — its names came from a CR a human had written.

5

find_agent_for_host, on a bounded timer

phase awaiting-agent

An Agent is the only observation that proves the install worked. It exists because the machine POSTed, booted the discovery ISO and reached assisted-service — so in one reading it proves the BMC accepted virtual media, the bond formed, the VLAN was the right one and DHCP answered. A 30-second durable timer, a 1-hour deadline: bare metal POSTs for longer than a VM takes to boot.

The Agent is matched by bond MAC, never by name. BMAC names an Agent after the host's own inventory UUID, and the live CRD's agent.spec carries approved, clusterDeploymentName, role and installation disk — no reference back to the BareMetalHost at all. Both bond members are searched, since the host registers with whichever NIC brought the ISO up.

This replaced a 10-minute Ironic-registration deadline, which was the wrong signal in both directions. It passed hosts that would never boot — one whose bond or VLAN is wrong registers perfectly and is then never heard from again — and it could not recognise a dead one: on an unreachable BMC Metal3 reports provisioning state registering with operationalStatus: OK and no errorType, observed unchanged for 14 hours on a live cluster. Nothing but the deadline itself ever distinguished a slow host from a dead one; an Agent distinguishes them by existing.

6

delete_host_resources, maintenance, then the run fails

phases rolling-back / setting-maintenance

No Agent by the deadline: the server’s NMStateConfig and BareMetalHost are deleted and the run waits for metal3 to let the BareMetalHost go (below), the server is put in maintenance in server-scan (phase setting-maintenance; the operator, 2026-11-17), and only then its install lock released (phase releasing-server). The run fails as AgentNeverAppearedError, saying where the host’s own state points (an Ironic registration error: the BMC; none: the bond, the VLAN, DHCP). A run started before 2026-11-17 releases the lock with no maintenance and goes back to step 3 with its next candidate.

PUT/servers/{id}/maintenance {reason} · then DELETE /servers/{id}/reservation

Why maintenance, then the release. A machine that cannot boot into the InfraEnv would only fail the next run that drew it, an hour later. server-scan’s allocation skips a server in maintenance, so once it is there the lock can go back. The other order would leave a moment in which another run could be handed it. The reason names the run, the InfraEnv and MCE, and where the host’s state points; end the maintenance in server-scan once the cause is fixed, and the machine is drawable again. If the cause is the MCE’s (its VLAN, DHCP on its inventory segment), each run that fails puts one more machine there, so look at the first failure before asking again.

server-scan refusing the maintenance (a token without the admin role, a rejected request) keeps the lock instead, to expire after its 2 h, and the failure ends “Its lock is kept until it expires, because server-scan would not put it in maintenance”. A server server-scan no longer knows is released as before.

Leaving a rolled-back host in place would strand that machine invisibly: server-scan reports a server unclaimed until a cluster reports the node, so no other MCE would know it was taken.

The rollback never forces metal3 (the operator, 2026-11-24, after 2026-11-23). The same rollback is used here, after a lapsed lock, and after an IPMI boot entry that never published:

  1. The NMStateConfig and the BareMetalHost deleted (delete_host_resources) — no detached annotation, and metal3’s baremetalhost.metal3.io finalizer never touched. On the delete metal3 deprovisions the host: powers it off through its BMC, deletes its ironic node, and only then lets the BareMetalHost go.
  2. Wait for it: the BareMetalHost is read every 15 s, for up to 15 min, until it is gone (30–45 s with a BMC that answers).
  3. Then the BMC Secret, if it outlived the host: metal3 needed it for the power-off. Its name is read from the host’s own credentialsName before the delete.

Still there after 15 minutes: the run fails with BmhDeletionTimeoutError, naming why it was rolling back and metal3’s state and error — usually a BMC it cannot reach. Nothing after the delete is done: no PXE unmap, no maintenance, no release. A BareMetalHost still points at the machine, so its install lock runs to its expiry. Fix the BMC and metal3 finishes on its own. The BareMetalHost stays Deleting meanwhile, visible on the MCE.

Why never force it. Until 2026-11-24 the rollback detached the host and, 30 s after the delete, dropped metal3’s finalizer itself. A deprovision through a BMC that answers takes 30–45 s, so that cut healthy deletes off half-way and orphaned the ironic node, whose power sync then forced the machine to a stale power state every minute. A run started before then still rolls back that way (teardown_bmh_resources).

✓

Result

phase completed

The server that is now installable, its VLAN, the BMC address that was written, the bond MACs and the boot MAC — plus agent_name, the Agent that proved it, and attempts, how many servers were installed and watched before one produced one (always 1 since 2026-11-17; more only on a run started before, which drew candidates). resources_changed is false for a re-run that found all three resources already present — the run still succeeds, and the flag says nothing was written this time. bmh_registered is implied rather than separately observed: an Agent cannot exist unless Ironic registered the host and drove it through a boot. lock_released says whether the install lock was given back once server-scan showed the server installed (server_scan_state, the last state read), lock_detail what happened — false keeps the lock to expire on its own and is still a success.

Everything between step 3 and the Agent is BMAC’s, not this workflow’s: it sees the infraenvs.agent-install.openshift.io label, finds the InfraEnv in the same namespace, and attaches its discovery ISO over virtual media. This workflow does not orchestrate any of that — it only waits for the one artefact that proves all of it happened.

The subtle part

Two link-up NICs on two distinct physical ports

Both halves of that sentence exist because of a specific way of getting it wrong. Since 2026-11-17 server-scan guarantees the link-up half for every server it allocates, and the run only picks the two members — one per physical port, link-UP first, in server-scan’s order. The strict refusal below still applies to a run started before then.

Members come from interfaces[], never nic_macs

server-scan reduces Dell NPAR partitions to one entry per physical port in network.interfaces, but leaves identity.nic_macs whole on purpose. A 4-port partitioned card therefore reports 4 interfaces and 16 MACs.

bmhgen indexed that MAC list positionally, which can bond two partitions of one physical port: one wire, no redundancy — and it looks correct right up until that wire fails. Distinctness here is by port, not by interface, so a Dell controller/port/partition location collapses to controller/port and two partitions of one port share a key.

UP is required strictly, and that excludes whole vendors

Not “not DOWN” — UNKNOWN does not qualify. HPE OneView’s portMap carries no link state at all, so server-scan stores UNKNOWN unconditionally, and Intersight vNICs mostly report none either. Servers from those collectors therefore fail bond selection rather than being quietly passed over.

That is a decided, accepted trade. The failure names the provider and every observed link state, because the usual cause is that the collector cannot report link state rather than that the hardware is down — and from the workflow’s side those two look identical.

server-scan now applies it before it allocates (its network category is HEALTHY only with two links read UP), so these servers are never handed to a run in the first place.

Why the overall health tier is not enough on its own

server-scan’s rollup is max(category severities), and UNKNOWN ranks below HEALTHY — so a category that was never read cannot lower it. A server whose NIC read failed has no network facts to fail a policy on, and comes out HEALTHY overall.

server-scan closes that itself since 2026-09-26: /servers/available also requires the network category to be HEALTHY, which it is only when at least two links were observed UP. The allocation also sends min_nic_macs: 2 (since 2026-11-17), so a server whose MACs were never read is not even locked for the run. So the run judges neither again; it still picks the two bond members, because the bond and the boot MAC are written from them.

Where the VLAN comes from, and why it is step one

An MCE has one inventory network, found by cluster name

The VLAN a host is tagged onto belongs to the MCE this run targets — not to the machine chosen, and not to the caller, who could otherwise supply a VLAN contradicting the segment the cluster actually owns. So the lookup takes one input, the cluster name, and runs before a server is allocated.

Why it is resolved before the allocation

A missing inventory allocation is the same for every machine in the pool, so no server could make it usable — and allocating one first would lock a machine for a run that cannot use it. Failing at the lookup names the real problem immediately, with nothing locked.

Run as InventorySegmentNotFoundError — non-retryable, because an operator allocates the segment and retrying does not. Two INVENTORY segments for one MCE is AmbiguousInventorySegmentError: broken data a human resolves, since picking one would tag hosts onto a VLAN chosen by document order.

bmc_vendor picks the driver, not the network

Ironic still reaches an HP, a Dell or an Intersight-managed server over Redfish and a UCS blade over IPMI — that is the bmc.address scheme, built from what server-scan parsed. It no longer selects a segment.

It was briefly two networks

For a day the type was split by how a BMC is driven — INVENTORY_REDFISH for HP, Dell (iDRAC is Redfish underneath) and Intersight, INVENTORY_IPMI for a UCS blade — on the reasoning that Ironic reaches the two over different networks. That made the segment a property of the chosen machine, so the lookup moved inside candidate selection, was memoized per class, and a candidate whose class the MCE had not allocated was passed over like any other unusable one.

Reverted on both sides on 2026-09-27, by the team lead’s decision: two inventory scopes per MCE is a second thing to allocate, track and keep in step, and an MCE holding only one of them made “this cluster takes no servers driven that way” a state every consumer had to model. The Segments Manager’s Literal accepts plain INVENTORY again and rejects the two split values, so an allocation still carrying one must be re-typed.

An InfraEnv whose hosts are VMs

A KubeVirt InfraEnv: the run has its own VM made, then installs that one

An InfraEnv says what fills it in the labels its Agents receive. When its spec.agentLabels say redbull.io/size: kv<cpu>, its hosts are VirtualMachines, and the run asks server-scan for nothing: it has one VM made by create-vm, as its child, and installs exactly that VM. Nothing is locked, held or released in server-scan — the VM is this run’s from the moment it exists.

What tells a VM InfraEnv from a bare-metal one

The size label, and only it: mtl is bare metal, anything starting kv is KubeVirt. The InfraEnv’s own name is not read and need not follow the naming convention. A size that starts kv but is not a VM size (kv7, kvx) is still a VM InfraEnv — refused, never a draw from server-scan.

What create-vm is asked for comes from the same labels and from the MCE’s name:

create-vm needsfromrule
flavorredbull.io/flavora letter, then letters and digits (c200)
vCPUs, memoryredbull.io/sizekv<cpu>, even, 2..256; memory is cpu × 7.5 GiB
zonetopology.kubernetes.io/zoneaz<N>
site, lifecyclethe MCE’s nameocp4-<lifecycle>-mce-<site>-<id>; redbull.io/site must equal that site

Each label is judged by the rule the InfraEnv name parser applies to that part, so create-vm is asked for exactly what its own route would derive from a conventional name. Every problem is named in one failure — InfraEnvAgentLabelsError, or MceNameNotConventionalError when it is the MCE’s name — before any VM is made.

What is written on the MCE for a VM

The same three objects as for a server, in another order and with one NIC:

objectnamewhat differs
NMStateConfig<vm>First. ONE NIC, enp1s0, no bond: the VLAN enp1s0.<vlan> on DHCP, straight on it
Secretkubevirt-cred-<vm>the kubevirt-redfish user, KUBEVIRT_BMC_*
BareMetalHost<vm>redfish-virtualmedia://<host>/redfish/v1/Systems/<vm>; boot MAC = the VM’s

<host> is the kubevirt-redfish Route of the KV cluster the VM landed on: one pattern on this MCE’s worker (KUBEVIRT_BMC_HOST_TEMPLATE) in which only {kv_cluster} changes. The system id is the VM’s name (kubevirt-redfish runs systemIdConvention: legacy). The VLAN is the MCE’s inventory VLAN, as for every host; the MAC is the one KubeMacPool gave the VM.

The NMStateConfig comes first so the VM can never boot a discovery image from before its own network config — the IPMI order’s reasoning. There is no PXE step (Redfish virtual media) and no NMStateConfig replace step: a differing NMStateConfig under a brand-new VM’s name would be another machine’s, not a leftover.

a

read_kubevirt_bmc_config

phase checking-kubevirt-bmc

Before any VM exists: can this MCE’s worker reach a VM’s BMC at all — the host pattern and the Redfish user. Not configured fails the run (KubevirtBmcNotConfiguredError, every missing key named) with nothing made. A worker from before this step cannot answer it and is retried until the new one polls, so that rollout window waits here too, with no VM.

b

create-vm, as an awaited child

phase creating-vm

Id create-vm-for-<this run’s id>, on create-vm’s own queue. It takes its zone’s lock, picks the oldest KV cluster of the zone with room, has the VM created Halted and waits for its disk. It answers with the VM’s name, MAC and KV cluster — all the install needs. The child’s run id is the VM’s redbull.io/created-by label: the run keeps it (create_vm_run_id), because that is what finds and deletes the VM.

Its failure fails the run as CreateVmFailedError, carrying create-vm’s own type and message (NoKvClusterFitsError, a lock not had in time, a disk that never bound): create-vm leaves no VM when it does not complete, so there is nothing to undo. One already running under that id — the child of an earlier run that was terminated — is CreateVmAlreadyRunningError.

c

NMStateConfig → Secret → BareMetalHost, then the Agent

phases selecting-server / creating-… / awaiting-agent

First one read: a BareMetalHost of the VM’s name already on the MCE is another machine’s (VmNameClashError; a VM’s name is unique across KV clusters only by chance). Then the three creates, and the same wait as for a server: an Agent reporting the VM’s MAC, every 30 s, up to an hour. With an Agent the run completes at once — no lock to hold, no wait for server-scan.

A run that does not end with an Agent leaves no VM

What a bare-metal run does about its lock, this run does about its VM: a Halted orphan would count against its KV cluster for ever, and a re-run makes a new VM.

  • No Agent in the hour, or a create the worker refuses for good: the NMStateConfig and the BareMetalHost are deleted, the run waits for metal3 to let the host go (phase rolling-back), then the VM is deleted on its KV cluster (phase deleting-vm, by its run-id label, name and MAC). The failure says so.
  • Never the VM while its BareMetalHost may exist: metal3 powers a host off through its BMC — the VM’s own kubevirt-redfish — before it lets it go, and ejects the virtual media, which is what deletes kubevirt-redfish’s <vm>-bootiso-… disk (nothing owns it). A host still deleting at 15 min keeps the VM; the failure names it, its KV cluster and its label.
  • A conflict at a create (an object of the VM’s name that is not this install’s) removes nothing on the MCE — a delete by name could take another host’s — and deletes the VM.
  • The delete has no deadline: a KV cluster that is down is out-waited, the run sitting in deleting-vm. One its cluster refuses (403, an identity that does not match) is named in the failure with its label, to delete by hand.

A run that FAILED has no result: what was done about its VM is in progress.vm_rollback, beside kv_cluster, create_vm_workflow_id and create_vm_run_id.

Cancel and terminate

  • Cancelled while create-vm runs (phase cancel-stopping-create-vm): the child is cancelled and removes its own VM. If it had just completed, its VM is known and this run deletes it.
  • Cancelled after the VM exists: as for a server, remove-server-from-mce takes the host out of the MCE (after the 2 min settle), then the VM is deleted — bounded at 10 min, after which progress.cancel_rollback says where it is.
  • Cancelled after the Agent: nothing is undone; the VM is installed and stays.
  • Terminated: terminate runs no code here, so the child’s close policy does it — REQUEST_CANCEL, the one awaited child that is not abandoned. create-vm, cancelled, removes its own VM. A VM whose host this run had already written is not cleaned up by a terminate: use cancel.

Not for a VM InfraEnv: server_names — the run makes its own VM, so there is no server to name (NamedServerOnKubevirtInfraEnvError, nothing allocated). count works as always: N runs, N VMs, each child taking the zone’s lock in turn. A VM made by create-vm’s own route has no install path yet.

How a hub workflow writes to a dozen clusters

One worker per MCE, routed by task queue — not by credentials

The brain runs on the hub. The resources belong on the MCE that owns the InfraEnv, which is a different API server at its own api.<mce>.<domain>.

mce_cluster is the whole mechanism

It names two things at once: the INVENTORY segment the VLAN is read from, and the activity queue every cluster write is dispatched to (server-lifecycle-activity-<mce_cluster>). A server-lifecycle-worker runs inside each MCE, polls only its own queue, and talks to its own API server as its own ServiceAccount.

So the VLAN’s cluster and the cluster written to are the same string and cannot disagree. The worker’s MCE_CLUSTER setting builds the same queue name, which is why it must match what callers send.

Routing beats holding kubeconfigs

No cross-cluster kubeconfig exists anywhere, and because workers dial out to Temporal to long-poll, the hub never needs inbound access to an MCE’s API server. The alternative — one hub worker holding a kubeconfig per MCE — concentrates admin-equivalent credentials for the whole fleet onto one pod.

A run whose MCE has no worker waits rather than acting. The cluster writes carry a 5-minute schedule-to-start timeout, so history shows repeated timeouts instead of a task sitting invisibly in a queue, and the status endpoint reports activity_queue — which says which MCE to go and look at.

Running it twice

A re-run converges — or refuses, but never lies

Temporal retries activities and operators re-POST things, so both have to be safe. “Safe” here means more than “does not crash”.

An existing resource is success once it MATCHES

An ALREADY EXISTS is not an error, and not an upsert either: the object is left exactly as it is. But reporting success for one that names a different BMC address, credential Secret, boot MAC, InfraEnv or VLAN would describe an installation that is not the one on the cluster — so those fields are read back and compared, and any disagreement is a non-retryable BmhConflictError naming the field. A human decides which is right.

Only identity fields are compared. Status, an operator’s added annotation, a hardware profile corrected by hand: all left alone deliberately. The MAC set is compared unordered — the bond is the same wiring whichever member became nic1.

The id names a slot of the POOL; the probe and the lock cover the rest

add-server-to-mce-<mce>_<infraEnv>_<slot> keys on the hub and its pool (^ocp-<first 3 words of infraEnv>-), not on the machine — which server-scan allocates inside the run — and not on the target. Each hub has its own slots, so it finds only its own runs; the machines themselves are shared by every hub and the install lock keeps them apart. A second trigger while one is in flight takes the next slot: it is a second install, never a 409, because asking the pool again is asking for one more server. A double-click therefore installs two; its callers are people, which is why that was accepted.

That covers concurrent runs. The sequential case an id cannot cover — a second run minutes later, before any cluster has reported the node, so server-scan still calls the machine unclaimed — is the install lock’s first, which the run holds until server-scan shows the machine installed, and step 3’s already-installed probe’s after that. Without the probe, every create would answer “already exists” and the run would report success having added nothing. A run for a different MCE cannot see that BareMetalHost at all — that case is the install lock’s alone.

Several servers at once: count, or a list of server_names

Every server is its own workflow run — its own id, status and failure, never one run for a batch. Every run the pool picks for is on a slot (add-server-to-mce-<mce>_<infraEnv>_<slot>), and slots still running are stepped over: send nothing more and one install takes the first free slot; send count: N and N are installed in parallel. So a second install while the first runs takes _2, and a second batch of 5 while the first installs takes _6–_10. Send a list of server_names and each machine gets its own run, on the same id a single named install uses.

No two runs take one machine, however they were asked for — two batches, or 5 from the pool and then 5 by name. server-scan allocates each run its own server, locking it in the same call (a compare-and-set there), and never allocates a locked one; a named machine another run took first fails its own run.

So a run sizes nothing for its siblings: every pool run asks for one server and every run’s input is the same. A run server-scan has nothing left for fails with ServerNotAvailableError and its reasons (RESERVED when its siblings took the rest): the pool had fewer free servers than were installing. Until 2026-11-17 each run drew candidate_count candidates instead, sized by the slots still running; the field is a 422 now.

Why one route, and why it is shaped this way

Decided with the operator on 2026-10-23, after someone asked for a second healthy server from the same InfraEnv and got the 409. Parallel installs already existed, as install-server/bulk with count, but nobody found them: “bulk” reads as a list of specific servers, and this page still said parallel installs had not been built. Now there is one route, and the body says what you want.

  • One workflow per server, never a batch workflow. Each server gets its own id, status, failure and history, and Temporal’s one-run-per-id rule is what refuses a second run for the same machine. Every other /bulk in this repo works the same way.
  • No 409 from the pool (revised 2026-10-24). A single install sent while another ran used to be refused until the first finished — up to an hour. Asking the pool again is asking for one more server, so it now takes the next slot, like count: 1, and keeps the simple reply. A named machine keeps its 409: asking twice for one machine is one install.
  • server_names takes a string or a list, and the reply follows what was sent. One name keeps the simple {workflow_id, run_id}. A list always gets the report, so a script that sends a list can always loop over results.
  • count next to names is a 422, not ignored. It sizes a draw from the pool, and a named server is drawn alone. Silently ignoring a field the caller sent would hide a misunderstanding. (candidate_count is a 422 anywhere since 2026-11-17, saying it was removed.)
  • count starts N more and is not retry-safe: sent twice, it starts 2N runs. An idempotency key was considered and left out, because the callers are people using Swagger or curl, not controllers. Revisit this if a controller ever calls it.

The options that were weighed, and the collision cases, are in docs/design/add-server-to-mce-api.md.

HTTP surface

How you start it and how you watch it

Served by workflows-orchestrator-api (Swagger at /docs). Async throughout: the POST hands back the workflow id at once and you poll it. To watch runs without curl, the same API serves a temporary page at /ui/server-lifecycle, until the ClickCluster Platform UI exists: each run’s steps, its server, and why a failed run’s server could not be installed. It can start a pool draw or named installs.

POST /workflows/server-lifecycle/add-server-to-mce 202 · 409 if that named machine is already installing

The minimum body is two fields — the InfraEnv to fill and its MCE; namespace defaults to inventory. The reply follows what was sent: one run (nothing more, or one name) is {workflow_id, run_id}; several (count, or a list of names — even a list of one) is a per-run report. The body forbids unknown fields. namespace must be the InfraEnv’s own namespace. BMAC looks for the InfraEnv beside the BareMetalHost, so a host created elsewhere is never given a discovery ISO.

GET /workflows/runs/{workflow_id} 200

Domain-agnostic: workflow ids are globally unique, so one route serves every domain. It addresses the progress query by name, so the response carries the live phase, the server chosen once there is one, and the activity queue this run dispatches to.

// 200 while running
{
  "status":   "RUNNING",
  "progress": {
    "phase":          "awaiting-agent",
    "server_name":    "ocp-cisco-m6-bat-yam-64c-512gb-WZP12345",
    "activity_queue": "server-lifecycle-activity-ocp4-mce-bat-yam-01"
  }
}

A phase that does not advance is diagnosable from this alone: it means nothing is polling activity_queue, so that MCE has no server-lifecycle-worker deployed or it cannot reach Temporal.

No healthy server server-scan can allocate, a server the run cannot install (no BMC driver, a BareMetalHost already there), and a host that never registers an Agent are all FAILED runs on the status endpoint — not 4xx on the trigger. Everything the outcome depends on happens inside the run, as a retried activity. A failed run has given its server back — one with no Agent in maintenance first: ask again for a new run.
